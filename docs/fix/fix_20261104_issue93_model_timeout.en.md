## Proposed implementation

### P1: harness correction; one attempt-deadline owner

Production transport already handles its own deadline and caller cancellation correctly. No production timeout/classification/retry change unless a failing test proves one necessary. Unknown LOCAL aborts correctly fail closed. Core transport owns the attempt deadline. Retain the existing 120-second default, at most three sends, 2s/10s backoff and Retry-After. Do not add concurrency, a new request queue, unlimited automatic recovery or hidden SDK retries. Remove competing 90-second attempt timers from the manual/online wrappers. Physical-send/tool counts and the acceptance admission window remain bounded.

Wrappers check call/tool/window limits before every send and throw explicitly named BUDGET_ errors. They must not introduce an inner timer aborting an in-flight SDK stream. Define the stop sequence as admission cutoff, up to 120 seconds of drain, then normal Core shutdown through its known parent signal. No subsequent physical send/retry is admitted after cutoff. Retry waits (including unbounded provider Retry-After) may outlive the attempt timer, so the final Core shutdown also cancels pending waits or remaining in-flight work as attributable CANCELLED. Record actual drain time and shutdown completion; do not call this a strict 25-minute completion cap. A pre-send BUDGET_ refusal is recorded as rejected, not as a physical request. Explicit user cancellation/Core shutdown still terminate promptly through Core's known parent signal and remain CANCELLED. Manual-service lifetime shutdown uses the known Core lifetime signal, not another hidden SDK abort. Crucial ordering in the harness: disable admission and signal modelLifetime(store) with CORE_STOPPING before awaiting server.close(); the current API close waits for running commands before App.close reaches that signal. A local 503 + Retry-After:3600 probe confirmed that API close was still waiting after 150 ms, then completed 88 ms after the explicit known-parent signal, with one physical send. Record cancellation of the retry wait separately; do not rewrite the preceding failed TRANSIENT ModelCall as CANCELLED. Never reclassify every aborted error as TRANSIENT; unknown aborts remain LOCAL.

Change the test tool-budget wrapper to consume/relay preview events as they arrive and check the tool budget before successful completion. Count every physical request; reject over-budget results. Preserve durableStream's invariant: **Agent must not execute streamed tools before the complete successful response is durably saved**. Partial-tool/error/over-budget streams must cause no business effects. No model replacement or SDK upgrade.

### P2: acceptance-side timing only in this scope

Instrument acceptance wrappers for fetch start, response headers, first/last SDK event, completion/termination, HTTP status and abort origin. Separate Input acceptance-to-claim, claim-to-payload preparation and actual network stages. Retain timing/status/counts and allowlisted correlation IDs only; no auth/full response headers or additional bodies, no per-token journal writes. Unobserved fields are null; SDK message creation time is not TTFT.

Defer persistent production ModelCall timing fields and splitting first-byte/idle/total timeouts. No production ModelCall schema expansion in this patch. The existing 120 seconds is total time; a continuously streaming response can still reach it and be retried. Test and disclose it, do not silently reinterpret it as an idle limit. P3 session/failure API extensions still come from source schema generation.

### P3: explicit blocked Main and explicit recovery

GET session adds a safe recovery_mode derived from state/model_blocked_call (NONE, EXPLICIT_REQUIRED, NEXT_MASTER_INPUT, CAPACITY_COMPACTION_REQUIRED), plus bounded categorical text; do not directly render arbitrary recovery_error. CAPACITY_BLOCKED maps to CAPACITY_COMPACTION_REQUIRED: show Main paused, offer no /resume, and explain that compaction is required and outside this patch. RECOVERY_BLOCKED with null model_blocked_call, including LOCAL and CANCELLED, maps explicitly to EXPLICIT_REQUIRED. Preserve existing semantics: LOCAL/CANCELLED require explicit resume; marked TRANSIENT/PERMANENT blocks resume the previous batch when the next Master Input arrives. The notice and failure-intent submission hint must explain the applicable behavior. TUI subscribes to the existing session resource and sync invalidation. Show a persistent Main-paused notice, a safe error summary, and an explicit recovery entry. For an unfinished failure Input, FailureDetail overlays session blocking so A does not misleadingly remain Main-processing while B only says accepted without the blocking cause. Preserve UNRESOLVED, do not fabricate HANDLED and do not admit duplicate failure intents.

Recommend adding `/resume` only in ordinary Main as an explicit scope choice for Master approval with this plan, reusing existing POST session/resume, ApiCommand and request reconciliation. Explain that it continues the claimed batch and queued inputs and can consume model budget. A typed slash plus Shift+Enter is explicit recovery intent. Task is a local wrong-page error; authorization/question/failure modes take precedence; wholly pasted commands remain literal. A small separate controller freezes request ID/bytes, single-flights and reconciles lost responses. Resume receipt is not business completion; do not re-send A/B/C/D Inputs or overwrite drafts. New ordinary input is not implicit recovery from LOCAL faults.

Add optional expected_revision to the resume body; TUI always sends the freshly read revision and freezes domain/session identity. Legacy callers without that field retain their existing behavior except for a universal active-loop guard: while a Main loop is actually running, every resume returns applied:false without changing state or generation. Check the live loop, not merely persisted RUNNING state, so crash-left recovery remains possible. Document and test this safety change for all callers; the optional revision path otherwise retains legacy compatibility. The guarded path only allows RECOVERY_BLOCKED with a matching revision: reject with 409 before admission if already stale; check again atomically with the session update at actual dispatch. Two distinct request IDs with the same old revision must only increment generation once. If a queued command becomes stale, return a deterministic applied:false rejection result with a clear code and no effects; admission is not permission to ignore the execution-time guard. The controller reads that result and fresh session state.

The command is QUEUED then RUNNING until the entire drain returns. It can be COMPLETED even when Main blocks again: command completion is not session health. At restart RUNNING becomes UNKNOWN / INTERRUPTED_DISPATCH, never auto-re-dispatched. Reconcile and show the authoritative session; do not silently create a new resume ID. Another failure needs a newly observed, explicit user instruction. Existing LOCAL Inputs are not rewritten, only their original batch explicitly resumed.

Session changes invalidate session, timeline, attention and failure detail. Derive MAIN_BLOCKED only for ACCEPTED/CLAIMED Inputs while their session is blocked, without writing FailureHandling. Test old tool receipts and generation boundaries; no automatic retry of all LOCAL errors or bypass of corrupt tool state.
