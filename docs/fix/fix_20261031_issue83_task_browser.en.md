### Current-set predicate

A browsable task is current when **any** of the following is true:

1. At least one real nonterminal Execution (CREATED, WAIT_PRECONDITION, READY, DISPATCHING, RUNNING, WAIT_DECISION, WAIT_AUTH, CANCEL_REQUESTED, RESULT_UNKNOWN), including paused/closed plans that still own such work.
2. Nonempty queued `pending_requests` or `pending_occurrences` belonging to this Task. Count actual objects once; preserve their identities and due times. `pending_followup_ids` is not an independent current reason: it can refer to a different Task, and same-Task reuse is already represented by pending_requests. A parent with only a cross-Task follow-up is historical; detail may show the link read-only.
3. Effective future work: `state=ACTIVE`, `trigger.kind` in `{AT,INTERVAL}`, parseable non-null `next_due_at`, and either no deadline or `deadline > max(as_of, next_due_at)`. Register this as a display eligibility rule: an occurrence already past its deadline or due at/after that deadline is not effective future work. The actual tick lacks this deadline eligibility check and may still create then expire an occurrence; show any real queued/nonterminal/failed object under the other rules, and do not change tick. IMMEDIATE future work is represented only by pending_requests; its next_due_at starts null. EVENT is only a schema variant at this base, with no supported producer/subscription; it confers no current membership on its own. Do not invent disabled/armed fields. PAUSED alone is not future work. ID lookup explains deadline-ineligible or unsupported schedule facts.
4. INITIALIZING/INIT_FAILED, or an execution of this Task with nonempty unknown_operation_ids, or applicable attention using the current attention-route predicates: AuthorizationRequest.state in {PENDING,APPROVED} with expires_at absent or > as_of; DecisionRequest.state=OPEN with deadline absent or > as_of and owning Execution.state=WAIT_DECISION. Resolve execution/task ownership and current-session access before counting. APPROVED here means waiting for consumption, not a request for Master to approve again. Actionable failure uses activity.ts existing rule: a FAILED execution is current until a newer execution of the same Task supersedes it (journal creation order, not UI invocation-time sort). No new failure-disposition marker is invented. A failed one-shot can therefore stay current until superseded or handled by future #93 semantics; the A1 fixture must account for that. Ended executions may also leave nonexpiring PENDING/APPROVED authorizations: completion obsoletes decisions but does not clear authorizations. Mirror the existing attention rule, keep the task current on that basis, and leave disposition to #92/#93. Exclude these cases from the 4/3/2 dataset unless deliberately counted. A successful ordinary one-shot with no remaining reason is historical even while its plan is ACTIVE.

Register and test the truth table below. These are projection rules, not a claim that every combination can be created through the current public API. PAUSED-with-work and CLOSED-with-work require labelled SEEDED isolated Store records at this base; do not add pause/close APIs just to manufacture them. Real PAUSED-without-work is produced by creating an AT task, stopping the isolated Core until after its due time, then restarting. Read predicates must not mutate plan, attention, retention or queue state. Where the existing domain has no resolved marker, preserve the actual unresolved fact and describe the unavailable action; #93 owns its disposition.

### Time and stable sort contract

- Scope `created_at` = `committed_at` of the first Scope mutation (`expected_revision=0`), with `created_sequence` provenance. Use `projectionFrames[firstSequence("Scope", id)-1].committed_at` after validating the first mutation; reuse replay-derived firstSequence rather than add a redundant creation index. First revision's `updated_at` may be shown only as historical source evidence, not a replacement for committed creation. If first creation evidence is unavailable, return null with a reason, sort after known times, and label unknown; never invent a date or mutate old records.
- Execution `created_at` similarly comes from its first mutation; `invoked_at = started_at ?? created_at`. Keep both values and which one supplied ordering. Group activity means a real nonterminal execution, not ACTIVE plan or a future schedule. Its group key is the maximum invoked_at among such executions. Queue-only groups remain current but do not masquerade as running groups.
- Active groups first by that timestamp descending; ties by stable group ID ascending. Next, inactive ordinary groups by real Scope creation time descending, null last, then Scope ID ascending. Inactive logical Shared is last. Active Shared participates normally in active-group sorting. Use noncolliding logical group ID `shared:null` (ordinary IDs `scope:<id>`) for ties. Shared has no fabricated creation date. A long-stuck RESULT_UNKNOWN remains in the active tier under this definition; its unchanged invocation time governs its position inside that tier.
- Within each group, last execution invocation time descending (latest by this clock, not unrelated updates), null/no Execution last, ties by Task ID ascending. Recent execution selection uses the same invocation order, ties by Execution ID ascending. This defines behavior for not-yet-started executions and clock ties.
- Exclude archived scopes and their tasks from browsing; display only the archived Scope count. A named `kind=NONE` entity remains an ordinary Scope; only null scope_id is Shared.
- Header Scope count = distinct nonarchived ordinary scopes with current tasks. Per-group count = current tasks only. Shared has its own count but contributes no header Scope. No global Task total is added. Empty/history-only groups are omitted by this implementation; historical lookup uses one clearly labelled temporary result section before the current groups, with the real Scope/Shared label even when that group is absent, and never changes any current count. A new search replaces that temporary section.

Build membership, counts and sorted row keys over the **whole authorized set before pagination**. A flattened sequence of scope headers and task rows preserves global order across boundaries; continued headers carry their complete group count. Counts and rows share a projection revision. Start with 50 rows/request, maximum 100, 256 KiB response bound; long goals are labelled previews, and detail provides the full paginated text if required. Client retains at most 200 row metadata entries with a requeryable anchor, not all historical tasks. Do not use loaded length as a total.

List membership/order changes invalidate the old list generation with a recoverable reset, not silent offset drift. The incremental cache stores facts; evaluate time predicates at query time against as_of, schedule a refresh at the earliest membership boundary even without an unrelated sync event, and recompute the list-key/count digest.

If archived, remove cached rows/details/messages and explain unavailability; never keep serving a cached archived conversation. If missing, choose a surviving remembered neighbor with a notice, never transfer a command's target by row number. Pending reads are cancelled/ignored on view changes.
