## 1. 已确认目标与范围

本轮先补齐原设计已预留、但代码未贯通的能力，不先重做任务分类或整个调度器。

1. `instructions.ts` 允许主会话理解、思考、推理、分析和解释；限制执行能力与权限，而不是限制思考能力。
2. `host.ts` 暴露并透传 `reuse_task_id`，允许向原任务提交补充要求；主会话能够查到原任务身份、要求和执行结果，而不是只能拿到不透明 ID。
3. `scheduler.ts` 受理任务复用：同一 Task（任务身份）下产生新的 Execution（单轮执行实例），沿用工作目录和必要材料，保留旧执行历史。
4. `tick()` 支持同一即时任务的第一次、第二次及后续执行；每个已受理执行请求使用稳定的 `occurrence_key`（执行发生键），不能每次扫描都重新生成。

一阶段核心链路：

```text
Master 提出工作 → T1 / E1 → E1 结束并保存结果
Master 补充要求 → 查询 T1 → 指定 reuse_task_id=T1、parent_execution_id=E1
              → 同一 T1 下创建 E2 → 使用本轮要求并沿用原 workspace
再次补充要求   → 同一 T1 下创建 E3
解释已有结果   → 主会话查询、分析并回复，不必增加 task 或 execution
```

默认支持上一轮已结束、尚未回收，且当前没有其他活跃执行或待执行接续的任务。正在等待普通决定的执行仍通过 `task_control` 回答并继续，不伪装成一轮新执行。

本轮不做：运行中追加要求或抢占、完整 Task Inbox（任务输入队列）模块、语义搜索与自动任务归并、并行分支、归档恢复、新的 mission/project 层、绕过 Task 的快捷执行器、长期任务预算体系、WebUI/TUI 任务页重构。必要的字段、持久化和兼容调整属于本轮，不以此扩张产品范围。

## 3. 修复方案

### 3.1 主会话职责：允许推理，不扩大执行权限

修改 `BASE_SYSTEM` 及必要的工具说明，明确：

- 主会话可自行理解需求、分析已有材料、推理、解释、组织回复，以及判断新建还是接续。
- 需要实际执行工具、操作外部资源或委托独立执行上下文的工作，提交 task agent；主会话不因此获得文件写入、bash 或授权能力。
- 查询进度、解释已保存结果或依据，不默认启动执行。既有信息不足时按需查询；需要继续工作时再提交接续。
- 对既有工作的补充、修正优先检查原任务；独立交付可以新建。不要通过“一律复用最近任务”替代原来的“一律新建”。
- 保留结果不明停止、不得编造材料、不得自行授权、不得反复轮询、不得自动创建替代任务等既有约束。

本项与模型推理强度、流式输出和可见思考展示无关，不改动最近完成的显示设置，也不要求模型输出内部思维链。

### 3.2 工具入口：复用字段与任务级查询

继续使用 `task_propose`，本轮不把接续迁移到另一套新工具。

| 输入组合 | 明确语义 |
| --- | --- |
| `reuse_task_id` 省略或 `null`，无 parent | 保持原有新建行为 |
| `reuse_task_id` 省略或 `null`，有 parent | 保持“新任务引用旧执行材料”的行为；不自动变成任务复用 |
| `reuse_task_id=T1`，`parent_execution_id=E1` | 在 T1 内受理新的即时执行请求；E1 必须属于 T1 并满足接续条件 |
| 非空 `reuse_task_id`，无 parent | 返回明确参数错误；本阶段不隐式选择或猜测父执行 |

新增字段在 TypeBox 参数、工具说明、Host 到 Scheduler 的参数传递、请求指纹、持久化提案和回执关联中全部贯通。省略与 `null` 的处理规则统一。宿主提供 session 身份、请求 ID 和控制字段，不让模型自行设置权威状态。

`task_query` 增加可选 `task_id`，保留现有无参数列表和按 `execution_id` 查询的用法。两个查询 ID 同时非空时明确拒绝，避免悄悄忽略一个字段。

按 task 查询至少组合返回：

| 信息 | 用途 |
| --- | --- |
| task ID、计划状态、原始/计划目标 | 确认所查工作身份，区分计划基线与本轮修订 |
| 最近执行 ID、状态、当前活跃/待执行情况 | 让主会话找到可指定的 parent，避免重提运行中的工作 |
| 最近执行的有效目标、约束、验收项及提案引用 | 判断补充要求应如何继承，不能只返回不可读取的 `proposal_ref` |
| 最近结果摘要、详情读取方式、产物引用、待决定事项 | 判断已有证据是否足够直接回应 |
| `can_continue` 与阻止原因，必要时附归档引用 | 对不可接续状态给出可操作的说明；字段名可按现有接口风格调整 |

无参数列表至少保留 task ID、可读目标、状态和最近执行关联，不能要求模型先知道 ID 才能发现任务。详情可按需读取，不把所有 Task Log、原始上下文和文件内容一次装入主会话。

主会话能查询到的信息必须来自当前宿主可访问的任务；受理端重新校验，不能相信模型传入的 ID 或之前查询时的 `can_continue`。不要求“本轮必须先调用过 task_query”才能接续：刚收到的任务反馈可能已提供充分信息。列表浏览不批量刷新全部执行的留存时间；有意读取具体热执行详情才按现有规则刷新，已回收执行不恢复为 HOT。

### 3.3 Scheduler 受理：同任务新执行，不复活旧执行

`propose()` 拆出明确的新建与复用分支。复用失败返回错误，不静默降级成新 task。

接续受理至少检查：

1. task 存在、当前宿主 session 可访问，计划处于本阶段支持的可执行状态。
2. parent 存在、属于指定 task，状态为已结束且 `retention_state` 不是 `RETIRED`。
3. 无 `RESULT_UNKNOWN` 或尚待核实的关联操作，无当前非终结执行，也无已受理但未完成的另一接续请求。检查实际 Execution 状态，不能只把历史 `active_execution_ids` 非空视为运行中。
4. 原 workspace 的归属和路径有效，材料/提案/结果引用可读取；缺失时报告具体原因，不能用新建空目录冒充成功接续。
5. 提案结构、执行器/程序参数、必要前提仍合法。不得因为复用就跳过原有检查和授权。

同一请求的重投先命中既有回执；不能因该请求已经进入运行状态，反而把合法重投判成新的忙碌请求。不同新请求在本阶段遇到活跃或待执行工作时明确返回忙碌，不先接受后丢失；运行中输入排队留待后续阶段。

受理结果必须能关联本次 `request_id`、原 task、父执行、要求快照和待执行发生键。尚未创建 Execution 时不能伪造已运行或已完成状态；创建后可以查到对应 execution ID。重复请求返回原受理关联，可附当前状态，不要求动态计划对象逐字节保持不变。

复用分支不生成新的 task ID，不创建第二个 TaskPlan，不重新初始化 workspace；新建独立 Execution，设置 `continuation_of`。已结束 Execution 的状态、要求、结果和操作历史不倒退、不覆盖；允许按留存协议更新活跃时间和后续关联。

### 3.4 本轮要求快照：使补充要求真正生效

优先复用现有 `goal`、`constraints`、`acceptance_criteria` 等正式提案字段，不把补充指令仅放进 `materials`，也不为本轮另建庞大的要求管理模块。

接续输入规则：

- `goal` 仍为必填，表达同一工作的本轮目标；例如“将现有报告压缩成一页”。原始目标仍保留，不以字符串必须完全相等作为接续条件。
- 未提供或为 `null` 的可继承字段从指定 parent 的执行快照继承，不再退回新建默认值。显式提供的 `constraints`、`acceptance_criteria` 是该字段本轮完整有效值，不做难以确定的自然语言自动合并。
- 显式 `constraints: []` 与省略不同；前者表示本轮无额外业务约束，但不能清除宿主安全规则、授权或仍适用的 Master 上层指令。`acceptance_criteria: []` 必须拒绝。主会话应保留未被 Master 修改的要求。
- `deadline` 省略或 `null` 继承；提供新值须合法且作为明确修订记录。本阶段不把 `null` 同时定义为“继承”和“删除截止时间”。
- 新材料与必要旧材料组合并按引用去重；材料及历史输出仍是证据，不具备修改正式要求或工具规则的权威。
- 复用不自动切换 AGENT/PROGRAM、程序身份或执行器配置。未填写 `program_id` 时继承原执行器，不能误变成默认 AGENT；程序登记、版本、参数及授权照常校验。

每次受理都保存不可变的完整有效 TaskProposal，并保留原始调用/输入关联；新 Execution 绑定自己的 `proposal_ref` 或等价的不可变快照引用。不能只更新共享 `TaskPlan.proposal_ref`，再让 E1、E2、恢复逻辑和验收逻辑读取同一份最新要求。

本轮接续是额外的一次即时执行，不修改原 TaskPlan 的基线提案、周期时间表或未来周期执行的要求。Task 查询分别展示计划基线和最近执行要求，不能将两者混为一谈。要修改计划本身，使用后续明确设计的计划调整语义。

统一梳理运行时所有要求读取入口：首次执行与恢复、任务提示包、材料继承、前提/截止时间检查、执行器和程序参数、安全规则及 `submit_result` 验收。它们必须使用同一执行快照，不能提示词使用新要求、结果检查仍使用旧计划要求。`plan_revision` 可保留，但仅有版本号而没有可解析原件不构成快照。

同步修改 `task-prompt.ts`：恢复同一 Execution 时继续原快照；在同 task 新建 Execution 时遵循新正式快照，历史目标、结果和材料只提供背景。保留“不得重复未知副作用”和“不能自行授权”等约束。更新 schema 中原有“同目标/约束”的说明，使修改后接续与恢复旧执行不再混用。

### 3.5 工作目录、产物与后续关联

- E2/E3 沿用 T1 的 `work` 目录；执行专属日志、检查点和结果仍按各自 execution ID 区分，不要求保活原 agent 进程。
- 沿用现有 parent 材料、检查点原文和结果装配能力，但读取指定 parent 的快照，而非原 TaskPlan 当前指针。提供必要操作回执/结果证据，不能仅依据 agent 总结推断操作已经完成。
- 原始 Task Log、结果和产物对象保留。E2 可以修改工作文件，但 E1 产物必须通过原 ObjectRef（不可变对象引用）仍能读取旧内容，不能只有指向现用文件的路径。
- 更新 `pending_followup_ids` 的受理、创建执行和结束释放逻辑，避免同 task 接续误形成自身永久依赖。请求已受理、尚未分派期间也应保护所需 parent 资料；新执行结束或待执行请求被明确撤销/拒绝后正确释放。
- 接续不继承旧的单次授权消费，不重放旧工具调用；新的操作按实际 execution、动作、资源和参数通过现有授权检查。仍有效的持续授权按原规则匹配，不要求无意义的重复人工授权。

### 3.6 `tick()`：稳定执行发生键与可靠待执行项

新即时执行请求使用宿主提供的 `request_id` 作为 `occurrence_key`，唯一性按 `(task_id, occurrence_key)` 判断：

```text
T1 / R1 → key=R1 → E1
T1 / R2 → key=R2 → E2
T1 / R3 → key=R3 → E3
重投 R2、重复 tick、重启恢复 → 仍对应原 R2，不产生 E4
```

不使用每次 `tick()` 新生成的 UUID、当前时间或“当前执行数 + 1”作为请求身份。也不能每次把 `once` 换一个随机字符串后重新设置到期时间。

仅改执行键不够。受理接续时必须持久登记待执行项，至少绑定 `request_id`、`occurrence_key`、本次到期时间和 `proposal_ref`；parent 从对应提案取得。当前 `pending_occurrences: string[]` 是周期时间点队列，不能直接混入请求 UUID 后继续按时间解析。

建议采用最小扩展：保留原周期队列，为已受理即时请求增加专用待执行字段；或以有明确类型的待执行条目表达同等信息。实施时在本节补记最终字段及迁移规则，只有一种权威表示，不建设通用消息队列。无论采用哪种表示，都必须满足：

1. 提案对象可靠保存后，在同一 Store journal 提交中保存请求回执、待执行登记、计划必要更新和 parent 保护关联。先 ACK 后登记、仅放内存均不合格。
2. `tick()` 消费一项请求时，在同一提交中创建 Execution、固定快照、移除待执行项并更新计划/parent 关联；提交成功后才启动执行。
3. 发现同一执行键已存在时复用原关联，并能清理已消费的重复待执行表示，不得永久卡在队首，也不得再次创建执行。
4. 一条请求只创建一个逻辑 Execution；暂停、恢复或重启不另换发生键。已分派后结果不明仍走原恢复守卫，不能用新执行绕过。
5. 多条请求的内容不得通过共享最新提案指针串台。使用既有 Store 提交/版本检查保证同一 task 不出现两个并发工作实例。

复用只增加一次即时执行。`at`、`interval_seconds` 在复用调用中非空时明确拒绝，不能悄悄改写原计划；周期 anchor、`next_due_at`、错过触发策略及正常发生键保持原语义。与已到期/排队的周期执行发生冲突时可以返回忙碌并等待该轮结束，本阶段不实现抢占。保留 PROGRAM、AT、INTERVAL 原有运行路径。

请求指纹覆盖原始业务参数、复用 task、parent、本轮要求及宿主 session，不包含后来生成的时间、对象地址或可变计划状态。同 ID 同内容返回原受理；同 ID 不同内容报冲突。保留 Host 现有稳定工具调用键和结果重放链路；不同调用使用不同请求 ID 时不宣称已解决自然语言语义重复，这是后续阶段的问题。

### 3.7 契约、旧数据与文档同步

涉及持久字段时，先修改唯一契约来源 `src/contracts/contracts.schema.json`，再生成 `src/pi_secretary/src/contracts.ts` 和 `docs/data/`，不能只手改生成文件。必要时同步 schema 示例和实际使用的兼容代码。

兼容要求：

- 已存在的 `occurrence_key="once"`、旧 TaskPlan、Execution、receipt 和 journal 必须仍可读取；不能新增必填字段后使原 Store 无法启动。
- 旧执行缺少快照引用时，在可验证的兼容读取或迁移中固定其原始提案关联；不能永久退回“每次读取当前最新计划”。无法确认来源时明确阻塞，不猜测。
- 旧任务已有 `once` 执行且无待执行请求时，升级和 `tick()` 都不再运行一次；之后受理 R2 可以在同一 task 下创建 E2。旧任务尚未首次执行时也只能运行一次。
- 旧回执重投仍指向原受理，不能因新返回结构或发生键规则改变被当成新请求。
- 先在复制的测试数据上验证迁移和重启；不清空 journal、历史任务或 workspaces，不以重新初始化规避兼容问题。

同步当前接口、数据模型、数据流、架构、测试说明和必要运行/恢复说明。历史归档保留其历史性质，不将其批量重写成当前设计。`docs:check` 通过只表示检查器覆盖范围通过，不等同于语义一致；实施者必须核对正文与最终代码。

## 5. 验收标准

### 5.1 确定性测试与状态断言

建议新增 `test_case/offline/runtime/task-reuse.test.ts` 或等价定向用例；可拆文件，但须纳入实际测试入口。以下是状态与接口测试，不用于冒充真实模型的接续判断验收。

| 编号 | 场景 | 必须验证的结果 |
| --- | --- | --- |
| A01 | 工具契约与参数传递 | 模型工具定义包含 `reuse_task_id`；省略/null 与非空分别走正确路径，最终持久提案不是固定 null |
| A02 | 任务发现与详情 | 从无参数列表得到真实 T1，再按 T1 查到目标、最近执行及要求/结果；不只返回对象指针；不可访问或不存在时明确失败 |
| A03 | 基本接续 | T1/E1 结束后受理 R2：TaskPlan 总数不增，生成 T1/E2，parent 正确，workspace 不变；再受理 R3 得到 T1/E3 |
| A04 | 补充要求与验收快照 | E2 使用修改后要求，`submit_result` 按 E2 验收项检查；E1 原目标、验收项及结果不变；重启后读取一致 |
| A05 | 继承和空值 | 省略/null 继承 parent；显式 constraints 数组按约定替换；空 acceptance 拒绝；PROGRAM 不因省略 program_id 变成 AGENT |
| A06 | 材料和产物 | E2 能读取/修改 E1 真实文件；旧 artifact 对象仍能读取 E1 版本；历史材料不能覆盖新正式要求 |
| A07 | 非法复用 | 缺 parent、parent 属于另一 task、未结束/已回收、计划不可用、workspace 或必要引用缺失等明确报错；不产生替代 task 或待执行项 |
| A08 | 活跃与结果不明 | RUNNING、WAIT_DECISION、WAIT_AUTH、RESULT_UNKNOWN 或已有待执行接续时不新受理第二份工作；普通决定继续原执行，未知副作用不自动重试 |
| A09 | 请求幂等 | 受理后、执行中、完成后重复原 R2 均不新增执行；同 ID 不同目标、reuse、parent 或约束报冲突，原请求不被覆盖 |
| A10 | 扫描与并发 | 连续 tick 不生成额外执行；两条不同新请求竞争同 task 时不同时受理成可并行工作；同键重复待执行项不造成队首卡死 |
| A11 | 崩溃恢复 | 受理提交前中断可安全重投；受理成功未 tick、执行创建成功未分派、工具返回前中断都不丢逻辑请求或重复创建；分派后未知结果仍阻塞 |
| A12 | 周期/定时回归 | 周期任务结束一轮后可增加一次即时接续，但 anchor、未来到期点和周期默认要求不变；复用传 at/interval 被拒绝；原 AT/INTERVAL/PROGRAM 测试通过 |
| A13 | 留存与后续关联 | parent 在接续待执行/执行中不会提前回收；结束后无自身依赖残留；列表不刷新所有执行；详情刷新与 RETIRED 行为符合原规则 |
| A14 | 旧数据 | 含 once、旧字段和旧 receipt 的数据可启动；不重复首轮；升级后接受 R2 得到同 task 新执行；历史引用保持有效 |
| A15 | 新建与权限回归 | 无 reuse 仍可新建独立任务；parent-only 仍新建；未把旧单次批准当作 E2 批准；持续规则、未知结果停止和主会话工具权限保持有效 |

崩溃测试需区分提交前后和分派前后，使用可控制故障点与持久状态断言，不能仅关闭再启动一次就勾为全场景通过。一个工具调用恰好返回成功也不等于外部副作用具有全局 exactly-once（恰好一次）保证。

### 5.2 真实模型 online 行为验收

新增 `test_case/online/test-task-reuse-live.ts` 或同等产品路径用例，并在 `test_case/online/README.md` 和 `docs/testing.md` 登记运行方法。必须使用真实模型及正常 Host → tool → Scheduler 路径，不能在测试中直接替主会话选择 reuse、伪造工具调用或写入期望结果。

| 编号 | 自然输入与操作 | 观测及断言 |
| --- | --- | --- |
| O01 | 提供足够材料，要求分析一个方案 | 主会话作出有内容的分析；没有因为“需要推理”而创建 task/execution |

保存主会话实际调用参数/返回、task 与 execution 对照、各轮快照引用、结果和文件证据。模型回答“已接续”不能替代代码断言；一轮通过只说明该配置下本组用例通过，不宣称已解决所有自然语言任务归属问题。缺少 API 配置或额度时明确记为未验收，不用 offline fixture 代替。
