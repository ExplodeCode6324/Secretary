## 5. Submission, races, errors and restoration

Create a narrow matter submission controller sharing CoreClient/reconciliation helpers where appropriate, **not** Main Delivery's ACCEPTED-is-delivered behavior. One explicit action freezes an **in-memory**, single-flight envelope `{domain,route,item_id,request_id,payload,display_revision/hash}`. Same submission retries in this TUI process retain the exact ID and bytes, including reconnect to the same data domain. At most one unresolved matter submission: another matter may be read but cannot submit until it settles. No LocalState version change, persisted matter envelope, recovery menu or stored unsent answer. Existing Main delivery persistence is untouched.

On TUI process restart, read fresh authoritative matter state; do not replay a lost submission or claim its outcome as ours. Core's revision/hash and OPEN/WAIT_DECISION guards prevent duplicate approvals/answers. If a still-actionable item is reopened after fresh state inspection, a new explicit Master action is a new attempt, not automatic replay of the lost one. If an old network request races it, Core accepts at most one. Record crash recovery's limit honestly: object-state reconciliation is available, but the previous process's request identity/local answer is not recovered.

POST receipt acceptance does not clear a pending row or return success. Requery authoritative detail and requests/{id}; success requires the matching decision_id and APPROVED/CONSUMED (or REJECTED) for authorization, or matching answer_request_id and ANSWERED with MASTER actor/answer for question. Subsequent domain progress does not require waiting for the whole Task; record proven outcome before later expiry/revocation obscures it. If consumed before observation, matching decision identity still proves approval. Nonmatching other-client completion is an external completion notice, never our success. Query/refresh excludes APPROVED permanently; do not rely solely on a local tombstone.

Disconnect/timeout/5xx while outcome is uncertain preserves temporary input and envelope, reconciles read-only, offers explicit same-ID retry, and never automatically retries under a new identity. Prevent editing an ambiguous submitted payload into a different action under that ID; allow Esc back while retaining the unresolved business envelope, with a visible pending status. A later result for the old target must not overwrite another editor or navigate a new view. On in-process reconnect first reconcile the envelope and require explicit intent before same-ID resend. On process restart use the fresh-state rule above, with no automatic retry. Definite pre-admission validation errors retain input; corrected payload is a new explicit attempt only after proof no earlier business mutation was admitted. REQUEST_CONFLICT never silently rotates identity.

Expired/not-open/stale/not-found/invalid-transition or externally handled targets exit automatically: Main restores its current Delivery-owned draft; Task returns to list and refreshes. APPROVAL_CONFLICT invalidates the displayed authorization and exits with a visible notice; reopen fetches new content. Transient detail-read failure does not prove invalidity. Error survives the view transition in a parent-owned local notice, clears on the next deliberate user action per existing rules, and stays separate from persistent task exceptions. An invalidation during submission reconciles the frozen request before classifying external completion; fresh state must never redirect input to another item.

On refresh while processing, retain the displayed version, confirm continued applicability, disarm changed authorization content and ignore stale async loads. Check expiry via valid_until; UI checks do not replace Core checks. Esc cannot revoke a submitted business operation: show its pending/completed status truthfully. Unsent temporary answers may be discarded on exit/invalidity, never copied to Main/Task or another item.
