## 1. 目标与边界

短暂的供应商故障由传输层有界重试；记忆整理和承诺提取失败由维护周期重试。成功摘要、Settings 生效和待补提来源分别保存，避免提取失败使主会话永久积压。删除预检、绑定、票据和显式提取恢复流程，历史 journal 继续可读。

模型响应完整保存后，工具才可开始执行。已保存的成功响应复用；FAILED / INTERRUPTED 下的诊断响应不等同于成功。工具、授权、World 写入与通知回执沿用现有规则，未知外部副作用不自动重放。

本批覆盖 MAIN、TASK、COMPACTION 和承诺提取的传输重试，以及主会话、维护、Settings 与公共合同的必要衔接。TASK 进程中断后的 Execution 恢复和未知结果裁定仍属 #18；#19 不改变 `Scheduler.recover()` 对运行中 Execution 的裁定策略。#21 / #28 的检索与旧输入退出、#24 的 Context 编码、#10 的客户端界面留在各自批次。

## 3. 设计决策

### 3.1 传输尝试与成功响应恢复

1. 一次逻辑模型请求最多发送 3 次，间隔为首次立即、再次发送前约 2 秒、第三次发送前约 10 秒。有效 Retry-After 支持秒数和 HTTP 日期，取与本次基础间隔的较大值。等待可取消，维护定时不占住 Host 执行槽。
2. 可重试：网络连接错误、单次请求超时、HTTP 408 / 409 / 429 / 5xx，以及供应商明确的过载错误。不重试：401 / 403、请求格式错误、容量校验失败、显式用户取消 / 进程关闭。未知程序错误不当作网络错误循环重试。
3. 错误分类集中在传输边界。实施时静态核对固定版本适配器对 status、headers、errorMessage 的保留情况；优先结构化字段，供应商字符串只做可验证的窄匹配。若 SDK 丢失 Retry-After，补充最小错误元数据桥接并以本地 HTTP fixture 验证，避免只在 mock Error 上通过。
4. 优先为每次物理发送建立新的 ModelCall，以可选关联字段连接同一逻辑请求，`transport_attempt` 为 1 / 2 / 3。Context、失败诊断、错误类别、时间逐次留存；首次准备、每次发送前和终态均写 journal。旧记录缺关联字段时视为单次历史调用。
5. 同一次请求的重试保持请求内容、作用域和逻辑身份一致。预算检查在发送前执行。观察 UI 可以收到失败预览；失败尝试的流和 toolCall 不能交给 Agent 执行。
6. 使用 ModelCall 成功状态及已持久响应共同判断复用，不能以 `response != null` 判断成功。恢复关联必须包含 scope、loop、调用位置和持久请求身份，不能全局按相同文本缓存响应。重启读取已消耗的尝试次数，不能每次重启重新获得三次发送机会。
7. MAIN 与维护调用补齐“响应已保存、消费者检查点未保存”的恢复：先采用持久成功响应，继续原调用的消费；已有工具结果按回执恢复。TASK 在一次运行内共享传输重试，跨进程 Execution 恢复遵守 #18 的边界。

### 3.2 主会话阻塞与新输入

继续使用现有 `RECOVERY_BLOCKED` 状态表达 Issue 所称 BLOCKED，增加可选、结构化的阻塞原因和关联 ModelCall，避免新增一套 Session 状态。该原因用于防止新输入误解除容量、未知工具结果或历史恢复错误。

- 三次可重试传输失败后，保存阻塞原因并创建一条现有 Notification，delivery_key 绑定本次逻辑失败，pump / 重启不重复创建。
- 不可重试模型错误立即终止当前尝试，并可记录为模型传输阻塞；新输入仍只开启一次正常恢复机会，401 等不会获得三次内部重试。
- `accept` 仅在新 Master Input 成功持久接收时解除上述模型阻塞；同 request_id 重放、反馈输入、后台 tick 不触发。原 CLAIMED 批次先恢复，新输入随后按现有输入顺序消费。
- `session/resume` 保留。CAPACITY_BLOCKED、未知工具结果、检查点不一致和没有明确分类的历史 RECOVERY_BLOCKED 均不由新输入自动解除。

### 3.3 维护退避与次数口径

Issue 同时写了“5 分钟、30 分钟、2 小时”三个失败后间隔和“最多 3 轮”。**本计划采用：首次正常维护后，最多 3 轮自动补试，分别等待约 5 分钟、30 分钟、2 小时；第三轮补试仍失败则停止。** 因此一个失败周期最多 4 次维护执行，每次逻辑模型请求最多 3 次传输；Master 已确认这一计数解释。

- 摘要与提取共用小型退避计算，不建设通用任务队列框架；保留各自来源和结果职责。
- 退避轮次、到期时间、最近错误和完成状态持久化在 journal 记录中。App 现有 pump 在空闲安全边界检查到期工作，重启继续原计数；无新增对话时也能到期补试。
- 摘要失败重试同一冻结来源范围；新输入不能绕过该失败周期获得无限次数。复用完成的摘要分段，只为失败段生成新候选。最终提交继续校验基准版本，STALE 结果不覆盖新记忆。
- 协议不合法的完整输出由下一轮维护重新生成；删除或收敛 `summary.ts` 旧两次即时修复循环，更新相关 prompt / output budget 选择，保持容量限制与逐字来源校验。
- 认证、无效请求、容量或来源证据错误保留原因且不自动反复发送；错误修正后可手动重排。暂时传输失败和协议不符才进入自动退避。
- 自动周期耗尽时摘要产生一次通知，提取在 MemoryStatus 中显示 FAILED 和原因。手动 `session/compact` 重置摘要周期；内部自动调度不能借用这个“重置”行为。提取用独立 retry 命令重置。

### 3.4 待补提来源、摘要与 Settings 解耦

新增一个小型持久 `MemoryExtractionJob` 记录表示冻结的来源批次，避免复用 ExtractionRecovery 的票据模型。字段限于 session、来源事件 ID 与不可变 CAS 引用、来源键 / policy、状态、维护轮次、next_attempt_at、最近错误、关联 ModelCall / 结果引用；唯一来源键防止 Settings 和普通维护重复排队同一事件。状态至少表达待执行、执行中、成功和失败，重启按成功响应及 journal 结果恢复执行中任务。

1. 在开始提取之前保存来源批次；成功摘要推进 `covered_event_sequence` 时，未成功来源必须已有可恢复的持久记录。Settings 提交不能清空该队列；后续对话、新的 compact、重启都不能通过覆盖水位把来源漏掉。
2. 原文来自 journal 事件和不可变引用，不依赖当前 Context 是否仍包含该段。Settings 的来源完整性、身份映射和证据校验继续保留；来源缺失或有歧义时保留失败，不推断成已提取。历史失败日志能可靠还原来源时转为待补提记录；不能还原的条目保留可见原因。
3. 普通维护：摘要成功时提交摘要及其覆盖进度；提取失败独立保存。Settings：摘要和设置校验完成后沿用原 World 回执与 journal 提交流程，提取失败不阻止 APPLIED；设置本身的失败仍按原规则处理。
4. 补提前从当前账本读取 existing；成功后从最新 revision 合并。按真实来源身份及经验证的承诺内容去重，不按文字把两个不同事件合并；已有 COMPLETED / CANCELLED 状态保持。补提只新增可验证承诺，不恢复旧 Consciousness 快照，不把历史 resolutions 重放到新账本。
5. 承诺合并与该来源任务的成功终态同一 journal 事务提交。若模型结果已经保存而合并未完成，重启复用结果并重做本地合并，不重发模型；并发的承诺解决操作通过最新 revision 重读保留。
6. `POST /api/v1/memory/extraction/retry {request_id}` 重新排队当前主会话中失败的来源；由于请求没有目标 ID，定义为对接收时的失败集合做一次快照。使用既有命令 receipt 固化集合和结果，同 request_id 重放不再重置轮次，空集合是幂等空操作。运行中、已成功或已排队条目不重复入队。
7. `GET /api/v1/memory` 增加提取待处理数、失败数、轮次 / 下次到期时间与失败原因的 DTO。重排仍使用现有本地 owner 鉴权与请求幂等，不需要预检、绑定、5 分钟票据或额外业务授权。

## 6. 实施与隔离验收记录

### 实现结果

- MAIN / TASK / COMPACTION 和承诺提取使用同一有界传输层。一次逻辑请求最多 3 次物理发送，底层 SDK 的 maxRetries 保持 0；2 秒 / 10 秒退避服从更长的 Retry-After。成功响应先持久保存再交给 Agent，失败响应仅作诊断。
- 主会话的模型传输阻塞、失败通知和请求 generation 持久化；真正新增的 Master 输入可恢复，重复请求、反馈和后台 pump 不能重置，容量或未知错误也不会被误解除。
