## 2. Proposed minimal durable business contract (new, not existing)

Use one small **FailureHandling** business record per failure plus attempt events (no separate attempt-record family) in the existing Store journal, schemas, replay, admission and sync mechanisms. This is not a UI read/audit log or a scheduler. Implement as a focused service shared by Main tools, master-attention and task-browser; register schema/types/indexes/migration defaults and recovery tests together.

A failure identity is server-derived within the owned data domain/session: `EXECUTION:<execution_id>` for a FAILED execution (terminal, so it fails at most once), or `TASK_INIT:<task_id>:<episode_sequence>` for initialization failure. Result ID and initiating sequence are immutable checked evidence attributes, not alternative execution-failure identities. Missing/corrupt result or cause never prevents dismissal of an otherwise owned FAILED execution; REDO still requires valid original proposal/evidence and existing guards. Move INIT_FAILED transition tracking from master-attention's private map into the shared rebuildable journal projection used by admission and all views. Current source produces only one INIT_FAILED episode per plan; repeated failed initialization ticks stay in that episode. Do not add a new lifecycle merely to produce multiple episodes. Shared derivation supplies the attention row's key and submitted failure_key exactly; execution failure keys do not change when provenance is unavailable. Keep original initiation ordering separately. Historical initialization provenance is reconstructed from actual validated frames; no invented sequence or new write on read.

Records are created only on explicit submitted business intent, not on query/view. Existing failures without records default to UNRESOLVED. Store exact original identity, revision, intent/input/request IDs, operation timestamps, attempt status, error code/reason and linked follow-up request/execution/result IDs. Effective disposition is UNRESOLVED, DISMISSED or REDO_SUCCEEDED. Attempts distinguish REQUESTED, Main-processing, linked QUEUED/RUNNING, BLOCKED/FAILED and SUCCEEDED; transport delivery is a separate dimension. Maintain indexed per-failure lookup and per-task unresolved counts, rebuilt from journal; avoid full historical reads on every refresh.

Proposed public read contract: `GET /api/v1/failures/{failure_key}` exposes exact identity, authoritative disposition, active/last attempt, reason, linked work and current continuation eligibility. Attention and task-browser add the fields needed to show unresolved/pending/error state, keeping historical execution state distinct. Main task_query exposes the same truth (optional failure key, mutually exclusive with other selectors). Exact route/schema names are finalized in implementation documentation before use; this section does not claim they exist today.

### Main admission and authority

Extend existing `POST /api/v1/messages` with an optional structured `failure_action` containing server-issued failure key, expected handling revision, and REDO or DISMISS. The request ID is the stable intent identity. Core validates ownership/identity, rejects UNKNOWN or mismatched tuples and conflicting identity reuse, and atomically records the intent and one ordinary MASTER Input through the existing admission transaction. Canonical human-readable text contains only the selected action and canonical IDs; it is constructed/validated by Core, never interpolates Agent-produced failure prose, and cannot carry an additional unrelated instruction. No original draft text is sent. Ordinary messages without this field keep their contract. Include structured data in dedupe fingerprints, Input persistence, message/history projection and recovery context.

A structured failure Input is handled alone in a Main batch, preserving ordering and recovery of previously claimed batches; ordinary inputs/feedback remain queued and are processed normally afterward. Main tools receive the authoritative active input/intent context, not authority inferred from model-supplied IDs or free text. Narrow the mutating task tools for this context: REDO may only query and propose the exact existing Task with the exact failed parent and linked intent; DISMISS may only query and dismiss that failure. Reject new-task fallback, wrong-parent/task, cancel/answer/plan-management or any unrelated mutation. Ordinary Main tools outside this context retain their normal behavior. Read/explain/report remains available. This prevents model interpretation from silently expanding a failed redo into new work.

Derive authority from the claimed Input; an optional model-supplied failure intent binding to task_propose is equality-checked only. Add that binding to task_propose, and a new Main `task_control` action `dismiss_failure` with the failure/intent identity (a proposed addition, not task_control.retry). The core revalidates against the active MASTER Input and session, including loop recovery. Arbitrary assistant text, feedback/timers, a foreign input, and stale intent IDs cannot authorize handling. A plain explicit new-work message later uses the ordinary Main flow and is not inferred from failure processing.

### Atomic linkage, replay and completion

For REDO, call the existing continuation path with all its guards. Core pins the complete effective parent proposal: goal, constraints, acceptance criteria, preconditions, deadline, executor/program parameters and original source materials. In the REDO-context tool schema only, goal becomes optional; Core fills every omitted requirement from the parent. The tool description tells Main to send only reuse_task_id, parent_execution_id and optional equality-checked intent binding. Ordinary task_propose keeps goal required, and Core validates it normally outside REDO. Omitted fields inherit canonical values; any differing explicit value (including empty replacement arrays, a narrower goal or new material) is rejected as BLOCKED. Normal parent-evidence enrichment and immediate continuation trigger metadata are allowed, but cannot change business requirements. Store a canonical requirements digest and verify the linked proposal matches it again before REDO_SUCCEEDED. Changed requirements require a separate ordinary, unlinked Master request; this issue does not add a correction-text UI. Persist the intent's linked request identity in the **same commit** as task.request.accepted and pending work. One intent can admit at most one follow-up, including repeated model tool calls with different call IDs, network resend and crash recovery. Replayed calls return existing linkage. Admission failure records BLOCKED and its actual reason without creating work. Recover the boundary between scheduler acceptance and Main tool-result using the existing tool reconciliation pattern; never enqueue a second retry to fill a missing tool-result record.

Link through exact request ID/occurrence plus task/parent/proposal identity to its dispatched execution. REDO_SUCCEEDED requires that linked execution and its matching TaskResult both establish SUCCEEDED, with matching original parent, and original failure still unresolved. Neither unrelated periodic success, arbitrary continuation_of success, model text, HTTP receipt, Main completion, queued/running work nor CANCELLED/EXPIRED/UNKNOWN settles it. If linked redo fails, both original unresolved failure (with attempt error/link) and the new failed execution are represented, each independently disposable. A fresh redo attempt still obeys latest-parent rules; never silently jump to a different newer parent. Missing/corrupt links remain unresolved with an explicit reason.

For DISMISS, Main's new action atomically marks only this failure DISMISSED, with business input/request identity. It does not rewrite FAILED or INIT_FAILED, touch retention, close/pause a plan, revoke authorizations, or cancel queued/running work. It remains available for RETIRED failures and failures whose continuation is blocked. If a redo is already admitted, dismissal only ends the original reminder; existing work and any later failure remain independent. Serialize admission/dismissal: a stale not-yet-admitted redo cannot enqueue after dismissal; an already admitted redo may finish but cannot overwrite DISMISSED. A second concurrent redo follows the admission table below. Exact request-ID replay is idempotent; a new intent on an already resolved failure is rejected, never reopens it. Explicit later new work is separate authority.

Use effective state derivation from persisted linkage and execution/results for crash-safe completion; do not require a best-effort UI callback to persist success. Reads may rebuild projections but never mutate business/retention state. Derive NO_ACTION from the matching Input becoming HANDLED without durable disposition/link or recorded failure outcome; no new write in finish() is needed for this case. Actual Core tool validation/admission failures are persisted as BLOCKED with their reason and a stable tool receipt; persisted model-call/session errors are projected as processing errors/recovery-blocked, never success. If Main is still pending or recovery-blocked, say so; do not invent a failure timeout. Admission and known errors are durably queryable, rather than transient TUI-only notices.

INIT_FAILED has no executable parent: REDO is visibly unavailable and Core rejects direct REDO admission for this kind; show the actual initialization error and allow dismissal of that episode. Its action is labelled “Dismiss this reminder; background initialization retries continue”, since the existing scheduler retries initialization on every tick. No new initialization scheduler or automatic replacement Task. A dismissal hides only the reminder, not the actual TaskPlan INIT_FAILED condition or any real background initialization progress; a later distinct failure is visible. No retention extension or RETIRED reactivation. Task eligibility continues to include genuine running/queued/waiting work even with a paused plan; an otherwise empty paused plan with all failures handled is absent. Archived Scope browse exclusion stays unchanged, while Main can still handle owned historical failure identities.

## 7. R2 explicit rules and approval consequences

### Admission table and revisions (B5)

Record-less failures have handling revision 0. Only writes to FailureHandling increment its revision; linked Execution/TaskResult progress and read-derived status never do. Admission compares expected handling revision, and the serialized business mutation revalidates the frozen intent identity/current applicability rather than reusing a stale UI revision. No automatic stale-revision retry under a new identity.

| Current effective state | New REDO | New DISMISS |
| --- | --- | --- |
| Any state, same request ID + identical fingerprint | Return original admission/outcome; no new Input/work | Same |
| Same request ID, different payload | 409 REQUEST_CONFLICT | Same |
| Unprocessed REQUESTED/Main-processing intent | 409 FAILURE_INTENT_PENDING | 409 FAILURE_INTENT_PENDING |
| Processed REDO with linked queued/running/uncertain work | 409 FAILURE_REDO_PENDING | Accept with current revision; only dismiss original reminder |
| UNRESOLVED with no active intent, or prior BLOCKED/NO_ACTION/failed attempt | Accept if execution-kind target, then Main validates exact unchanged continuation; otherwise explicit blocker | Accept |
| DISMISSED or derived REDO_SUCCEEDED | 409 FAILURE_ALREADY_RESOLVED | 409 FAILURE_ALREADY_RESOLVED |
| INIT_FAILED | Reject REDO at admission; disabled UI with actual reason | Accept owned episode |

A no-action/failed Main attempt is processed only when its durable input/receipt state proves settlement. A still CLAIMED/recovery-blocked input stays pending. After E1's linked E2 fails, E1 displays the current PARENT_NOT_LATEST prediction but REDO remains explicitly submittable so Main reports its authoritative blocker; dismiss remains available, while E2 has its own failure entry. The same rule applies to RETIRED, busy, paused and other execution-continuation blockers: only INIT_FAILED and the admission table's 409 states disable submission. Predictions do not replace Main processing or silently change the target. With a pinned past deadline, current continuation may be admitted and then become EXPIRED under existing scheduling; show that prediction and actual outcome, never success. Changing the deadline requires a separate new-work request. A legal target may become blocked between read and Main execution; persist and show the actual blocker without changing target. If the linked redo succeeds between DISMISS admission and Main execution, return already-resolved instead of overwriting REDO_SUCCEEDED. The reverse order preserves DISMISSED. After replay, the first durable terminal fact by journal sequence wins: use the dismissal commit sequence versus the earliest frame where the matching linked Execution and TaskResult both prove success. These are explicit outcomes requiring tests, never silent intent loss.

### No autonomous recovery from terminal failure feedback (B3, proposed policy for approval)

Choose the minimal host-enforced extension of the existing UNKNOWN-feedback guard. Isolate each FAILED/CANCELLED RESULT feedback Input as its own Main batch, extending the same ordered boundary mechanism used for attachments and structured failure inputs. It cannot mix with unrelated SUCCEEDED feedback or a MASTER message; preserve existing CLAIMED-batch recovery and apply this boundary on new admission-to-claim selection. EXPIRED feedback is explicitly outside this new guard and retains existing behavior; UNKNOWN retains its existing separate guard (no general UNKNOWN redesign in #93). A Main batch with RESULT feedback for FAILED or CANCELLED work, regardless of cancellation origin, and no MASTER input may not call task_propose at all (neither reuse nor new-task fallback). Report the real result and wait for Master's explicit failure action or separate new-work message. Scope the same check to recovery of that batch, including direct Core service recovery paths; timers/feedback/old intents do not replenish a failure action's authority. Ordinary explicit Master requests and independently due periodic scheduling retain their normal semantics. Prompt rules also prohibit autonomous failure/cancellation recovery outside that authority. Capture attempted rejected calls as well as accepted calls; live L1–L3 fail if Main initiates unrequested recovery. This behavioral tightening is part of the plan Master is asked to approve, not a claim that baseline already enforced it.

### Recovery contract and smallest storage design (B6)

One FailureHandling record plus immutable attempt/business events suffices. Both REDO linkage and DISMISS commit a stable tool receipt keyed by stableID(toolKey), plus the action-level idempotency identity. Extend recoverTools to reconstruct both from proven durable receipts. Enforce identity/ownership, current input/intent and pinned requirements **inside the Core service**, covering direct proposeTask recovery paths as well as the wrapper. An already completed effect can return its receipt even when the failure is now resolved; a new side effect cannot bypass the guard. Catch continuation validation failures in the service, commit BLOCKED/reason/receipt idempotently, and expose a structured failed tool result that recovery can reconstruct; do not lose it through an unrecorded throw. Receipt recovery does not rerun arbitrary effects. Derive NO_ACTION from HANDLED Input as specified above. Add crashes after disposition/link/error commit and before main.tool.result, wrong-input recovery, same intent under distinct model call IDs, and valid FAILED + unresolved operation dismissal (UNKNOWN remains, REDO blocked).
