## 3. 同步游标与初始加载

### 3.1 持久游标

`GET /api/v1/sync/cursor` 返回当前 cursor S、对应 sequence 和 instance_id。公开 sequence 使用十进制字符串，供客户端判断通知是否早于初次加载边界；续传仍只提交不透明 cursor，不要求客户端解码。新增公开位置字段限该响应的 sequence 与通知的 created_sequence，不扩散到其他业务 DTO。cursor 仅编码数据域 owner_id、事务 sequence、该事务 digest。同步游标独立于现有实例内分页 Cursors，不引入密钥或签名。

校验编码/字段、合法安全整数范围、owner_id、sequence 不超过末端、对应 digest。正常 Core 重启不影响游标；另一数据域、旧水位超过恢复末端或对应 digest 已分叉，统一返回 HTTP 409 `RESYNC_REQUIRED`。仍属于同一历史前缀的有效游标可继续。校验依赖重放确认的帧 digest，不重新散列整个 journal；sequence=0 对应既有零 digest。限制输入长度防止不受限解码；错误码只用于确实无法继续原历史的情形。

Store 的权威写入和 digest 计算不变。新增索引可由 journal 重建；读游标不写初始化记录，API 所需身份仍在启动阶段建立。#24 后续改造须保留 sequence/digest 含义。

### 3.2 取游标后加载与追赶

1. 客户端先取得 S，然后用现有资源查询和新通知查询加载所需列表/详情。
2. 从 S 追赶 changes，再用同一位置进入 SSE；初始加载读到 S 之后的数据允许保留。
3. 单记录资源只接受较新 revision；聚合失效项必须触发重新查询，即使根 revision 未变化。
4. 客户端区分收到的游标与已应用游标。事务对应刷新结果写入本地后，才原子推进已应用游标；失败保持待刷新，不越过失败事务。SSE 的 Last-Event-ID 也只使用已应用游标。
5. `RESYNC_REQUIRED` 后放弃旧同步水位并重新加载；待发送修改仍按稳定 request_id 查询回执，不自动制造新请求。

Core 不保存客户端游标，不提供一致快照。上述落盘与恢复规则形成 #10 接入合同，本批测试客户端覆盖逻辑与崩溃窗口，实际 SwiftUI 集成由 #10 验收。

### 3.3 稳定列表分页

分页算法只在 `Cursors.page(scope, values, query, keyOf)` 一处实现：从现有已物化的 values 按 keyOf 的稳定元组排序，取严格大于 last_key 的前 limit 项，cursor 保存查询范围/参数和 last_key。不建立每类列表自己的排序、偏移或版本失效机制；排序不修改调用者的数组。

`Store.install` 统一维护可重建的首次提交位置 Map，按 `object_type + object_id` 区分记录身份，首次出现后不随 revision/updated_at 改变，重放恢复相同值。`ApplicationService.page` 的薄封装统一提供默认 keyOf：顶层记录使用 `[first_sequence, id]`，包括 tasks/executions 的字符串 id 列表。少数例外只传 keyOf：工作记忆用 item_id，内嵌请求用 request_id，产物/关系用稳定类型与身份的组合。例外不另建持久索引或独立分页器。

分页不再携带用于拒绝续页的全局 Store.sequence 或可变根 revision；响应已有 version 可保留为观察信息，不能被描述为整组快照版本。现有实例内分页编码可继续使用，重启时列表可重新加载；持久同步位置由独立 sync cursor 保证。

scopes、tasks、task requests、executions、decisions、authorizations、operations、authorization-rules、programs、artifacts、related、memory summary/commitments、attention 和 notifications 共用这一机制，列表枚举仅用于覆盖检查。已有约 15 个 page 调用点只删除版本参数或传入稳定 keyOf，目标为每处不超过 2 行语义改动（不计格式调整）；若实际超出，在 PR 单列原因并检查是否重复实现分页。薄封装和 Cursors.page 本体不受这一调用点行数目标约束。已使用事件/固定内容位置的 timeline 与消息分片保留其专用算法；World 保留其既有分页语义，不在本批扩成跨域快照。

S 前已有且之后未变的记录必须遍历到。集合自身新增/删除/修改允许通过 S 后失效与追赶收敛；新项落在已翻过的键区间也由变化流补齐，不宣称分页期间冻结集合。attention 的到期继续用 valid_until 提醒客户端刷新，不为时间流逝制造业务事务。

## 4. 变更流与聚合失效

`GET /api/v1/sync/changes?after=<cursor>&limit=<n>` 返回按事务分组的 changes、每组之后的 cursor、next_cursor、has_more。limit 是检查的事务数，默认及上限 100；没有公开变化的事务也计数并推进位置，防止一次读取无限扫描内部历史。

单记录变化含 resource_type、resource_id、revision，可带相关 request_id；聚合/集合失效使用显式 invalidate 项和公开查询范围。客户端据此区分可比较 revision 的记录与必须刷新的聚合视图。内部 CAS 路径、参数快照、凭据和原始 journal 不进入响应。

页面按完整 UTF-8 序列化结果限制约 256 KiB，包括外层字段。单事务不拆片：若逐记录结果过大，改为该事务涉及的公开资源类型/集合整体失效，仍完整覆盖其聚合依赖。多事务达到预算就在前一完整事务结束，下一页续上。处理超大事务时边映射边去重并及时退化，不先构造任意大的响应数组。

映射表以 `satisfies Record<Mutation["object_type"], Mapping>` 声明，覆盖生成合同中的全部 mutation 记录类型；无公开投影也显式登记为 none。类型别名可写作 MutationObjectType，但不得另写一份可漂移的字符串枚举，也不用类型断言或宽泛索引签名绕过检查。新增记录类型未登记时，`npm run check` 必须失败；此保证只防漏键，错误填 none 或漏聚合依赖仍由行为回归检查。

日志 event_type 当前为开放字符串；main.message、world 桥接和新展示事件的分类仍由日志映射与回归保证，不把 mutation 穷尽性描述为对全部日志事件的编译保证。映射表维护直接投影和依赖失效，至少包括：

| 提交来源 | 公开变化/失效 |
| --- | --- |
| Input、Session、main.message 等历史事件 | session、timeline；最终消息按既有 call_id/message id 合并 |
| TaskPlan、Execution、Dispatch、WorkerReceipt、TaskResult | 对应 task/execution/request 状态；Execution/结果额外使相关 task 详情失效，结果/归档使 artifacts/related 失效 |
| DecisionRequest、AuthorizationRequest、Operation | decision/authorization/operation、attention、相关 task 接续状态 |
| Scope | scopes 列表和 scope 详情，以及实际依赖 Scope 的公开视图 |
| AuthorizationRule、Operation 派发事件 | 两个规则查询别名及派生匹配次数/时间；不能只看 Rule revision |
| SettingsDraft、SettingsApplication、UserInstructions、Consciousness、CompactionJob、MemoryExtractionJob | settings、memory 状态/摘要/承诺等聚合查询 |
| Notification、notification.presented 日志事件 | notification、notifications；展示事件使对应通知聚合失效，不暴露投递目标协议 |
| AssistantProfile、ClientRegistration、ApiCommand、ProgramRegistration | 已有 assistant/client/request/admin 等可查询资源 |
| world.change_* outbox 桥接事件 | world 查询失效；业务操作与设置的变化按同事务记录映射 |
| 无公开投影记录 | 不输出资源，但保留该事务的水位推进 |

持久模型/执行状态变化可让对应查询失效；预览 delta 和实时活动快照自身不属于持久 changes。映射按公共查询依赖核对，旧分支的 ExtractionRecovery、Delivery 等映射不照搬。Scope、授权规则、人工裁定必须有独立回归断言。

同一聚合资源刷新使用本地递增请求代号：只有最后发出的请求仍可应用响应。最新刷新失败，保持陈旧/待刷新并重试，迟到的旧成功也不能清除该状态。测试客户端模拟乱序响应；Core 不为此新增跨资源 revision 或快照存储。

## 5. SSE、预览与资源上限

`GET /api/v1/sync/stream?after=<cursor>` 接受 Last-Event-ID。只有其中一个时直接使用，同时提供时必须一致，否则复用 INVALID_QUERY；游标在发送响应头之前完成校验。所有 SSE 请求经过现有 bearer、Host/Origin 和版本校验。

补发与实时跟随共用 changes 的已提交帧读取循环，每个事务一条 change 事件，id 是该完整事务之后的 cursor。无公开变化的事务也可发空 changes 事件以推进水位。Core 写出成功不等于客户端已应用；断开后按客户端已应用位置补发。提交后、推送前崩溃不会丢失事务。

约 5 秒发送无 id 心跳。每连接总待写预算初定 512 KiB，单 change 事件不超过页面预算，等待 drain 最多 5 秒；超限/超时仅断开该连接。瞬态预览与活动合并成最新状态、可丢弃，无 id，不推进同步水位；持久追赶期间也留出心跳与最新预览的处理机会。

为防止重复重连遗留连接占用描述符，初定每服务最多 8 个活动流，达到上限复用 BUSY/503。此上限与写预算是单机资源限制，测试报告同时记录实际待写峰值和其他客户端响应，实施时若调整常量须说明依据。

读取循环按批让出事件循环，断线/服务关闭清理计时器、drain/close 监听和活动计数；不为每连接维护无界事务队列。预览保留既有文本/块上限；通知 DTO 按 §6 有界内联，已有消息分片查询保留。SSE 重连期间预览允许丢失，最终保存消息按既有稳定身份接替预览，只显示一次。

## 6. 通知查询、展示与全局已读

### 6.1 数据和接口

提供 `GET notifications`、`GET notifications/{id}`，所有客户端均可查询同一通知集合。DTO 包含既有身份/状态/时间、created_sequence、内联内容及元信息、全局 read_at、各 client_id 的 presented_at。缺失新增字段的历史通知投影为未读/无展示证据，GET 不回写旧数据。

通知内容有 text/plain 和既有 JSON；DTO 返回 UTF-8 文本与 media_type/content_version/原始 bytes，列表每项文本初限 2 KiB，详情初限 64 KiB，超限返回完整 Unicode 边界上的前缀与 `truncated: true`。JSON 前缀作为文本展示，不要求客户端把截断文本解析成完整 JSON。只限制读响应，Store 中原文和现有生成路径不截断；业务证据检查使用服务端原内容。

本批不增加 `GET notifications/{id}/content`、内容 next_cursor 或通用 cas-text 模块；有界通知读取留在 notification-service 内。现有 MasterInteract 的 message 没有长度约束（Host:1031–1040），Store.put 也不限制字节数（Store:205–231），因此有界响应有源码依据；这并不等于已经观测到超大通知，也不足以证明本批需要内容分页端点。#10 如实际需要完整超长内容，再单独明确合同与验收。

- `POST notifications/{id}/presented {request_id, client_id}`：client_id 必须是本数据域已有 ClientRegistration。首次展示只保存一个 `notification.presented` 日志事件，payload 为 notification_id、client_id、服务端 presented_at；event_id 从通知/客户端组合确定，scope 绑定通知 session，actor 为 MASTER_UI。同对再次上报保留首次时间/事件，不新增另一种 NotificationPresentation 持久记录或通知快照引用。不提供 received/目标绑定/路由。
- `POST notifications/{id}/read {request_id}`：在 Notification 上新增可选 read_at，首次写入后单调保持；所有客户端看到同一值。已读不自动补 presented，presented 也不自动已读。

两类命令沿用短命令 admission，将 ApiCommand 和首个领域变更写在同一事务；presented 的事件与 ApiCommand 原子保存，回执关联原 Notification 资源。相同 request_id 重投取原回执，换 payload 沿用 REQUEST_CONFLICT。不同 request_id 对同一展示对/已读状态仍为业务幂等，可保存现有 NO_CHANGES 回执。对已提交日志建立可重建的通知/客户端索引，查询、幂等与重启恢复使用同一索引；展示 payload 校验其类型，但不扩展 Mutation 的记录枚举，不新增投递状态机。

Notification 的 QUEUED/SENT 等原字段与状态含义保留；presented/read 不把通知伪造为渠道 SENT。notification.presented 映射为通知聚合失效，即使 Notification revision 不变也必须刷新展示状态。

### 6.2 记忆承诺与历史

唯一的持久展示证据是上述 `notification.presented` 事件。履约判断验证真实已提交的事件、通知/客户端关联及展示时间，不绑定 Notification revision 或整个记录快照散列；read_at、发送进度或 receipt 更新因此不会使展示证据失效。读取或已读本身不构成展示证据。

选择事件形式是为沿用现有 `resolution_event_ids` 和 sourceEnd：来源事件必须在展示事件之前，本次维护只使用 sourceEnd 内的证据，完成承诺仍记录真实展示 event_id。仅保留新增业务记录会要求另改证据引用合同和事件水位判定。Notification 的 message/session 在本批创建后不编辑；现有 send/read 更新只改进度/回执/已读，履约查询沿用原内容与 TaskResult 的任务、执行和 outcome 匹配，不假设 Notification 已有独立来源/结果字段。

memory 的新自动履约与 Host delivered_notifications 一起改为读取 presented 证据，继续校验同会话、来源时间/事件先后、持久来源批次、承诺文字范围、任务/执行和结果关联。通用/复合承诺仍由 Master 明确裁定。旧已完成承诺保留；新自动判断不再仅凭旧 SENT 完成未履约承诺。旧通知、旧 notification.result 和 receipt 原样可读，不批量改写为新展示记录。

展示命令不新增 Input、主动运行模型或执行工具；常规维护过程消费真实展示证据。实际 ack 接口与维护路径分别验收，避免只测一个纯函数。

初始加载 S 前的通知只进入列表，不弹系统通知；重启后的本地已展示记录用于抑制重复弹出。通知首次创建 sequence 可从 journal 派生并公开，用于区分 S 前历史与 S 后新增，历史通知后来的 read/presented 更新不应被误判为新通知。若首次加载中实际展示历史条目，也只能在展示后上报 presented。#10 负责实际 UI，测试客户端覆盖这套判定；#22 的发送结果不能制造 presented/read。

## 7. 只读边界与新增守卫

sync cursor/changes/stream 与资源 GET 只访问已有记录和可重建投影，不调用 accept、pump、viewed、drain、migrate 或工具派发。反复读、重连、翻页不得写 CAS/journal、增加 Input/ModelCall、改变业务 revision 或执行留存时间。初始化与常规后台业务运行单独计量，避免将后台自然变化误归因于读取。

| 守卫/行为 | 防止的具体故障 |
| --- | --- |
| owner_id + sequence + digest 校验，RESYNC_REQUIRED | 换目录或同身份恢复分叉后，把另一历史错误接到已有缓存 |
| 稳定键续页 | 持续模型/任务写入让初始列表永远翻不到第二页，遗漏 S 前旧记录 |
| 聚合 invalidate、最后请求结果生效 | Execution 变化被 TaskPlan revision 否决；旧响应覆盖新结果 |
| 事务数/字节预算、整体失效 | 超大事务产生半应用水位或响应/队列失控 |
| 连接/drain 上限和关闭清理 | 慢读或反复重连耗尽内存/连接，拖住另一客户端及后台 |
| 注册 client_id、唯一展示事件、首次 read_at | 拼错客户端身份、重投产生重复履约事件或分叉已读状态 |
| 唯一展示事件、来源/结果校验，不绑通知 revision | read/发送进度更新使原证据失效，或无关通知错误完成承诺；保持证据的事件先后与维护水位约束 |

除必要 RESYNC_REQUIRED 外，优先复用现有 INVALID_QUERY、INVALID_LIMIT、NOT_FOUND、FORBIDDEN、REQUEST_CONFLICT、BUSY 等错误；不增加无具体故障依据的状态或通用框架。
