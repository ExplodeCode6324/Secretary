## 3. 授权判定与内建策略

### 3.1 固定顺序与派发复核

1. 校验真实 Execution、绑定工作根、动作 resource 和持久参数；沿用 #18 的未知结果拦截。同一文件未知写入、同执行未知 shell/program 均不能被新策略绕过。
2. 命中有效用户规则则记录其 ID/revision；否则尝试内建策略；再否则创建现有审批请求。多条用户规则采用稳定选择顺序，避免重放后选择变化。
3. Operation 的 rule_id 为用户规则 ID 或 `builtin:workspace-write` / `builtin:readonly-shell`；内建规则使用固定策略版本写入 rule_revision。
4. dispatch 根据已记录的来源复核：用户规则精确复核原 ID/revision/时间/约束，内建策略重查当前适用条件；不因另一条规则现在可用而偷偷替换原授权。现有 approval revision/display_hash、owner_epoch、attempt_id、取消、资源版本和前置条件全部保留。
5. 内建或用户规则派发前失效，统一以 `RULE_CHANGED` 拒绝派发，不增加 AUTHORIZED→WAIT_AUTH 回退。仍为 AUTHORIZED 且 effect=NOT_STARTED 的操作，沿用状态目录已有的 `Operation-14` cancel 转移收束为 CANCELLED，保存失效原因；不得伪造 DISPATCHED 后再 finish。这样避免悬挂 AUTHORIZED 使 continuationParent 永久报 UNRESOLVED_OPERATION。Scheduler 沿用工具错误/执行失败反馈，不自动新建操作重试。
6. **取消后的同参数再次调用采用 r2 方案 1 的收窄版本。** 当前 prepare 对同 intent 只返回旧 Operation（authorization.ts:32–43），write 的 intent 又由 Execution ID + 参数生成，同执行重试不会自然产生新 intent。保留这个基础身份；仅当旧操作因本批策略复核 `RULE_CHANGED` 被取消、state=CANCELLED、effect=NOT_STARTED 且没有派发/进程启动证据时，后续 prepare 才可创建后继 Operation。Master 的 REJECT/REVOKE、执行取消、其他取消原因以及 DISPATCHED/RESULT_UNKNOWN 均不适用；禁止把所有 CANCELLED 当作可重试。
7. 后继 intent 由基础 intent 与被替代的 Operation ID 确定性生成，`retry_of` 指向旧记录；旧记录保留。prepare 从基础记录查找已有后继链，先返回最新未取消后继，不能每次调用都从第一代再创建。参数/resource/action 的冲突校验保留；后继重新经过未知结果拦截、当前 Scope/规则判定，并取得当前文件 revision，绝不继承旧授权。创建后继沿用 Store 串行提交；同输入重复 prepare、重启或重放都复用同一后继/审批请求，连续策略变化也不分叉。
8. 只有后续实际工具调用才触发上述 prepare；RULE_CHANGED 的取消处理自身不递归 prepare、不自动重放。write 仅在 `op.state === WAIT_AUTH` 且存在有效关联的审批请求时设置执行 WAIT_AUTH；CANCELLED 返回明确工具错误及原因，其他不可派发状态也返回错误，不设置空 waiting_request_ids。已成功操作仍复用结果，未知操作仍进入未知结果处理。recover 沿用 epoch 重绑，后继链选择由 prepare 完成。

### 3.2 workspace-write

- 仅覆盖有真实 Execution 的 `file.write`；resource 必须等于服务端从其绑定根及写入 path 推导的目标，不能由调用者仅传一个看似位于目录内的 resource 冒充。
- DIRECTORY Scope 新增 `default_write: allow | ask`，缺失按 allow 读取；新建默认 allow。NONE/无 Scope 的临时 workspace 始终启用此内建策略。
- 本计划选择：DIRECTORY 执行在 prepare 与 dispatch 时读取关联 Scope 的当前 default_write，allow 改 ask 可阻止尚未派发的默认写入；执行根始终使用 Execution 的旧绑定，不跟随 Scope 改根。Scope 后续改变 kind 也不改变旧执行绑定种类。
- ask 只关闭内建写入，已有有效显式规则仍可匹配；已派发写入不撤销。Scope 归档沿用 #16 的既定执行生命周期。
- 继续拒绝根目录本身、越界、符号链接路径；不修改文件版本冲突与未知写入校验。

### 3.3 readonly-shell

新增一个小型纯解析/判定模块（拟 `shell-policy.ts`），由 prepare、remember 推导及 dispatch 复用；不引入通用 shell 执行解释器。

- 保守规则：原始命令只要出现 `; & |`、反引号、`$ > < ( )`、CR/LF 就不匹配，即使位于引号内。引号仅用于分词；引号未闭合、悬空转义、环境赋值前缀、空命令和未知语法均回审批。反斜杠按受支持的 shell 引号规则解释，不能通过转义藏入控制字符。
- 返回固定 token 数组，再按命令专用语法识别选项值、模式、路径和 revision；不以字符串 startsWith 匹配。短选项组合只允许全部属于该命令支持集且无歧义的形式；未知长选项、缩写和参数形式回审批。
- 本期允许集合以上游 #17 表为上限，具体如下。路径类位置全部复用公共路径检查；目录参数 `.` 仅在显式 allowRoot 模式有效。模式不是路径，`*.ts` 保留字面；不做 shell glob 展开。

| 命令 | 首期支持 | 参数识别与收紧 |
| --- | --- | --- |
| ls | -l -a -h -R -t -1 | 其余参数全是路径；省略路径视为根 |
| cat/stat/file | 无选项 | 参数全是路径；拒绝 stdin 的 `-`；cat 内容读取须为普通文件，stat/file 可检查目录元数据 |
| head/tail | -n | -n 后为受限整数，其他位置为文件；不支持 -f |
| wc | -l -w -c | 其他位置为文件；拒绝 --files0-from |
| tree | -L -a -d | -L 后为非负整数；拒绝 -o |
| grep | -r -n -i -l -c -E -F -w --include --exclude | 单个模式及路径；include/exclude 值为字面模式；拒绝 -f |
| rg | -n -i -l -c -F -w -g --hidden -t | 模式、glob、类型与路径分别校验；拒绝 --pre/--pre-glob |
| find | -name -iname -type -maxdepth -mindepth -path -size -mtime | 至少一个明确根内起点，支持列出的谓词与隐式 AND；拒绝所有执行、删除、输出文件谓词 |
| git status/diff/log/show/rev-parse | 按子命令定义的 --stat --name-only --oneline -n --cached 子集 | 不把整个选项集应用于所有子命令；允许明确的安全 revision 形式和 -- 后的路径；复杂对象/pathspec 语法回审批 |
| git branch | 无参数 | 仅列出；分支名、任何选项均回审批 |

- `git diff/log/show` 生成最终 argv 时，在子命令之后、用户参数及 `--` 之前插入 `--no-ext-diff --no-textconv`；最终 argv 存入操作参数参与哈希、公开展示并直接执行。
- 仅内建只读策略放行的命令不经 bash -c。保留原始 command 供审计，持久记录执行方式、最终 argv 与 cwd。prepare 与 dispatch 比较同一持久描述；历史无 argv 的操作保持原审批语义，不能在恢复时悄悄改写其哈希或执行方式。
- 通过原 launchProcess 保留 #18 的先落盘后启动、取消、EOF、超时、输出上限、进程组停止与 UNKNOWN 回执。用户规则与单次批准沿用现有 bash 路径，复用相同 cwd、PATH 和环境构造，不因 remember 换执行器。

### 3.4 路径与工具隐式行为

路径检查采用固定入口检查与固定 argv/env，不进行递归目录预扫描，不建设通用 Git 仓库隔离器。

- **路径与链接：** 所有路径参数禁止绝对路径、~、.. 路径组件，复用现存祖先符号链接检查；读目录允许根，写目标不允许根。递归命令只保留默认不跟随链接的形式：ls 不支持 -L/-H，grep 不支持 -R/-S/-O，rg 不支持 -L/--follow，find 不支持 -L/-H/-follow，tree 不支持 -l。tree 的 -L 是深度选项，继续支持。GNU grep 的 -r 会跟随命令行显式链接，公共路径检查仍须保留；macOS grep 的 -r/-R 是递归别名，跟随开关是 -S/-O，不能直接套 GNU 说明。分别在 macOS/Linux 合成链接树验证。
- **特殊文件：** 保留直接内容读取的文件操作数的 lstat 普通文件检查，覆盖 cat/head/tail/wc/grep/rg；grep/rg 的递归目录操作数仍允许，stat/file 保留其元数据检查用途。删除递归特殊文件预扫描。grep 最终 argv 由服务端加 `--devices=skip`（两端均支持），不向用户白名单开放该选项；其他递归工具以固定不跟随/不读特殊文件形式验证。超时与输出上限限制时长和数量，不能阻止 FIFO 接收根外进程数据，也不能把设备读取变成普通文件读取。
- **程序解析：** 内建命令从服务端固定的工具查找目录解析，排除工作根及其子目录，不继承模型输入或项目临时改写的 PATH；记录可执行绝对路径。程序缺失回审批。此规则仅用于内建命令，用户规则沿用显式批准 shell 的环境。
- **Git 固定条件：** `<root>/.git` 必须是实际目录且不是符号链接，gitfile/worktree 形式回审批；`.git/objects` 与 `.git/objects/info` 的现存祖先复用无链接检查。存在 `.git/commondir`、`.git/objects/info/alternates` 或 `http-alternates` 就回审批，不递归解析借用对象链。这个固定存在性检查保留根外对象边界，不采纳“alternates 只读所以无需检查”。
- **Git 环境与 argv：** 显式环境白名单设置 `GIT_CEILING_DIRECTORIES=<root 父目录>`、`GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_OPTIONAL_LOCKS=0`，不继承 GIT_DIR/GIT_WORK_TREE/GIT_COMMON_DIR/GIT_OBJECT_DIRECTORY/GIT_ALTERNATE_OBJECT_DIRECTORIES/GIT_CONFIG_* 等调用方注入。服务端固定全局参数 `--no-pager -c core.fsmonitor=false --git-dir=<root>/.git --work-tree=<root>`，后接子命令，避免本地 core.worktree 指向根外。用户传入 -c/--git-dir/--work-tree 仍拒绝。diff/log/show 的禁用外部处理选项继续按 §3.3 放在子命令之后。rg 服务端加 --no-config。所有服务端参数进入最终 argv 与审计，不加入用户可选白名单。
- **验收边界：** 测试逐项验证上述入口；固定命令仍依赖本机工具和仓库配置的正常工作语义，不构成任意恶意仓库或并发文件替换的 OS 隔离。发现新的具体外部读取/执行入口时，记录失败并收紧对应内建形式后再验收，不用模糊的“无法证明”判定或全目录扫描替代。扩大白名单需修订计划。

## 4. 可复用规则与批准并记住

### 4.1 约束模型

在既有 parameter_constraints CAS 中加入有区分字段的结构化对象，继续读取 `{parameter_hash}`。未知形状不匹配，不能当作空约束放行。

| 动作 | 新约束 | 语义 |
| --- | --- | --- |
| file.write | 明确的文件前缀约束类型 | resource 在某个规范目录前缀内；按路径组件匹配 |
| shell.run | command_prefix: token[] | 简单命令 argv 以完整 token 前缀开始；cwd 在 resource 前缀内 |
| program.run | program_id | 同一登记程序、参数不限；仍保留程序身份/版本与派发检查 |
| world.change | 旧 parameter_hash | 维持精确授权 |

用户 shell 规则是 Master 授予的可执行命令前缀，可有副作用，不套用只读选项白名单。公开展示须明确“cwd 范围 + 命令前缀”，不能描述成文件/网络沙箱。用户规则以解析 token 匹配前缀，执行仍使用保存的原始 command 经 `/bin/bash --noprofile --norc -c`，与首次单次批准复用同一环境/cwd/timeout 构造；这里的 token 仅用于匹配，不是内建只读执行 argv。为避免前缀被 bash 展开成另一条命令，可复用规则还拒绝未引用的 glob、花括号/波浪号展开、注释和 shell 保留字起始；有引号的字面模式允许。无法满足者仍可单次批准。该收紧与内建策略分开，用户规则不取得内建只读保证。

现有 RuleCommand 的 parameters 精确规则入口保留；新增显式结构化 constraints 分支并与 parameters 互斥，增加 shell.run 及有效期输入。owner 才能调用，模型不注册创建/扩大规则工具。valid_from/expires_at 严格验证，范围前缀按动作校验；旧 hash 规则不自动转换成宽规则。

### 4.2 remember 事务

- ApprovalCommand 仅 APPROVE 可带 remember；REJECT/REVOKE 携带时拒绝，不忽略。其他动作首期不支持 remember。
- shell：`{prefix_tokens: n, expires_at: time|null}`，n 为 1..token 数的整数，服务端从已展示操作推导前缀，resource 固定为该 Execution 的绑定根。复杂 shell 无法生成规则，Master 可不带 remember 单次批准。
- write：`{path_prefix: relativeDirectory, expires_at: time|null}`，必须是本次文件的祖先目录、根内且无符号链接；`.` 明确代表整个绑定根。未存在目录可按安全祖先与规范路径校验，不能把目标文件本身当目录前缀。
- 先核对 revision/display_hash/有效期/状态，再推导并完整校验规则，最后一次 Store.commit 写入 AuthorizationRequest、Operation、AuthorizationRule、审计事件和请求幂等回执。不能先调用会自行 commit 的 rule() 再 decide()。
- request_id 相同且 payload 相同只返回原结果，不重复建规则；payload 不同冲突。崩溃恢复只有全部提交或全部未提交；CAS 孤立对象不构成授权生效。
- 本次操作仍由原单次批准授权，所建规则作用于后续匹配。之后 REVOKE 不隐式禁用已创建的持久规则，禁用走现有独立入口；DTO 与手册说明该关系。

### 4.3 客户端可展示合同
