## 4. 展示语义

### 4.1 消息之间的活动记录（第二版，已批准）

Master 于 2026-10-05 明确：多个活动并行时可以同时展示。本计划据此采用活动集合，不选出唯一的当前状态，也不设置活动之间的展示竞争或覆盖优先级。

WebUI 将活动主要展示位置移至消息流内部，位于有关消息前后，以小图标、较弱文字层级和简短说明呈现，参考 Master 提供的截图。活动不是 Secretary 正文，不使用用户气泡，不写入模型上下文。连续短步骤可以折叠为一组，点击查看具体步骤、时间和现有操作入口；失败与等待处理不能藏在默认折叠的成功步骤内。并行活动保持各自身份与位置，不能互相覆盖。输入区不再重复显示整份活动列表，仅保留排队/连接提示，以及运行中或待处理活动的跳转入口，便于找到已滚出视野的任务。

示例：

- `主会话：正在思考 · 已用 8 秒`
- `设置：正在整理旧上下文，第 2/3 段（已完成 1 段） · 待处理消息 2 条`
- `主会话：正在查看 World Model · 后台：1 个任务执行中，1 个等待授权`
- `连接中断，活动状态暂不可确认 · 最后同步于 10:20:15`

例如主会话与两个后台任务并行时，同时显示三条：

```text
主会话：正在思考 · 已用 8 秒
任务 A：正在读取文件 · 已用 3 秒
任务 B：等待 Master 授权 · 查看授权
```

只有真实模型调用进行中才使用正在思考。活动记录不承载推理文本；已有正文及可见思考显示偏好保持原语义，两项仍默认开启。没有段数时仅显示阶段和耗时，不产生百分比或预计完成时间。

详情显示开始时间、已耗时、最近实际进展时间和适用操作入口。正常完成后在原位置保留简洁终态记录，不再三秒后消失；终态耗时冻结。完成文案描述真实结果，例如「已读取文件」「命令执行失败」，不能直接把「正在读取」作为完成文案。失败、等待用户处理、未知结果保留明确状态与入口。保留数量及跨刷新/重启边界见第 12 节；这不是无限期活动审计流水。

### 4.2 活动归属与独立生命周期

活动至少区分主会话、设置/记忆维护、各后台 Execution；父活动与子步骤关联。设置正在等待主会话释放安全边界时，应同时显示主会话真实活动与设置待处理，不能提前标为正在摘要。

主会话、设置/记忆维护和各后台任务并列展示；排队数量及阻塞原因作为独立提示同时出现，不替换其他活动。采用稳定的分组及开始顺序，活动更新不抢占位置。后台数量可作为辅助汇总，等待授权、决定、前置条件及未知结果分别计数，不能算作执行中。后台数按唯一 Execution 统计，不能把一个任务的模型和工具算成两个任务。

每项活动按独立 ID 更新和结束；A 完成只结束 A，不能清空 B 或全局活动集合。同一活动的连续步骤更新该活动行；父任务和当前子步骤可合并在一行说明，真实并行的子活动分别展示。仍需处理同一活动的迟到事件及重连旧快照，避免已结束活动重新出现；这是事件一致性要求，不需要引入活动之间的互斥仲裁。

### 4.3 排队计数

- 只统计当前 session 中 producer 为 MASTER 且 state 为 ACCEPTED 的消息；CLAIMED 表示已领取，显示处理中，系统反馈另计。
- 输入区的队列提示显示待处理消息 N 条及阻塞原因。若展示单条消息前方数量，按真实持久化接收顺序统计更早的 ACCEPTED 用户输入，同时说明可能批量处理；不能暗示严格单条 FIFO。
- HTTP 发送中或发送结果未知不等同于已收到；只有持久化回执或状态确认后才展示排队。沿用 request_id 去重，不因刷新、断线或点击活动栏自动重发消息。

### 4.4 状态来源覆盖

| 实际来源 | 活动呈现与结束依据 |
| --- | --- |
| MAIN 模型生命周期 | 调用开始显示思考；完整响应保存或失败/中止后结束该调用；下一工具/调用有独立 ID |
| `memory_read` 的 `source` 白名单 | world、consciousness、log 分别对应 World Model、工作记忆、历史查询；进入真实 execute 后开始，finally 清理 |
| `task_propose/task_query/task_control` | 分发、查询、控制；返回已接受仅表示交接成功，不表示任务完成；命中结果缓存不伪装重新执行 |
| 设置运行配置变化或用户应用 | 依据触发来源区分运行配置初始化与应用设置；按真实等待、整理、校验、提交、重建、终态切换 |
| 摘要和承诺提取 | 子步骤区分摘要、提取、校验；只有整段验证及 checkpoint 成功才增加 completed |
| `feedback.delivered` 与所领取反馈输入 | 读取结果及后续整理回复；仅投递反馈不代表已生成回复 |
| Execution、Operation、AuthorizationRequest、DecisionRequest | 执行、等待、取消中、完成、失败、RESULT_UNKNOWN；以已有业务状态为准 |
| 主会话恢复/容量阻塞、设置失败 | 固定安全原因码与可理解文案；展示已存在且适用的恢复入口 |
| 已有自动尝试循环 | 第一次标为尝试 1/2，第二次为重试 1 次（尝试 2/2）；人工重试单独关联，不虚构 provider 内部重试 |

## 5. 实现方案

### 5.1 共用只读活动投影

新增 `src/pi_secretary/src/activity.ts`，统一字段、来源映射、脱敏和聚合。活动是观察结果，不是业务命令或新的任务状态机。建议数据包含：

```text
snapshot: server_instance_id, activity_revision, store_revision, observed_at,
          activities[], background_counts, queue, recent
activity: id, parent_id, scope, session_id, execution_id, source_id,
          kind, phase, status, started_at, last_progress_at, ended_at,
          progress? { current, completed, total, attempt, max_attempts },
          safe_reason_code?, actions[]
```

优先从既有 ModelCall、SettingsApplication、CompactionJob、Input、Execution、授权、决定和相关事件派生持久状态。读取设置的 source_ref/candidate_ref 时只取数量，按记录 revision 缓存，不能每个客户端每次轮询重读整份历史。

实时模型/工具的开始、子阶段和 finally 结束由有界内存观察器补足，带当前后台实例 ID；内部按活动 ID 维护集合，各条目有自身版本，快照有整体 activity_revision，不依赖正文预览或每秒 Store 写入。客户端按 ID 更新对应行，不能用单个全局 status 相互覆盖。只保存白名单标量，不保存提示词、参数、查询结果、原始错误及提取引句。

第二版以既有历史库（journal 事务、结构化事件及 CAS 对象）作为已发生活动的主要来源，构建独立于普通消息列表的只读活动视图；内存观察器只补充进行中的细阶段。已落盘的工具结果、模型调用、任务和维护事件可跨重启重建，不再受内存 recent 的 50 条限制。默认不新增持久化记录类型、数据库表或迁移，不逐 token 写 journal；旧历史缺少的开始时刻、未落盘的阶段不能补造。具体覆盖、分页与重建方法见第 12.3/12.5 节。

### 5.2 业务接入边界

1. `durableStream` 接入轻量生命周期回调，覆盖 MAIN、TASK 及摘要/提取的父子关系；只在真实调用开始时标活跃。无需消费第二份 provider stream，不更改先保存完整响应再执行工具的约束。
2. Host 工具包装器在去重命中判断后、真实 execute 前开始；成功、异常、取消均用 finally 收尾。保持原返回值和异常，不让显示模块错误改变执行结果。
3. Settings/summarizeSettings 在真实阶段边界发观察事件。已有 source/candidate checkpoint 继续作为总段数、完成数和重启恢复依据；当 checkpoint 未完成时不能对外报完成。
4. 当前工作区的专职承诺提取必须接入父活动，不额外引入模型请求；摘要输出有效但提取失败时该段仍未完成。
5. Scheduler 复用现有业务终态、等待状态和恢复判断，补充必要的执行中观察；UNKNOWN 不改成失败或自动重试。取消请求期间显示取消中，直到已有业务逻辑确认终态。
6. 活动元数据不得成为用户记忆、模型指令或新事实证据；不得为了展示读取原始日志全文。无需修改 vendored Pi 源码。

### 5.3 API、SSE 与重连

- 新增经过现有 Bearer、同源和 client 校验的只读 `/api/activity`，提供完整活动快照，支持实例 ID 与活动 revision 条件查询；它不等待 `client.busy`。
- 扩展现有 SSE，增加独立 `activity` 事件。前端按 event 类型路由，preview 与 activity 各自维护版本；不能让现有解析器把活动快照当作 preview。
- 关闭正文 streaming 时仍订阅 activity，禁用正文预览传输/渲染；关闭 thinking 时活动载荷也不会包含思考字段。
- 新连接先发送当前快照；版本按 `(server_instance_id, activity_revision)` 比较，重启允许版本归零。SSE 断开后通过 `/api/activity` 降级轮询，恢复后回到推送；不生成第二次业务请求。
- 阶段变化合并推送，目标间隔 100–250ms；近期状态有界，保留快于推送间隔的已结束步骤。沿用慢客户端断开和连接清理，限制任务明细和文本长度，同时返回总计数及截断标识。
- 客户端独立更新耗时，不因此每秒生成服务端事件。心跳和拉取成功只更新连接时间，不能冒充业务进展。
- 初次连接、实例变化、CLIENT_EXPIRED、乱序快照和过期请求响应均有明确重置规则。网络请求设超时；连接不可确认时停止活跃动画并显示未知，不凭浏览器掉线断言后台失败。

### 5.4 WebUI 与 TUI

WebUI 将 `app.js` 的消息/预览渲染与 `activity.js` 的活动渲染接入同一个时间线排序和节点管理入口，保留独立数据源，按稳定 ID 就地更新。不能只把现有活动容器移动进 `#messages`：两套 DOM 排序会冲突，活动也没有消息锚点。具体关联、保留及增量实施方案见第 12 节。恢复按钮仅定位现有设置重试、授权、决定、任务详情入口；每次操作仍走原验证流程。错误文案由原因码映射，未知异常显示通用原因和关联 ID，不直接插入 `String(error)`。活动文案使用 textContent；任务摘要可选且必须短、单行、清理控制字符，不显示完整 goal/materials。

本次截图对应的布局调整限定 WebUI；TUI 保留已实现的输入区活动布局与 `/activity`，只做新增投影字段的兼容回归，不改成可回写的终端消息历史。

TUI 使用独立 `/api/activity` 请求，与命令和 `/api/poll` 并行，活动读取不改变命令串行语义。TTY 提供紧邻输入区的多行活动区，同时列出并行活动；终端高度不足时明确显示其余数量，通过 `/activity` 查看完整列表。重绘必须保留 readline 输入、光标、中文宽度、换行及 resize；普通输出到达时协调清屏和重绘。非 TTY 只在实质阶段变化时按活动 ID 输出简短文本，不每秒刷屏。`/activity` 同时提供近期活动，沿用 `/auth`、`/decisions`、`/web` 恢复入口。共享 TerminalController 与直接 TUI 入口都需覆盖。

### 5.5 进程退出与恢复

- 已停止进程不可能继续发通知；客户端根据 SSE 断开、请求失败或心跳失联降级为连接中断，不能一直保持正在思考。
- 启动先沿用已有业务恢复，再构建投影；旧 ModelCall IN_FLIGHT 记录只能标上次中断/待恢复，不作为本次活动。只有当前进程实际重新进入执行边界后才标运行。

- 脱离数据层的观察回调故障应被隔离；真正的 Store 提交失败继续按原业务逻辑失败，不能被活动显示掩盖。

### 12.2 具体展示与关联规则

示意结构（仅文案示例，不新增业务步骤）：

```text
Master：帮我查询并整理……
  ✓ 本次思考已结束 · 用时 2 秒
Secretary：我先查一下已有记录。
  ✓ 已查看 World Model · 用时 1 秒
  ✓ 已查询历史记录 · 用时 2 秒
Secretary：查到的情况如下……
  ◌ 任务 A：正在读取文件 · 已用 5 秒
  ! 任务 B：等待 Master 授权 · 查看授权
Master：再补充一个条件……
```

- 主会话以 loop 和实际领取的 input_ids 关联处理批次；同一次领取多个输入时只建一组处理活动，锚定最后一个被领取输入之后，不能给每个输入重复一份活动。后续排队输入不抢走前一批次的活动。
- 模型调用关联 call_id：正在思考位于该次回复之前；预览与完整回复共用同一消息节点及排序身份。工具活动放在发起它的 assistant 调用之后、后续回复之前；没有可见正文的工具调用也有稳定的隐式锚点，不为此制造空消息气泡。主回复可以分多次调用，不强行把整个 loop 的活动全塞到最后一段回复下方。
- 后台任务每个 Execution 有独立分组，锚定已证明的创建/交接事件；以后更新原分组，不随新用户消息移动。多任务可同时显示，父任务摘要和子步骤避免双重计数。任务反馈仍是自己的消息，只关联同一 execution，不重复生成活动副本。找不到历史来源的旧任务放在明确的「既有后台活动」分组，不归到最近输入。
- 设置与自动记忆整理按各自来源事件定位，标签明确「设置」或「记忆整理」。来源不是聊天输入时，按真实开始时间形成独立系统活动组，不虚构由某条用户消息触发。
- 相邻成功步骤在同一归属、且中间没有新消息时可以折叠；不跨用户消息、并行任务或失败/等待状态合并。简洁模式显示动作摘要和固定用时，详情保留各步骤；不显示命令参数、文件内容、工具返回值或原始错误。
- 耗时变化与状态更新原地刷新。用户阅读上方历史时保留首个可见节点及相对偏移；只在原本接近底部时跟随新增内容。远处任务更新时，输入区显示可点击的运行/待处理数量并定位原活动，不复制一条新的活动记录。

### 12.3 数据、排序和恢复边界

1. 扩展展示 DTO，拟加入 `loop_id`、`call_id`、`input_ids`、`anchor_event_id`、锚点前/后位置及稳定排序键；具体字段在实现时收敛，但身份与关联必须由服务端明确给出。内部工具 ID 可能含复合信息，前端不靠解析 ID 字符串建立因果关系。复用已有 Input/Context/ModelCall/事件元数据；按 revision 缓存，不能每个耗时 tick 扫描或读取完整 Context/日志内容。
2. 时间线采用消息和活动两类节点；按已确认的锚点、事件顺序、首次开始顺序和 ID 决定位置，不能按每次更新时间重排。预览开始与消息落盘的 `at` 可能不同，必须保留 call_id 对应的稳定位置；活动先于锚点消息到达时暂存或放在明确未关联组，锚点到齐后合并一次。不得因到达顺序永久归错消息。
3. 新增独立的只读历史活动查询，例如 `/api/activity/history`，沿用现有鉴权、client 和 session 校验，返回活动 DTO、来源标识、排序键和分页游标。首屏默认最近 **50 个活动**，可向前加载；50 是页大小，不是历史保留上限。不得把原始 journal/CAS 内容、工具参数、原始错误或完整响应直接传给浏览器。当前快照仍沿用最多 128 项及截断提示；历史分页与当前/待处理项独立，兼容旧 API。
4. 从已验证的 Store 日志、对象和事务快照建立可重建的只读索引。按 Store 提交序号增量维护，分页查询不重复扫描所有 journal 或读取所有 CAS。现有 Store 启动会重放 journal，但公开 `all()` 只保留最新版本；若需阶段历史，增加只读投影钩子或受校验的事务迭代器，复用现有校验链，不让 UI 私自读文件绕过完整性验证。索引只保存白名单摘要与定位引用，正文按选中页懒读；明确测量长历史下的启动、查询和内存开销，不新增第二份业务历史库。
5. 同一活动的实时与持久记录用稳定来源身份合并，例如 call_id、工具调用身份、Execution ID 或维护 job ID；多个日志佐证同一次工具执行只生成一项活动。落盘确认后由持久结果替换临时状态，显示位置与 ID 保持稳定。历史 ID 不含 server_instance_id，跨重启仍可去重；实例版本只约束临时活动。缺少持久结束证据的旧实时记录不能因重启直接当作成功，也不能继续显示正在执行。
6. 分页使用固定查询上界及稳定游标，防止新事件插入导致翻页漏项/重复；运行项的后续状态通过增量更新归并。按活动原始创建来源排序，结束事件不把旧活动搬到最新位置。浏览器采用有界页面缓存及保留可见位置的淘汰规则，旧页可重新读取，不以缓存淘汰删除持久历史。刷新、双客户端及后台重启后，从同一历史来源重建相同的已发生活动，未被记录的细阶段明确缺失。
7. 继续沿用独立活动 SSE/API、连接判断、隐私过滤及终态耗时修复。等待授权/决定属于未终结等待，可以计时；FAILED/SUCCEEDED/CANCELLED/EXPIRED 等已终结项固定结束时间。旧工具只有完成记录时只显示完成时刻，不显示假设起点的耗时。折叠、重连、切换正文/思考开关都不得重置计时或重新执行业务。

### 12.5 历史库证据与可恢复范围

2026-10-05 核查了实际写入与重放代码。这里的历史库是 `Store` 的 `journal.jsonl` + CAS `objects/`，不是只包含聊天正文的 `conversation()` 返回值，也不是 PostgreSQL World Model 事实表。journal 事务保存记录变更的完整快照引用和 OperationLogRecord；Store 重放恢复事件与记录。既有历史已经包含普通聊天接口没有显示的活动证据。

| 来源与已核查写入点 | 可以生成的活动 | 必须保留的证据边界 |
| --- | --- | --- |
| `transport.ts` 持久化 ModelCall，关联 Context，记录 started_at/completed_at 及完整 response | 模型调用开始/结束、失败/中断、调用耗时、主会话/任务/摘要归属 | 保存了响应不必然代表调用成功，需核对 stopReason；请求中的 toolCall 只表示请求，不证明工具已执行 |
| `host.ts` 的 `main.tool.result`，以及 `main.message` 保存的结构化 toolResult | 主会话历史查询、任务交接等工具结果；可从结果判断成功/错误 | 多来源去重；部分旧记录没有 execute 开始时间。恢复时补写的结果确认时间不冒充原始执行完成时刻 |
| `scheduler.ts` 的 `agent.message`、Checkpoint/Context，含 toolResult；`authorization.ts` 的 operation.prepared/dispatched/result | 后台读取文件、执行命令、操作等待和结果 | 工具成功、操作成功和任务整体成功分别映射；工具请求、授权通过或分发不等于操作成功 |
| Execution/TaskResult、execution.finished、decision/authorization 相关记录 | 任务运行、等待、完成、失败、取消及未知结果 | 使用真实起止时间；历史阶段需要事件/事务快照，不能用最新状态倒推所有过程 |
| `settings.ts` 的 settings.progress/applied、SettingsApplication 快照 | 配置排队、摘要、提交、重建、失败与应用完成 | 已落盘阶段可恢复；未持久化的细分尝试只实时显示，不承诺旧历史有每个子步骤 |
| `host.ts` 的 consciousness.started/retry/committed/stale/failed 等事件、CompactionJob | 上下文整理/压缩开始、重试、完成或失败 | 提取与摘要关联通过 job/Context 元数据验证，不根据回复文字判断是否压缩 |

历史解析采用事件类型白名单和结构化字段，不用 LLM 推测聊天里的「我执行了……」。工具分类只读取所需标量，例如工具名及 memory_read.source；只在服务端解析原始 payload，生成脱敏活动 DTO。某条旧记录无法可靠关联时保留独立来源分组，缺时间显示「耗时未知」或省略耗时，缺结果显示「结果未记录」，不推断失败或自动重试。

因此修正先前评估：**没有独立活动表，并不意味着没有可恢复的活动历史。已存在的结构化日志应优先复用；只有未落盘细阶段和缺失精确计时才是现有数据的真实限制。**

**实施补充：** Master 已批准本节并追加长对话性能评估。历史采用 Store 的已校验事务引用、按会话排序的活动索引及二分分页；新增每页至多 50 个 ID 的只读刷新，用于重连后同步已打开的旧页。活动详情最多保留 12 条阶段摘要，Web 缓存至多 4 个旧页。Store 还增加按类型的当前对象索引，普通消息投影按新事件缓存，均不改变持久化格式或业务语义。

1 千/1 万/3 万活动性能及 1 万条聊天消息缓存已测量。已确认活动分页无需扫描/重读全部历史，但完整聊天响应和 DOM 仍随消息数增长；本轮不包含正文分页/虚拟化，限制及后续方向在第二版报告中明确。生产服务部署与 GitHub 发布仍未执行。

## 13. 第三版：历史按需读取与有界显示（已批准实施）

### 13.1 Master 补充后的目标

Master 明确：不是必须让普通消息与活动共用 2000 条额度，合并索引也不是必要条件；核心是限制读取数据的量和次数，避免长对话性能问题，兼顾简洁性和可维护性，不增加额外外挂组件与逻辑。此补充优先于先前第三版方案中的严格共享额度、固定创建水位和变更游标要求。

第三版继续限定 Web，保留 TUI 和旧 API；不改业务状态机、journal/CAS 格式或 PostgreSQL，不新增服务、依赖或持久化表。2000 条作为默认浏览器缓存参数，不作为产品必须共用配额的业务规则。保留一个普通进程内查询入口，是为了复用排序、鉴权和前后分页，不建立第二套活动事实来源。

### 13.2 收简后的实现决策

| 需求 | 采用方式 | 不再引入的机制 |
| --- | --- | --- |
| 限制历史读取量 | `POST /api/timeline` 每页最多 200 条；只读所选消息正文；活动直接引用第二版投影 | 全量正文缓存、下载完整历史后前端截断 |
| 限制读取次数 | 未变化的轮询不读旧正文；有活动约 700ms、闲置约 5 秒、后台页面约 30 秒查询；状态轮询约 5 秒且版本不变直接返回 | 另一套 SSE 正文/活动缓存与轮询并行运行 |
| 迟到结果与刷新 | 稳定 ID/显示顺序；只检查已加载区间元数据，按条目版本返回变化；区间超过 2200 项则重查阅读位置 | 固定创建上界、服务端变更事件队列、过期事件游标补投 |
| 任务/授权面板 | 复用现有 Store 类型索引和历史归属；打开时一次最多 20 项，按需翻页 | 新建一套任务、授权和决定摘要索引 |
| 浏览器资源 | 默认 2000 条、16 MiB 序列化内容上限，视口附近最多挂载 150 个逻辑条目 | 为凑额度而隐藏一份不计数的活动或正文缓存 |
| 大正文 | 每条保留一个有界正文/思考片段，显示继续/前一段入口，服务器保存全文 | 累加无限全文或静默丢弃历史 |

普通消息和活动在当前实现里使用同一个窗口，以减少两组翻页状态和重复代码；这一选择服务于维护成本，不是新的业务约束。查询层只保存来源引用、稳定顺序及版本；活动对象来自已有 `ActivityHistory`，不复制正文或建立新数据库。深页通过二分定位，没有深页 OFFSET；活动的阶段摘要仍至多 12 条。

### 13.3 接口及一致性

- 新版 Web 使用 `/api/state?window=1`，不调用旧 `conversation()`、不传全量聊天或任务/授权详情。旧 `/api/state` 保持原语义；旧客户端的全量成本不算作新版性能。
- 页游标包含稳定排序键、ID、会话、显示偏好、进程代际和协议版本；支持 before、after、指定 ID 定位。游标不冻结历史成员，新插入的较早活动通过当前窗口版本刷新或下一次翻页可见。不是数据库快照隔离协议。
- 常规刷新最多检查当前窗口附近 2200 项元数据，只读取发生变化的正文，响应仍最多 200 项/1 MiB。无变化时不扫描历史区间或读 CAS 正文；只返回轻量版本和有界活动摘要。实例更换则重新定位当前条目，不重提用户输入。
- 流式和最终回复使用相同调用 ID 及显示顺序；关闭 streaming 不传流式正文，关闭 thinking 不传思考内容。偏好切换取消旧请求并检查客户端 generation，迟到响应不能恢复已关闭内容。
- 同一方向最多一个翻页请求，正文分段一次一个请求；重新定位取消在途请求。失败显示重试入口，不连续自动重试。客户端借当前阅读位置释放较远端，需要时可向相反方向重新读取。
- 原始正文在历史库中完整保存。当前片段按 JSON 编码预算限制在 64 KiB 内，整页不超过 1 MiB；当前实现每个文本字段最多约 4999 个 UTF-16 单位并避开代理对边界。片段切换替换旧片段，字符范围和全文长度明确显示。

### 13.4 UI 与维护范围

Web 只渲染视口附近条目，按稳定 ID 和像素偏移恢复位置，动态高度通过 ResizeObserver 测量。草稿不放进历史窗口；查看旧记录时新消息只提示跳转入口。展开的子活动各自是普通逻辑条目，不偷偷加载整组历史。运行/待处理活动仅保留有界定位入口。

文字选择、当前阅读位置和用户主动展开的详情受短期保护；默认展开的思考块不算用户操作，不得阻止历史释放。预算冲突时暂停预加载并提示重试。详情/高度表/节点随窗口释放，不积累全历史记录。浏览器原生查找只覆盖当前渲染部分，全历史搜索不在范围内。

实现范围：`timeline.ts` 为只读分页查询，`timeline-window.js` 为可单测的缓存操作，`timeline-view.js` 为列表显示，复用现有 Markdown、安全活动文字和 Store。它们是现有程序内模块，不是外挂服务。`backend.ts`、`app.js`、样式及历史投影提供相应接入；业务执行不依赖显示模块。

### 13.5 性能边界与验收

本项目历史来源是本地 journal/CAS，并非此次新增 PostgreSQL 查询。限制页条数不意味着每次底层字节读取都恒定：一个很大的历史消息仍需按现有 CAS 方式读取/解析该对象，再返回小片段。本版不为它另造持久化分块系统。Store 重放、历史元数据内存与初始化时间仍随历史增加；应与热态翻页分开报告。

| 验收 | 证据要求 |
| --- | --- |
| W-A01 顺序/归属 | 独立混合历史 oracle；前后分页、定位、迟到工具、后台子活动、会话隔离，无重复遗漏 |
| W-A02 资源上限 | 连续浏览至少 5000 项，再向下加载被释放项；观察缓存条数、内容预算、DOM/高度表 |
| W-A03 长正文 | 大中文/emoji/控制字符正文可分段还原，页响应 ≤1 MiB、片段 ≤64 KiB，不将正文当 HTML |
| W-A04 变化/恢复 | 已加载区间变化、窗口外新消息、失败计时、实例代际；不重新执行输入 |
| W-A05 时序 | 乱序请求、断线、重试、偏好切换及双客户端；旧响应不恢复思考内容 |
| W-A06 UI | 四种 streaming/thinking 组合、桌面/390px、中文草稿/光标/文字选择；明确跳转以外，稳定后锚点误差目标 ≤4px |
| W-A07 热查询 | 1 千/1 万/10 万条混合历史，每档各 100 次随机深页，单客户端与 4 并发；API P95 ≤100ms；另外记录每页 CAS 次数、响应字节、索引成本和浏览器响应至可见延迟（目标 P95 ≤300ms） |
| W-A08 持续使用 | 10 分钟翻页/更新及 GC 后堆采样；DOM ≤150，缓存/高度表/监听器不随已访问历史无限增长 |
| W-A09 兼容与安全 | 旧 API/TUI、授权隔离、HTML/控制字符；观察或查询失败不改变业务执行 |

运行类型检查、完整离线回归、必要审计与真实 Chrome。没有改变 provider 或 World SQL 路径，不重复真实模型或 PostgreSQL 压测；不得将其写成已验证。先保留失败证据，再修复及复测，不以静默放宽标准掩盖失败。报告位于[第三版验收报告](../../test_case/reports/timeline-window-20261005/README.md)。

## 14. 小幅上滚被拉回底部（Master 已批准修复）

### 原因与修复

真实 Chrome 滚轮复现：底部向上滚 40px、80px 后，`onScroll` 仍因距离底部不足 100px 而保持 `follow=true`，随后 `render()` 强制回到底部；120px 才能脱离。因此并非固定第三次才响应，而是小幅手势被自动跟随覆盖。此前浏览器测试主要直接设置 `scrollTop`，部分还预先关闭 follow，遗漏了首次小幅输入。

- 首次向上滚动立即关闭跟随；向下回到实际底部（2px 浮点/布局容差）或点击“回到最新消息”才恢复。
- 加载较新历史仍使用原有 100px 接近阈值，与自动跟随判断分开。
- 每次渲染记录最终滚动位置，识别稍后到达的程序滚动事件；不再使用同步设置后立即清除的 `adjusting` 标志。
- 同时记录视口和内容尺寸。窗口放大可能在 ResizeObserver 前压低 scrollTop，交由渲染恢复已有跟随或锚点，避免误判为用户上滚。
- 仅修改现有 TimelineView，不增加查询、服务、依赖或新的状态组件。

### 验收与交付边界

新增原生滚轮回归覆盖首次 1/5/20/40/80px、连续小幅上滚、接近底部不恢复、真正到底恢复、键盘上滚、回到最新、流式输出期间阅读历史、窗口缩放及原生滚轮触发历史分页。保留旧代码失败及首轮尺寸边界失败证据；执行已有浏览器分页/流式/断线与竞态回归、受影响离线测试、类型及文档检查。

结果见[滚动修复报告](../../test_case/reports/timeline-scroll-20261005/README.md)。本次不重复未变化的数据库性能压测、模型调用或十分钟持续测试。界面装饰文案清理沿用上一轮已验证修改。未部署、未重启生产、未推送。
