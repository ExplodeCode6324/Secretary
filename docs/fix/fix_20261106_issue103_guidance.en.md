## 1. Result and current implementation

Master or Main can guide an exact unfinished AGENT Execution. Core persists the instruction before delivery, exposes SENT / RECEIVED / GUIDED separately, and prevents an old tool plan or recovered response from silently bypassing it. Guidance changes the approach within the assignment and existing authority; it does not approve an operation, answer a pending question, expand authority or create a new execution.

Example: a write is waiting for approval. Master sends “first inspect the logs; do not write yet”. The instruction is durably SENT while authorization remains pending. Even if approval arrives, the old write cannot run before a fresh model request includes the guidance and its disposition. Granting authorization alone cannot override the guidance: the obsolete approved operation is retired and the model replans; any replacement passes ordinary authorization again. If Master rejects/revokes instead, preserve the existing FAILED outcome and close the guidance as UNPROCESSED with the denial reason. Leaving the request pending keeps the execution waiting. This plan does not introduce “deny and continue” or automatic withdrawal of pending authorization.

## 2. Contract, identities and atomic acceptance

Implement a small shared `guidance.ts` domain service used by both entrances.

- Proposed Master command: `POST /api/v1/executions/:id/guidance`, body `{request_id, task_id, text}`. Exact execution/task IDs are mandatory. Authentication establishes MASTER; body cannot set source, timestamps, receipts or call IDs. Main `task_control(action=guide, id=execution_id, task_id, text)` derives MAIN from the trusted tool runtime, with session/loop/ModelCall/tool-call provenance. Same domain validation, separate trusted constructors.
- Guidance identity is stable across retry. Preserve exact UTF-8 text in immutable object storage, its hash/length, task/execution/session, source kind/reference, request identity/fingerprint, per-execution acceptance sequence and record revision. Master source references the actual authenticated command and paired Input; Main source references its real persisted calling context, never fabricated Master text.
- Same identity + identical payload returns the original accepted object even if the target later ended; changed payload/target/source or reuse across unrelated command namespaces is REQUEST_CONFLICT. Check identity before current-state validation. Main replay also deduplicates by the original loop/tool identity.
- Commit Guidance + required Master informational Input + command binding in ONE synchronous journal transaction. The Input contains exact text and structured `guidance_id`, exact target, and “already accepted; do not deliver again”. Prepare it directly; do not call ordinary `accept()` in a way that clears RECOVERY_BLOCKED or resumes Main. Main settings/model unavailability cannot block direct guidance admission/delivery. No paired Input for Main's own tool invocation.
- Queries: `GET /api/v1/guidance/:id`, bounded `GET /api/v1/executions/:id/guidance?cursor=&limit=`, and existing request-receipt lookup for uncertain commands. Default page 20, maximum 100; acceptance-order cursor plus stable ID. Expose both MASTER and MAIN origins, exact text via bounded detail, stages, evidence references, processing/closing reason and revision. Add sync mapping/invalidations and task-history entries without emitting normal PROGRESS feedback.
- Master-approved hard admission limits: 16,384 UTF-8 bytes per instruction; 64 accepted instructions / 65,536 aggregate original-text bytes per execution. Reject before acceptance with explicit limits, never trim/truncate or silently convert text into a pointer-only “consumed” claim. These bound the active guidance set, independent of unrelated history; total model capacity checks still apply. This preserves long/multiline text within an explicit contract; no attachment/large-document subsystem in #103. Over-limit input cannot be sent: Core rejects it atomically before creating Guidance or its informational Input; no truncation, splitting, automatic retry or partial acceptance. The #106 client prevents known-over-limit submission and preserves the draft; Core remains authoritative for count/aggregate races.

## 3. State and receipt semantics

Admission checks the immutable effective executor, real ownership and current execution. CREATED, WAIT_PRECONDITION, READY, DISPATCHING, RUNNING, WAIT_AUTH, WAIT_DECISION accept guidance for an existing AGENT Execution. A queued request without an Execution is not a target. A paused/archived scope does not become dispatchable through guidance. RESULT_UNKNOWN accepts durable held guidance with `UNKNOWN_EFFECT` reason but cannot resume/replay unknown effects; existing reconciliation may end the execution, then settle it unprocessed. CANCEL_REQUESTED or `cancel_requested=true` rejects new guidance; SUCCEEDED/FAILED/CANCELLED/EXPIRED reject as ended. PROGRAM rejects as unsupported. No retarget to Main/latest/next round.

Suggested public errors: `GUIDANCE_EMPTY`, `GUIDANCE_TOO_LARGE`, `GUIDANCE_LIMIT_REACHED`, `TARGET_NOT_FOUND`, `TARGET_MISMATCH`, `TARGET_ENDED`, `TARGET_CANCELLING`, `GUIDANCE_UNSUPPORTED_EXECUTOR`, plus existing `REQUEST_CONFLICT`. WAIT reasons are queryable, not misleading send errors.

Use independent milestones and a processing disposition, not one overwritable state:

| Fact | Evidence required |
| --- | --- |
| SENT | Accepted Guidance transaction and server time. An HTTP request without confirmed acceptance remains client-uncertain. |
| RECEIVED | Host-injected guidance is durably present in the Agent context/checkpoint, bound to execution/attempt and its exact ID/hash. Use the existing message_end checkpoint seam, verifying that the checkpoint actually includes the emitted message before recording reception. No separate inbox record; merely calling steer is insufficient. Waiting/no-agent states remain SENT with their wait reason. First receive time is immutable; re-deliveries append evidence. |
| GUIDED | A durable successful ModelCall request actually contains the host-injected instruction and the same persisted response includes a validated structured ADOPTED receipt. Link request, response, tool invocation and acceptance evidence. |

Processing outcomes: PENDING, ADOPTED, CONFLICT, CANNOT_APPLY, UNPROCESSED. ADOPTED alone advances GUIDED. A later conflict does not erase an earlier GUIDED milestone; it changes current applicability and blocks success until resolved. Closing reasons cover cancelled, failed, expired, target ended, unknown-effect settlement, capacity and mandatory-consumption failure. Preserve original text and append evidence events; keep a bounded current projection instead of growing arrays inside every revision.

## 4. Real model evidence and effective requirements

- Add executor tool `guidance_receipt` with a bounded batch of `{guidance_id, outcome, explanation, effective_requirements, conflicts_with, resolution_refs}`. It runs as part of the ordinary task response; do not make an extra model call solely to obtain a receipt. The model does not supply authoritative ModelCall/attempt/source identities.
- Host binds each assistant tool invocation to the persisted response which contains its exact tool ID/name/arguments, then to that ModelCall's actual request. Validate execution, receive evidence, full guidance ID/hash/text in the trusted injected envelope, and receipt idempotency. `onPrepared` alone is not adoption. Text mentioning an ID, a fabricated tool ID, checkpoint, message_end or a preview does not qualify. Saved-response replay can only reproduce receipts for instructions present in that saved request.
- Tool order is not processing evidence: before a success or side-effect gate, validate all guidance_receipt calls anywhere in the same complete persisted response against the actual originating request and host provenance. Use one validator for ordinary receipt execution and response-wide resolution; reject contradictory/invalid receipts without fabricating adoption. A valid receipt after submit_result or a write/bash in the batch still counts. Build pending receipt mutations first; at the domain success boundary commit applicable receipts and the result/settlement atomically. For effects, commit validated receipts before effect dispatch and recheck current guidance/conflicts. Later execution/replay of those receipt tool calls is idempotent. An unresolved conflict creates its explicit wait and prevents success/effects; success-before-ADOPTED in the same response must not falsely fail.
- Keep original guidance exactly once in the live context: the dispatch packet carries instructions not already represented in the resumed context, and running deliveries use trusted steered messages. Remove the proposed repeated active-requirements packet and do not append a per-request full-text reminder. Retain prior Master text and receipt outcomes in context; no Task history truncation/compaction is introduced. If capacity is exhausted, preserve the instructions and report capacity blocking. On recovery use the actual frozen request and re-deliver only missing IDs after its turn. A transcript/checkpoint proves reception, not model consumption: only persisted ModelCall requests establish consumption coverage. Deduplication recognizes host-recorded injection provenance/positions and hashes, not arbitrary quoted JSON or text from materials. Prompt plus structured effective_requirements/conflict receipts enforce precedence without replacing the originals with a model summary.
- Executor prompt requires reconciliation with all effective Master restrictions, reports conflicts, and allows later explicit Master correction without treating Main as equivalent authority. The receipt must state the resulting requirements, not just “latest ID read”. Host checks source precedence and provenance; it cannot mechanically prove arbitrary natural-language compliance. GUIDED is the executor's attributable adoption claim; acceptance separately checks behavior.
- A known conflict or CANNOT_APPLY blocks success and new conflicting side effects. Always enter an explicit WAIT_DECISION with one deduplicated DecisionRequest and coordination event; host requires MASTER when a Master restriction is involved, otherwise uses the ordinary decision path. Do not leave the model repeatedly attempting success until MODEL_CALL_LIMIT. A later receipt can resolve it only with actual new guidance/answered decision evidence from this execution; changing an explicit Master restriction requires a new MASTER instruction or MASTER answer, not a Main answer. Preserve prior outcomes and resolution references. A read marker never resolves conflict. Main can clarify its own suggestion without overruling Master.
- Add optional `DecisionRequest.required_answerer = MASTER` and guidance-conflict references, selected by the host when a decision concerns a Master restriction; absent means the existing ordinary-decision behavior. Enforce it inside the shared `answer()` domain method before any ANSWERED/READY mutation, for API/Main/replay paths; return `DECISION_MASTER_REQUIRED` to Main. A model cannot downgrade the restriction. Public decision/attention DTOs expose it; the existing question/attention rendering displays “Master answer required” in #103 as a narrow integration, not the #106 /guide UI. Main may coordinate but cannot clear this wait. Receiving further guidance while WAIT_DECISION does not implicitly answer it.
- Main prompt explains guide versus continue/cancel, this-execution-only scope, informational copies and no resend/reply unless coordination is required. Final TaskResult detail and existing RESULT feedback include a bounded guidance outcome/reference summary so Main judges the updated work. Historical guidance in continuation material is provenance, not automatic live authority in a new execution; no implicit cross-round carryover or task-plan mutation.

## 5. Delivery, old tools and recovery

1. Persist acceptance as entry into the durable guidance queue; delivery is a required obligation, not best effort. For an eligible running Agent, both API and Main entrances call steer synchronously immediately after the acceptance commit inside the same admission call, before returning or awaiting; never defer to the scheduler pump. Waiting or recovery-held delivery follows its explicit phase rules. A crash between commit and steer is repaired from the durable queue. Keep execution-scoped pending/active indices and reconstruct them from journal. RECEIVED is preserved historical context evidence; whether delivery is needed for the current attempt is checked independently against its actual persisted request/context provenance. Do not assume historical RECEIVED means current model consumption.
2. Use explicit delivery paths, with `steeringMode: "all"`:
   - Fresh dispatch or ordinary resume without recovery_call_id: place held instructions missing from saved context into the existing dispatch packet alongside operation and answered-decision evidence. Do not also steer them.
   - Normal running Agent: enqueue each new instruction once through steer. Take the immutable guidance acceptance-sequence snapshot BEFORE the steering poll that builds the next fresh request: for initial non-recovery dispatch, synchronously before creating the dispatch packet/calling prompt; for subsequent turns, in finishTurn immediately before releasing held instructions and allowing Pi to poll. This precedes all message emits/prepareRequest awaits. Do not assume awaited hooks cannot interleave with another Agent’s ready microtasks. Verify coverage in prepareRequest and again against actual request bytes before transmission. Persist the captured cutoff as metadata in the first PREPARED ModelCall commit for the logical key; transport retries/restarts inherit it, never resnapshot. The first resumed frozen call is exempt from current-queue coverage and uses its original stored cutoff (legacy calls use their actual frozen request as coverage), then finishTurn establishes the next fresh-turn cutoff. Every still-applicable instruction accepted by that boundary must be represented in that request with trusted original text, without a duplicate full-text packet. The cutoff defines the minimum set that MUST be included, not whether the model actually saw a later arrival. A post-cutoff arrival may be picked up by Pi’s upcoming poll and included in this very request. Gate each instruction by actual inclusion in the persisted request: included instructions use the ordinary receipt/effect rules and immediately fail a premature success attempt without a valid disposition; only absent instructions block old tools/success nonterminally and remain due for the next eligible fresh turn. Do not advance the cutoff or remove obligations on restart/retry. Frozen-call recovery remains the separate path below; it cannot certify new guidance.
   - Frozen-call recovery: hold all newly pending guidance OUTSIDE Pi's queue and context until the recovered assistant turn (response plus tool results) has finished. Set a recovery-phase flag before exposing the Agent; admission during this phase persists only. Never steer before `agent.continue()` or during its initial steering poll/prepareRequest. In finishTurn, after the recovered normal response/tool batch is appended, release held guidance in order and continue if the execution is still runnable. A text-only recovered response must also allow this next turn. If it ended in WAIT_AUTH/WAIT_DECISION/UNKNOWN/terminal, retain pending guidance for that state's permitted later boundary. Error/abort remains Pi's hard exit, with honest failure/unprocessed handling.
   - Guard recovered old tools against all newly accepted instructions even while those instructions are held outside context. The transcript must not place a new instruction before an assistant response generated without it. Frozen request/budget/logical key/response remain unchanged. Check adoption only against the persisted request, never apparent transcript order.
3. Bind old/new tool batches to their real ModelCall snapshots. Before each tool, block actions planned without newly accepted guidance using a nonterminating `GUIDANCE_PENDING` result; drain the queued guidance and obtain a fresh normal planning response. Allow validated guidance_receipt and necessary read/decision paths from a request that includes the guidance. Before new side effects require valid adoption and no unresolved applicable conflict. FAILED submission/cancellation/expiry can settle unprocessed guidance without adoption. This is not a blanket tool lock.
4. Repeat the gate at actual effect start, after asynchronous preparation: immediately before file write dispatch/start and, for shell, before the launcher's start barrier. The synchronous final check and start/commit establish order relative to admission; work already started is not retroactively undone. Persist provenance or conservative legacy treatment for pending Operations. Preserve unknown-effect handling, process-stop checks and authorization/resource revision checks. At the shell barrier, request STOP and reuse the existing explicit not_started→NOT_APPLIED path; wait for actual no-start and process-stop evidence, distinguish guidance deferral from execution cancellation, then replan. Missing no-start proof stays UNKNOWN. For writes check immediately before auth.dispatch/start; no retroactive suppression after the start boundary.
5. WAIT_AUTH follows the issue's existing wait semantics, not automatic withdrawal:
   - With a PENDING authorization, guidance stays SENT/held; leave the operation and authorization pending and the execution in WAIT_AUTH. It does not authorize, reject, or set READY.
   - A real rejection/revocation retains today's `CANCELLED_OPERATION_ON_RESUME` FAILED result, preserving decision evidence and settling unresolved guidance as UNPROCESSED. It never becomes a supersession reason and is never ignored by recovery. Cancellation is always available; “reject and continue working” is outside this issue.
   - After legitimate approval clears the wait, inspect all never-started AUTHORIZED operations before applying any, and repeat the check inside the resume loop at EVERY operation boundary, synchronously immediately before auth.dispatch for both writes and shells. Guidance may commit while the previous effect is awaited. On a hit, retire the current and all remaining obsolete never-started AUTHORIZED operations using the existing AUTHORIZED→CANCELLED transition with immutable `SUPERSEDED_BY_GUIDANCE` provenance and host-proven never-dispatched evidence; stop applying and continue to replan. Return an explicit guidance-deferred outcome to the resume caller, never throw a guidance block into the dispatch FAILED catch and never reuse a pre-loop check as clearance. Only guidance arriving in the asynchronous shell launch window uses the distinct not_started→NOT_APPLIED path in §5.4. Ignore only host-proven supersessions in the generic cancellation-on-resume branch; actual denials/revocations/rule failures still fail normally. No new Operation state is needed. The associated old grant stays auditable but cannot dispatch a CANCELLED operation.
   - Then create the normal new Agent/recovery turn with both old operation/approval evidence and guidance. No approval reuse, even for identical reissued arguments: a replacement is a new operation and passes ordinary authorization (including existing applicable rules). Never spoof a fresh model tool intent to retry a superseded old response; old intent replay returns its original retired operation. All never-started obsolete approved operations follow this uniform rule. Operations planned by a real request containing current guidance follow normal adoption/effect gates.
   - The existing authorization/attention detail exposes a narrow warning when newer guidance is pending: approval will retire the obsolete operation and replan rather than run it; denial retains failure. Public projection presents pre-dispatch cancellation and proven launcher-window NOT_APPLIED consistently as “retired by guidance”, while retaining their distinct underlying evidence. This is a narrow #103 integration, not the #106 command UI.
   - Already dispatched/unknown effects are not classified as never-started by an absent receipt. The shell launch-barrier case uses its distinct observed not_started result (below). With no new guidance preserve prior behavior.
6. WAIT_DECISION: persist/receive without answering or setting READY. Once legitimately answered, resume with both answer evidence and guidance. RESULT_UNKNOWN remains held until existing reconciliation, with no automatic replay. Cancellation always takes priority.
7. Success/admission linearization: the final synchronous domain check and commit in `finish(SUCCEEDED)` examine the current accepted sequence, all applicable dispositions and cancellation state; include result evidence and guidance settlement in the same journal transaction. If guidance commits first, old success is refused; if success commits first, new guidance is rejected. Recheck after any awaited artifact/effect preparation. No separate “check now, commit later” window.
8. Failure/cancel/expiry settle unresolved guidance and execution/result atomically, preserving prior RECEIVED/GUIDED history and unknown-effect constraints. This includes guidance accepted/steered after the Agent loop has ended without submit_result: the MISSING_STRUCTURED_RESULT FAILED commit atomically closes it UNPROCESSED. Add recovery repair for legacy or interrupted terminal settlement. No cancelled execution is revived.
9. **Master-confirmed mandatory consumption, no refusal counter or three-attempt grace:** accepted guidance must enter the next eligible fresh request as defined by the immutable preparation snapshot above. Check actual persisted-request coverage; merely steer/checkpoint/PREPARED never proves successful model consumption. Never send a fresh request silently omitting an instruction due at its boundary; failure to satisfy this host invariant fails the execution with GUIDANCE_NOT_PROCESSED (subject to process/unknown-effect safety), preserving the missing IDs and underlying cause. Ordinary provider retry of the same frozen call retains its obligation and existing retry policy; it is not a new chance to omit guidance.
   - A successful model call carrying guidance may perform necessary reads and then provide a validated structured disposition in a later ordinary response which also contains the original guidance. Master explicitly chose this completion boundary, NOT a rule requiring a disposition in the first response. No acknowledgement-only model call is added.
   - If submit_result(SUCCEEDED) is attempted with guidance that was present in its generating request but still lacks a valid persisted processing disposition after response-wide receipt validation (including receipts later in that same response), fail immediately with GUIDANCE_NOT_PROCESSED, atomically settle outstanding guidance and emit one deduplicated failure report. No three-response counter, reset or grace retry. Evaluate obligations per guidance ID: a newly arriving instruction cannot excuse an older included-but-unprocessed instruction.
   - An old in-flight/frozen response that never contained a newly accepted instruction is blocked nonterminally with GUIDANCE_PENDING so the first eligible new turn can consume it. It cannot report success and is not automatically failed merely for having been generated before admission. A new instruction arriving after a request snapshot is handled by actual request inclusion, not by cutoff alone; if the upcoming poll included it, missing disposition at success fails immediately. The final domain success gate rechecks all acceptance/disposition evidence before commit.
   - Valid CONFLICT/CANNOT_APPLY is a processing conclusion, not GUIDED or successful completion; keep the existing explicit coordination/Master-decision path and prohibit success until resolved. A read marker is not a processing conclusion.
   - Authorized waiting remains waiting; active cancellation remains CANCELLED and expiry remains EXPIRED, each with honest UNPROCESSED closure. Do not reinterpret cancellation as failure or run a model just to consume after cancellation. Existing provider/capacity/MODEL_CALL_LIMIT failures retain their primary cause and also settle every unprocessed obligation visibly. Unknown effects retain RESULT_UNKNOWN/process safety until reconciliation; guidance cannot erase or replay them. A queue entry cannot disappear or allow an otherwise successful execution to complete without processing.
   - Keep the existing per-dispatch 20-model-call cap and bounded provider retry policy, with near-limit arrival tests. No new timeout, unlimited steering loop or relaxed capacity guard. Failure retains exact accepted text and never fabricates GUIDED.
