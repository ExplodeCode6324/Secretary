## 2. Preview identity, lifecycle and durable handoff

Extend the internal preview envelope with a discriminated source (`MAIN` or `TASK`), Core runtime/preview epoch, task_id/execution_id for Task, ModelCall ID, transport_attempt, dispatch attempt provenance and a monotonically increasing preview revision. Task identity comes from trusted runner scope and actual ModelCall, never provider text. Registry handles are bound at start; events with an old identity/epoch cannot update another attempt or resurrect an ended entry. A retry creates a distinct ModelCall entry; do not append its text to the failed attempt. Replayed RESPONSE_SAVED is projected as saved, never as a new live generation.

The registry is disposable and per Core runtime. It does not write token events to journal, add Inputs/Feedback, modify model context or set Guidance RECEIVED/GUIDED. Observe and display errors cannot change execution outcome. Leave the pinned Pi version/loop and all #103 guidance gates intact. Add no Task prompt/tool text for preview: the #103 continuation budget has little margin.

Current Task transport already retains unconsumed provider events until result() completes; the observe path instead pushes every consumed delta into a second unconsumed replay queue. Task observation must drain the provider and avoid retaining that second queue, reducing existing transient cost. Drain Task provider events into the bounded display observer, discard intermediate transport events after observation, and return the existing done-only savedResponse(complete) only after RESPONSE_SAVED commits. The pinned Agent already supports this replay. Preserve Main's current consumer semantics unless a separately tested shared simplification is required. Also preserve Task's existing thrown failure/classification path: adding observe must not enable the Main-oriented diagnostic error-stream branch just because observe is present. Test normal and resumed success, toolUse, length, error, abort and retry with observation both enabled and disabled; request identity, final content, tools and domain outcome must match.

At Task message_end correlate only a response proven to be the actual saved ModelCall output. Clear any pending display token before each durableStream invocation, including before capacity/call-limit/guidance/recovery checks. A host-only successful-save/replay callback sets a one-shot token with the actual call ID and exact saved response; message_end consumes it only when the assistant message exactly equals that response (structural equality, not similarity). Consume/clear it once, clear before the next invocation and on the catch path, and release it at runner-lifetime teardown. It MUST survive durableStream returning: do not clear it in transport finally or promise-finally, because Pi emits message_end only after awaiting the returned stream. onPrepared remains useful for Guidance but is NOT sufficient display provenance. Capacity blocked, MODEL_CALL_LIMIT, GUIDANCE_NOT_PROCESSED, recovery mismatch and other Pi-generated synthetic error messages retain independent event identities and cannot erase a preceding real message. Validate TASK purpose and exact task/execution scope.

Use existing journal metadata: set causation_id to the ModelCall ID on correlated agent.message and model.response (the latter is already committed with RESPONSE_SAVED); include the related ID in related_object_ids if useful. No new OperationLogRecord field or payload wrapper is needed. Keep Agent messages and event payloads unchanged. Old events with null causation stay readable under event IDs. Non-assistant user/tool messages retain event identity and are never merged just because they share a call. Existing frozen-call replay may repeat tool-result events; preserve those facts and note this existing limitation, without deleting them heuristically under #104.

For new assistant messages, expose a canonical display key derived from execution + ModelCall, alongside source_event_id, model_call_id and attempt metadata. Keep historical event-ID content lookup compatible. The pending preview and finalized message use the same display key; durable agent.message wins. Between RESPONSE_SAVED and agent.message, expose the persisted ModelCall response as a saved fallback with that same key, and later replace its source with agent.message rather than rendering both. This covers a crash after response save but before Agent/checkpoint commit. A rebuildable per-execution call/message index links these sources; never scan every ModelCall for a content query. Do not fabricate agent.message/checkpoint or replay tools for display.

Show distinct presentation facts: generating, response saved/awaiting message, continued, completed, length-truncated, interrupted/failed attempt. A transport failure is not automatically a Task failure: retry may continue. Final execution state, unknown effect and cancellation come from durable domain records. Partial preview loss/disconnection is only a display gap. On Core restart the old epoch's previews disappear, durable responses/history restore, and an unsaved partial has an explicit interruption/gap notice rather than a false completed body. Late saved/incomplete snapshots cannot replace a durable message or a newer revision. A display truncation badge is distinct from the provider's length stop reason; full saved text remains available after preview cap.

## 3. Bounded streaming and reconnect protocol

Keep Main's existing behavior compatible, and expose Task preview metadata through the generated API/SSE contract. Use a separate `task_transient` SSE event so Task metadata is never dropped with the existing oversized Main-preview/activity frame. It carries bounded metadata/invalidation for Task (identity, version, status, truncation, epoch), not a full copy of every Task's 32K text. Main text previews can also be invalidated through the existing content path; preserve current clients' contract or version/add fields explicitly. No full reasoning is broadcast. Task detail/content reads honor the existing CoT flag, redaction and safeText rules; do not expose signatures or hidden reasoning. Any visible thinking is only what existing provider display rules already allow.

Provide a bounded Task-execution preview snapshot/read path, either as an additive facet of messages and content or a narrowly scoped preview query. It returns current membership plus epoch/version and is subject to the same browsability, recent-three and ownership checks. SSE is a sampled complete membership snapshot with revision watermarks, or includes explicit removals; absence must not be mistaken for business failure. Subscribe/reconnect by durable cursor, fetch current snapshot/history, then reconcile subsequent invalidations with epoch and per-entry versions. Resolve races with dirty/re-fetch flags, not by trusting arrival order. Each transient channel has an independent sampler/watermark and budget; a new connection gets its current state even if the durable cursor has not advanced. Test three simultaneous 32K CJK Main previews (which can overflow the legacy combined frame) while Task metadata/content still advances. Preserve follow intent across SSE reconnect, but never retain an old runtime's live bytes as current.

Use these initial ceilings (implementation may lower them based on measured cost, not raise without recording evidence): eight Main entries as today; up to 32 Task entries; 128 blocks and 32,768 UTF-16 units per entry; Task-registry aggregate text <= 1 MiB UTF-8; transient metadata frame <= 64 KiB; existing 512 KiB connection/5 s drain/8-client limits unchanged. Evict finalized/old inactive entries first, then oldest live preview if needed, exposing a display-eviction notice on affected detail; execution and durable response are unaffected. Bound client transient cache to the selected Task's recent three executions, with the existing 200-item / 4 MiB history/body envelope, accounting for previews and rendered-entry references rather than keeping a second uncharged copy. Keep surrogate-safe slicing and Unicode rendering.

Coalesce registry-to-SSE and visible content pulls at about 100 ms. Maintain one in-flight + one dirty refresh per selected execution, under RemoteViews' existing two-read concurrency limit; stale jobs carry selection/epoch/CoT/follow generations and cannot overwrite newer state. A delta updates only the affected visible preview/body and render entry. Background Task metadata does not refresh Main history or reread the Task root list. Durable task/control changes use targeted invalidation; a completed assistant body triggers one keyed reconciliation. Indexed lookup work is proportional to new frames + requested rows/bodies, not unrelated total history or every message in the execution on each delta. Build message ID/sequence/tail and call-handoff indices once from retained journal frames, then advance incrementally. Reuse existing body fragment readers and page byte limits.

## 4. Explicit Task following and true latest windows

Add a generated query option such as `position=latest` on `/task-browser/:task/executions/:execution/messages`, mutually exclusive with cursor/message_id. Return the newest bounded window in chronological order, retaining the newest items when the byte budget trims it, with valid before/after cursors. Default history query behavior remains compatible. Tail lookup uses the execution index, not walking every old page. Body-tail reads likewise reach the actual tail of a very long message. No change to recent-three eligibility or archival/retention semantics.

Proposed minimal #104 UI: `/follow` in Task ordinary detail input means “return to latest and keep following” for the execution section containing the current reading anchor, or, when the anchor is outside execution sections, the newest displayed execution. Resolve from the last accepted detail snapshot at explicit submission, immediately freeze the exact ID and show the selected target; subsequent refresh never re-resolves it. `/follow <execution_id>` explicitly selects another displayed execution, with contextual ID completion and status labels. No implicit title or relative round parsing before #105. Reject no-execution/outside-detail/non-AGENT targets without falling through to another target; read-only navigation creates no business input and preserves the two ordinary drafts. #105 may add human-friendly name/round affordances later without changing the internal exact target. The matching `/follow off` action or ordinary reading turns follow off; matter/authorization input states do not execute these reading commands. The detail header shows following/paused and the exact target, never just an unqualified “latest”.

Follow state is local `{task_id, execution_id, intent_generation}` separate from the reading anchor. Target is frozen until a new explicit action. In a document containing three execution sections, scroll to the target section's last content row, not the global document end; prune/hydrate around that target. At terminal state show the final tail, then stop with a clear finished status. A new execution does not steal follow. If target leaves the recent-three/browsable range, stop with a notice; retain the existing honest anchor fallback rather than silently follow another round.

PageUp/PageDown, arrows entering reading, wheel, pointer press/drag/selection, explicit history/body paging, back/open-other-task and Main/Task switch stop following before navigation. Scrolling manually to bottom does not enable it. Background output does not enable it. Resize and CoT toggle preserve valid intent/target; stale old-mode reads are discarded. SSE/Core reconnect revalidates exact target and preserves intent if still eligible; restarting the TUI need not persist follow as a user preference. Selection freezes selected rendering/anchor using existing view mechanics; refresh must not move copied text underneath a drag. Hook Task's onReading/onPointerRead/selectionActive in the existing view, with programmatic follow positioning distinguished from a reading action to avoid self-disabling. Keep Main follow semantics, matter priority, Ctrl+C and editor behavior unchanged.

## 5. Main routing and authorization notification

Use a mechanical routing table, not a classifier model:

| Fact | Destination / dedupe identity |
| --- | --- |
| Tokens, text, tool transcript, ordinary progress, normal Guidance milestones | Display/history only; no new Main Input/PROGRESS Feedback. |
| Master direct Guidance original | Existing #103 atomic informational Input once; no resend on stage changes. |
| Guidance conflict / cannot apply | Existing #103 DecisionRequest + stable Feedback, preserving required_answerer=MASTER when applicable. |
| Ordinary question, unknown effect, final result/failure | Existing durable decision/operation/result control chain; use the originating fact's stable identity and preserve existing failure/attention semantics. |
| Authorization required | New typed AUTHORIZATION_REQUIRED Feedback keyed by authorization_id; Main may coordinate, never approve on Master's behalf. |

For a valid Task/Execution scope, create the new authorization Feedback in the same transaction as PENDING AuthorizationRequest + WAIT_AUTH Operation in authorization.prepare. Cover both AGENT and PROGRAM Task authorizations. World/Main-only scopes without an Execution keep their current path; do not fabricate Task IDs or send them through Task Feedback. Payload references exact task/execution/operation/authorization and the existing display_ref; no extra copy of secrets or capability/grant. Add optional authorization_id to Feedback and its Main Input envelope and add the kind to the source schema; regenerate unions/state/API docs and audit every consumer (timeline, push, retention, recovery, Main). Before Feedback→Input delivery, synchronously require all of: AuthorizationRequest.state=PENDING and not expired; its Operation.state=WAIT_AUTH; its Execution is neither terminal nor cancel_requested. Validate ownership/references as usual. Do NOT require Execution.state=WAIT_AUTH: prepare commits the request before runner changes execution state, and crash recovery may leave that same live wait in READY. The after-authorization-commit crash test must yield exactly one Input after restart, never permanent suppression of a valid wait. An already resolved, expired, cancelled or otherwise nonactionable request produces no new Main Input. Atomically settle its queued Feedback in an explicit terminal `SUPPRESSED` state with reason/time, input_id=null, retaining the original authorization fact; add only QUEUED→SUPPRESSED to `src/state_machine/catalog.json` and audit all terminal-state consumers. In particular `retention.ts` currently blocks retirement for any Feedback != HANDLED; count SUPPRESSED as settled there and test eventual retirement. Update generated contracts/docs from source. Never pretend it was DELIVERED/HANDLED. If still actionable, create Input + DELIVERED atomically as today. A later resolution after Input commit does not retract that Input; Main must read current state before coordinating. The notification is neither approval nor a guarantee it remains pending. One-time rules and all API approval authority remain unchanged.

Reuse #103's deterministic Feedback-ID pattern. Keep feedback→Input and DELIVERED state atomic. Repeated prepare/recover/pump/UI refresh never creates a second input for the same authorization. Recovery reconciles pre-upgrade active pending authorizations missing this Feedback through a scoped index, once at startup plus incremental updates; do not replay every old resolved authorization. New transactions cannot fall into that gap. A SUPPRESSED identity is settled and never requeued on refresh/restart; another authorization uses its own ID. For ordinary questions/results use stable decision_id/result_id keys and create their Feedback atomically with the authoritative fact where possible, retaining recovery repair. At this baseline an Execution has at most one RESULT_UNKNOWN episode: recovery does not resume it and settlement ends it as FAILED. Keep this behavior. UNKNOWN is one notification per execution episode, not per affected operation. Derive the deterministic identity from execution_id alone, because this execution has only one unknown episode; this avoids replaying historical Execution snapshots. Create UNKNOWN atomically only while actual unknown operations exist or process shutdown remains unconfirmed. A recovery-only temporary RESULT_UNKNOWN with no unknown effect must settle to FAILED with only RESULT feedback. Pass the originating summary/detail into the atomic producer so shell receipts, program output and runner errors survive. Recovery repairs a missing notice for the same genuine unknown condition. Include all affected operation references as evidence, not separate wakeups. During upgrade, ANY existing legacy UNKNOWN Feedback for that execution already covers its only episode, regardless of its random ID or missing operation refs; retain it and do not add a new-key duplicate. Do not add future resume/multiple-episode behavior under #104. Narrow fixes required to guarantee delivery once per originating fact belong here; do not create a parallel notification bus. Guidance conflict identity is left intact. Do not promise exactly-once model execution: prove durable input dedupe and existing Main batch replay semantics.

Source audit finds no current runtime PROGRESS producer; the enum is retained for stored-record compatibility. Current ordinary transcript is already display-only; do not add a feedback emitter to streaming. Existing historical PROGRESS/accepted Input records are not deleted, rewritten or migrated speculatively. Tests assert that all new ordinary output/stage paths create no PROGRESS or Main Input. No model invocation is added for routing or receipts. #103's final guidance outcome summary stays visible to Main.
