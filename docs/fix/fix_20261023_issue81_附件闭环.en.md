## 3. Proposed public contract

All routes retain the existing authenticated loopback local-owner/data-domain boundary and `/api/v1` prefix. Source paths never go through a shell. Remote callers and task-only clients do not gain a new supported owner credential path.

| Operation | Contract |
| --- | --- |
| POST `/attachments/import` | JSON `{request_id, source_path, expected_sha256, expected_bytes, name}`. UUID request; absolute path (max 4096 UTF-8 bytes, no NUL); lowercase 64-hex digest; positive decimal-string byte count; display-only basename (1–255 characters, no separators/control characters). Return existing 202 Receipt, resource ID `AttachmentImport`. |
| GET `/attachments/{id}` | Ready attachment's minimal metadata: attachment_id, import_request_id, name, media_type, decimal-string bytes, sha256, integer width/height, created_at, availability (`available` or `unavailable`). No path/base64. Unknown ID 404. |
| GET `/attachments/{id}/content` | Authenticated immutable original bytes, checked length/hash before headers. `application/octet-stream`, attachment filename*, Content-Length, strong digest ETag, `nosniff`, no-store; no path exposure or inline execution. Runtime missing/corrupt content 410; after restart, missing/truncated referenced objects fail Store.open under the existing invariant (section 5a). Read-time failure uses `ATTACHMENT_UNAVAILABLE`. No range support in v1. |
| POST `/inputs/{id}/withdraw` | Explicit owner-only withdrawal with new command request_id and expected_revision; only attachment Inputs, while quiescent and with no unresolved effects. Exact rules in section 5a. Not a running-generation stop endpoint. |
| Existing GET `/requests/{id}` | Authoritative import progress/result and stable attachment ID after COMPLETED; FAILED supplies a stable code. Only COMPLETED authorizes source deletion. Imports remain QUEUED while pending; generic RUNNING/UNKNOWN handling is not used. |
| Existing POST `/messages` | Preserve required `text`, allow `""` only with 1–4 valid ordered `attachment_ids`; optional list, empty list equivalent to no attachments for internal text hash only. Reject duplicate IDs. Text must be exactly empty or non-blank (whitespace-only rejected even with images). Nonempty text keeps current size rules; both blank text and no attachments fail. Text is emitted first if present, then images in declared order. |

Import request_id and message request_id MUST differ (same global request namespace). Changing any submitted field, including source_path/name/digest/length/order, with the same ID conflicts. Public fingerprint continues to use the original complete body, so omitted vs explicit empty lists can still conflict on public retries; clients freeze exact JSON semantics. Different import IDs for identical bytes create distinct attachment identities and may share CAS bytes. Reusing one ready attachment across different messages is allowed; bindings live on each Input, not a mutable single-message pointer.

A 202 receipt means accepted import work, not transferred content. The client may delete its owned source temporary file only after GET requests reports COMPLETED and returns the ready attachment identity/metadata. Source files are never deleted by Core. After this point source deletion/changes do not affect import retries, sending, history or restart. Before this point the client preserves its snapshot. A crash before a copy completes can return explicit source missing/changed failure, never silently read different bytes.

Proposed errors include INVALID_REQUEST/REQUEST_CONFLICT, ATTACHMENT_SOURCE_UNREADABLE, ATTACHMENT_SOURCE_CHANGED, ATTACHMENT_TYPE_UNSUPPORTED, ATTACHMENT_INVALID_IMAGE, ATTACHMENT_TOO_LARGE, ATTACHMENT_CAPACITY_FULL, ATTACHMENT_NOT_READY/UNAVAILABLE, ATTACHMENT_MODEL_UNSUPPORTED and CAPACITY_BLOCKED. Schema/auth/id-conflict errors occur before admission. Async validation failures become durable FAILED import receipts. Message admission failures produce no Input and no accepted message receipt. HTTP mapping and retryability are documented/tested; unknown IO outcomes preserve the pending import identity rather than promise no effect; import ApiCommands do not enter generic UNKNOWN.

## 4. Storage, validation, capacity and crash ordering

First formats: static PNG and JPEG only, determined from bytes and fully decoded; filename/extension/client MIME is not authority. Add pinned `sharp` dependency and lockfile for validation, with `limitInputPixels`, fail-on-invalid/truncated decode, single-frame requirement and no output rewrite. Reject APNG (parse PNG chunks, reject acTL/fcTL/fdAT), JPEG MPO (MPF marker), trailing bytes after parsed PNG IEND/JPEG EOI, GIF/WebP/AVIF/HEIC, SVG, PDF and other formats explicitly in v1. Parse JPEG marker/entropy framing; do not mistake embedded EOI bytes in metadata for the terminal marker. Original bytes, including EXIF metadata such as GPS if present, are sent unchanged to the chosen provider; document this without silently stripping content. Original accepted bytes remain immutable; no silent conversion/resize. Validate sharp's actual PNG/JPEG behavior in the implementation; animated PNG detection must not depend only on first-frame decoding.

Limits proposed for coordinator approval: 5 MiB per file, 4096 per side and 4,194,304 pixels, 4 attachments / 10 MiB original bytes per message; 1 GiB logical import reservation budget and 10,000 import identities per Core data domain. Same-content new identities are charged separately (conservative accounting; physical CAS can dedupe). One bounded import worker at a time. Limits are named validated Core configuration with these defaults and exposed in capability metadata. They are import ceilings, not a promise that every imported image fits the model context.

Filesystem read: open absolute source using descriptor APIs with O_NOFOLLOW and nonblocking where supported; fstat regular-file check before bounded reads; reject directories, final symlinks, device/FIFO/socket, unreadable/zero files and bytes beyond max. Allow symlinked ancestor directories (macOS /var and /tmp are normal examples); do not reuse scopes.noLinks. Only the final component is O_NOFOLLOW; descriptor identity and expected digest/length are final authority against replacement. Compare fstat identity/size/time before/after; reject a mutation observed during reading. Hash exactly the bounded buffer to be copied. This addresses Chinese/spaces/metacharacters literally, without invoking shell. Source path is private command data, omitted from ordinary metadata/errors/log text.

New records (retain separate Import to make durable quota reservation and invariants explicit): `AttachmentImport` (immutable request identity, expected digest/length, reserved bytes, state PENDING/READY/FAILED, stable allocated attachment ID, sanitized failure code); immutable `Attachment` (owner/data-domain association through the Store, import request, name, verified format/dimensions, ObjectRef). New Input optional ordered immutable attachment snapshots contain IDs and verified immutable refs/metadata, plus versioned full-content digest. Server resolves refs; clients cannot submit CAS paths or forged metadata. Extend schema unions, record/state handling, Store replay identity/ref validation and generated internal types, without rewriting old records.

Crash-safe sequence:

1. Validate schema/global ID namespace and capacity (including API-to-internal Host reuse in both directions), allocate stable IDs, then atomically journal `AttachmentImport(PENDING)` reservation + ApiCommand(QUEUED). Admission is synchronous; never hold `withAdmission` across await. This reserves quota before any attachment bytes are written. PENDING has plain expected_sha256/expected_bytes fields, never an ObjectRef-shaped expectation. Bound concurrent reservations before scheduling work.
2. The attachment-specific worker reads/validates bounded bytes (or verified previously written CAS with expected digest), fully decodes within pixel/memory limits, puts original bytes in existing CAS and fsyncs. At most one file-sized in-memory buffer plus bounded decoder output; no general object scan.
3. One journal frame commits immutable Attachment + Import READY + ApiCommand COMPLETED/result/resource IDs. Only this is successful content handoff. A crash after CAS write but before frame commit is recovered from the reserved expected CAS identity, validated again, using the same allocated ID. A crash before CAS exists can re-read only matching source bytes; mismatch fails.
4. Exclude command `attachments/import` from BOTH the constructor generic RUNNING/QUEUED loop and command() generic queued scheduling branch. Schedule it solely in the serialized import worker; ApiCommand remains QUEUED during all PENDING work, and moves directly to COMPLETED or definite FAILED in the final domain frame. No import enters generic RUNNING/UNKNOWN/INTERRUPTED_DISPATCH. Startup asynchronously resumes its PENDING records independently. If CAS/journal integrity cannot be resolved, keep QUEUED with a bounded diagnostic/retry pause and retained reservation (no success claim), or fail closed with Store corruption. Do not delete possibly referenced CAS. Generic command recovery remains unchanged.
5. Implement unlink-on-write-failure inside Store.put for precisely the temp filename allocated by that call, never hash-named shared objects; record/fsync write failures. A definite validation/source failure before any CAS write atomically records FAILED and releases its byte reservation (identity still retained/count-limited). Once CAS may exist, retain the reservation even on failure; v1 has no automatic reclamation. Disk full/fsync/journal failure must not produce a successful receipt. Quota and temporary peak overhead are documented separately from a whole-store disk quota.

READY and unbound content/reservations are retained on restart, no age expiry. Capacity checks include pending reservations; replay rebuilds accounting from durable records. Full capacity rejects new imports without deletion. Changes in configured quota below current usage block new reservations but preserve existing content. Per-message caps and model checks still apply after import.

Message admission resolves all ready attachments and verifies all bytes before any mutation, verifies model capability and standalone input budget, constructs ordered immutable Input binding, then atomically commits Input + input.accepted + internal receipt + ApiCommand through existing admission. Existing accepted message retries return original receipt even if source vanished or configured model changed; never rebind. Concurrent same-ID submissions cannot double-import or double-admit.

## 5a. Storage and failure design

Persist image-bearing aggregate request/context/payload evidence in a versioned dehydrated CAS envelope: replace only recognized image leaves with verified immutable binary ObjectRefs; keep structural order and all non-image fields. Include exact original serialized-body SHA-256 and encoding version. Hydration must reproduce the exact original JSON bytes/hash, including data-URL MIME/prefix, before use. Unsupported encodings/hook transformations fail, not normalize silently. Preserve legacy raw JSON reads and current logical request-key semantics; do not key retries by new physical envelope hash. Use shared explicit encode/decode helpers for ModelCall.request, model.payload, model.capacity_blocked, and aggregate settings/summary/extraction evidence. Per-message CAS putMessages remains deduplicated; no need to change every historical record. Audit every reader of these ObjectRefs. The canonical Attachment retains its normal directly verified ObjectRef; envelope hydration validates all referenced image leaves and the exact-body hash; missing/truncated attachment bytes remain store corruption on replay. Five-MiB resident-image repeated-call fixtures must show CAS growth proportional to changing text/metadata, not calls × base64 size; rehydration equals captured provider-body digest for both adapters. This is required attachment correctness/storage containment, not general history optimization.

Store corruption boundary: while running, any attachment read detects missing/truncated/hash-mismatched data and returns unavailable/no-send. On reopening, missing/truncated ObjectRefs fail Store.open under current invariants; do not promise a 410 server when the Store cannot open. Same-length corruption can pass structural replay but must fail hash validation at use/read. PENDING expectations are not refs. No weakened Store invariant, repair service, general CAS deletion or silent damaged-content fallback is introduced.

Withdrawal proposal (new narrow domain action, for coordinator approval): add terminal Input state WITHDRAWN, not HANDLED, with immutable withdrawal reason/time/command evidence and `input.withdrawn` event. Only attachment Inputs in ACCEPTED or CLAIMED may be targeted through POST inputs/{id}/withdraw with new request_id and expected_revision; stale revision fails, same command replays. Ordinary text Inputs retain their existing state machine. New non-recovery scheduling takes attachment Inputs one per handling loop (each can contain up to four images); text-only batches stop at attachment order boundaries. This avoids a new image taking unrelated queued text into its blocked batch, without changing recovered legacy batches.

Withdrawal v1 is deliberately limited to loops that have produced no assistant output. The actual CallState values are PREPARED / IN_FLIGHT / RESPONSE_SAVED / INTERRUPTED / FAILED (no UNKNOWN). Require Host active and maintenance/extraction work idle and no settings rebuild at the serialized check/commit boundary. For CLAIMED, additionally require session RECOVERY_BLOCKED or CAPACITY_BLOCKED, claimed_input_ids exactly [target], active_loop_id equal to input.loop_id, no loop ModelCall IN_FLIGHT or RESPONSE_SAVED, no durable assistant output for the loop (including a response not yet installed in a checkpoint), no assistant/toolResult after the input in the latest loop checkpoint, and no pending/executed tool or unresolved Operation effect for that loop. All other cases return WITHDRAWAL_UNSAFE. Preserve existing INTERRUPTED attempt evidence; withdrawal stops further processing, not a claim that no provider attempt ever occurred. This covers deterministic profile/budget/same-length-hash failures before response. A model change after tool iterations still requires restoring the deployment/existing recovery and cannot use v1 withdrawal. Do not invent a result reconstruction protocol.

Use the latest checkpoint for this loop if present, otherwise the current last_context_id from the preceding completed history when failure preceded the first checkpoint. Replace the exact target occurrence with one deterministic notice; if it was never inserted, append one notice. The notice contains only Input ID, ordered attachment metadata and “withdrawn by owner; this input must not be executed”, never its typed text or pixels. No need to read damaged image bytes. Verify the source checkpoint/event association and descriptor using immutable metadata and the owning CAS message refs; do not waive arbitrary message authenticity to achieve this. All prior completed history remains unchanged. An ACCEPTED-only withdrawal writes Input/event/receipt and does not clear another session loop or create an unnecessary checkpoint.

Atomicity: split saveContext into a non-committing context builder and the existing committing wrapper. The builder may putMessages/tools schema in CAS and construct Context + model.context event, but MUST NOT call store.commit. Safe CLAIMED withdrawal performs exactly one journal commit containing the built Context, Input WITHDRAWN, Session revision (IDLE, active_loop_id=null, claimed_input_ids=[], recovery_error=null, model_blocked_call=null, last_context_id=new Context), model.context and input.withdrawn events, and the admission ApiCommand. No earlier journal mutation inside withAdmission. Preserve all original evidence and accepted message receipt. SIGKILL after CAS writes or around the frame must leave either no accepted withdrawal or exactly one complete withdrawal; same-ID retries cannot observe an ApiCommand without the matching state. After commit schedule drain() so already queued text proceeds; never wait for drain inside admission.

WITHDRAWN is terminal and not mandatory pending input. Update main-loop selection/finish, app.settle, activity/context counters, historical/settings filters and schema/state catalog. The host withdrawal notice is not a Master Input or quote: it is projection/audit metadata keyed by withdrawal event. It appears once in the next new-loop context and is then eligible for deterministic omission at the following new-loop boundary, without summary coverage. Frozen request checkpoints retain their original form for replay. It remains permanently visible as a status on the historical input row. A before-next-loop crash cannot create a second notice; persist its notice-consumption boundary in the same context evidence used for projection.

Withdrawal abandons the entire Input, including typed text. Raw accepted/input-message events remain in the journal as audit evidence but every new event-derived projection uses the shared boundary-aware renderer: summary/settings sources exclude withdrawn text/images (optional metadata notice only); quote extraction skips them; World rejects withdrawn input events as evidence even when explicitly named; search catch-up handles input.withdrawn as a tombstone/retraction of the original input document. Search query/World admission also consult the current withdrawal index so a lagging read projection cannot expose withdrawn text as active evidence. Expose historical raw text only through explicit history/audit APIs marked withdrawn, never as fresh context or memory source. Exact pre-withdrawal source snapshots remain verifiable audit objects; when a pending summary/extraction/settings job would publish after withdrawal, publication rechecks source Input withdrawal revisions and rejects/re-freezes affected candidate material, rather than publishing a stale pre-withdrawal quote. Serialize withdrawal against active maintenance; already committed independent effects are preserved, not silently retracted.

Gate: after recordInputMessages persisted a CLAIMED text+image source, withdraw it, process queued text, compact, apply settings and catch up search. Assert zero withdrawn text in new summary/commitment/search hits/World evidence, one historical status and one transient context notice, bounded notice residency, and crash-idempotent atomicity. Include a frozen-before-withdrawal pending candidate that cannot publish stale material afterward. Missing/truncated objects on Store.open still require separate storage recovery; same-length binary corruption must not prevent metadata-only safe withdrawal.

## 5c. One concrete identity/authentication mechanism

Extend pure messageIdentityHash only for well-shaped v2 attachment tags to return a mode-invariant candidate hash of `{version:2, role, timestamp, session_id, input_id, input_content_digest}`. input_content_digest already commits the exact typed-text SHA and ordered attachment descriptors. Using the digest instead of embedding typed text keeps withdrawal notices free of withdrawn prose. Full/stub/withdrawal forms of one occurrence share this candidate key. Text-only, v1 and legacy hashes remain byte-identical. This pure key is NOT authentication and MUST NOT authorize coverage, dedupe or provenance on its own. Provider logical request keys and exact-byte payload hashes remain form-sensitive and unchanged in purpose.

Introduce one store-aware `attachmentForm(store, message, boundary, sourceEvidence)` returning authenticated `{input, mode, typedText, identityKey, originalDigest, renderedDigest}`. boundary includes session, journal sequence/digest, residency policy and persisted form decisions; sourceEvidence names the owning event or immutable Context/message ref. Verify Input/session/time, immutable full descriptor digest, event/context association and exact canonical rendering. Full image forms require exact MIME/order and canonical base64 of hash-verified image content; stub forms require an exact deterministic rendering plus HANDLED proof at boundary; withdrawal notices require the committed withdrawal event at boundary and carry typedText=null. A v1 tag, spoofed v2 input ID, stale boundary, wrong mode or extra/deleted/changed content cannot authenticate. The helper accepts historical frozen forms for verification, but choosing a new form always uses the target boundary and its authorized transitions.
