## 操作者如何使用

递归检出仓库，安装锁定依赖、Node 22.19+、Python 3、PostgreSQL 18 服务端工具及支持的 Hermes 评分器版本。README 给出评分器和隔离环境的获取、版本检查方法。公共示例用可公开的合成材料，在干净检出上就能运行，无须改代码、读取历史私有回执或使用个人 Hermes 配置。从示例配置开始，用受保护的本地设置引用工作和评分凭据，选择已授权的真实模型配置。

拟议主命令为 `npm run benchmark -- evaluate --config examples/secretary-smoke.json`。示例给出公开测试包及版本、C04-resident、一次重复、目标与两个模型配置、评分规则和上限。命令打印运行 ID、状态以及 `.local/benchmark/<run-id>/reports/report.md` 和对应 JSON 的位置。发送请求前核验版本、能力、凭据、隔离、每角色请求次数、超时和输出目录归属。遇错提示操作者可执行的修复动作。被测系统答错时仍可完成测量；配置无效、运行或评分不完整使用可区分的非零退出码。

沿用同一 npm 入口提供按配置选案例、重评、重建报告、导入基线和归档清理。帮助中逐项给使用示例，面向操作者只暴露运行 ID。一次真实调用加载并验证本轮获准的冻结与上限，正常路径没有人工接力。工作模型、评分模型及推理档位在运行间可换；记录能核验的实际服务身份。严格配置遇身份不符拒绝评分或严格比较，无法识别的版本明确列缺口。

## 实施顺序与验收

1. 先实现配置、单命令、可搬移运行包和脚本对照。在 correctness CI 中先用模拟目标及评分端，再用隔离的、版本锁定的 Secretary 加脚本模型。覆盖正反例、能力缺口、校准失败、评分中断恢复、目标效果未决、重复调用、隔离探针、材料缺失或损坏及预算耗尽。核验基线导入摘要和不兼容标识。将导出包复制到独立目录，原路径不可读时验证重评零目标调用、报告重建零模型调用。四个历史规范产物使用已有私有归档重放流程及清理证据的完整摘要核验；公开 CI 使用公开输入。保留首失败。
2. 接入真实 Secretary 和独立 Hermes API 评分路线，仍走同一命令。付费前先用已安装的准确评分器版本和本地模拟传输穿过实际请求构造、解析和回执路径。清洁安装所需的非秘密依赖必须随库提供或有可重现获取说明。若需要私有 R79 临时脚本或人工生成、递交评分材料，即未达到验收。目标与裁判分别控制调用、费用及时限，核实版本及计费归属，禁用静默换路。
3. 真实操作者验收拟用 C04-resident，固定公开时间线，先经正常入口送入 Elm 的 token REED-843，再提问。轨迹必须有投喂确认并证明它早于真实提问；本例测量常驻使用。工作模型采用已核实的必测 DeepSeek Flash 路线。独立评分沿用 R79 的 Hermes / opencode-go / deepseek-v4.1-flash / max 路线，记录公布版本、实际返回标识和评分规则版本。每轮固定案例字节、每角色请求次数、重试和停止条件、模型、推理档位与报告预期。使用 operator v2 固定规则时重新校准；更换模型或扩大案例范围须单独决定。按 Master 最新指示，后续费用和用量据实登记，未知值保留为未知。仅在供应商实际报告额度限制时通知 Master。未参与开发的操作者从干净检出只按 README 操作。保存命令、解析配置、退出码、结果位置、偏离之处，人工搬包/回填回执/拼报告次数为零，并确有一次真实语义评分。对同一封存包禁用目标进行一次获准的真实重评；再禁用两个端点，以原评分逐字节重建首份报告。独立列出程序正确性、实模覆盖、真人操作、产品使用门槛。工具验收批次独立记账。
4. 第三项使用同一协议。ProkBot 原生 Host 负责对话、调度与记录，可裁去无关外部 UI，保留原生记忆体系和必要执行器，以实测轨迹证明维护确已触发，记录实际 Host 版本与裁剪清单。普通 pi 固定原版执行器和压缩次数及硬 reset；原 Hermes 备选改为同一 pi 加载固定版本的 pi-hermes-memory，使用干净存储，禁止索引操作者会话，观察实际扩展读写。各自声明可观测能力。此次桌面核对使用上游 [ProkBot](https://github.com/aha-duoduoduo/ProkBot) 与 [pi-hermes-memory](https://github.com/chandra447/pi-hermes-memory) 的说明，钩子与退出语义在第三项原生试跑核实。外部可执行文件可独立交付。预先指定共同案例及适用性；既有基线无法证明身份与条件等价时，在同一窗口交错采集 Secretary 参照；保留分母、能力和解释限制。原生对照与后续可选的借鉴型变体各用独立批次。
5. benchmark 实施 PR 更新源码、使用说明及运行示例，执行 npm run verify 与准确提交的既有 CI。保留首失败和私有原证据，公开脱敏回执。以准确提交差异、测试、实测与操作者记录请同一 Claude 会话复核，再交 Master 终审。本轮仅拟定设计，实施由 Master 确认后开始。

## 首轮复核处置与验收细节

- 使用实际组合校准。锁定提交的 targeted-reader-packet.ts 中，targetedControls 合并 generateCalibration 提供的 22 个断言对照和 newVisibilityControls 提供的 6 个可见性对照，强制总数 28，须 28/28 通过。另预登记两个 C04-resident 合成候选包，一份答对当前 token，一份虚构错误 token。用生产候选格式，由真实裁判在各自新会话盲判，包内隐藏预期标签。natural_access 分别取得 PASS 和 FAIL 后才接纳正式评分。每个有效校准期执行一次，实发计入事前冻结，控制包回执独立列出。被测系统仍只需跑一个真实案例。评分回执绑定实际外发正文字节摘要、原始响应和证据，排除 HTTP 鉴权头。
- 正式发布采用预登记尝试顺序中首个完成执行的原始评分。“完成”只看执行证据，不依赖答案和裁判结论。选定后，首份评分缺失或无效，正式报告保留未评分。更早的未完成尝试、无效评分和后续重评逐项保留，计入对应覆盖与费用分母。没有任何尝试完成则发布不完整。选择其他尝试或评分 ID 的报告明确标作非正式诊断，保留首份规范产物字节。默认实测只预登记一次尝试。
- 操作者机器在任何真实发送前，用本次目标相同的隔离配置、UID 与挂载执行拒读探针。先证明宿主能读取探针，目标能读自己的对照文件，再验证目标直接和经别名读取私有探针均失败。只向目标挂载 SUT 及运行依赖，整个 benchmark 检出不可见。隔离失效或不支持的平台拒绝实发。每种宣称支持的宿主及隔离组合在 CI 重做拒读检查。目标和裁判共用供应商账号时，分别核算每角色请求次数，共享请求账本。原有 bounded 配置保留已承诺的费用边界；新的公开示例显式选择 record-only。
- 每次 CI 从公开证据重算覆盖表 b96a85cb…，另保留四个历史产物的私有发布核验。本轮采纳真实投喂、裁判判别力、正式结果选择和实机隔离意见；依据源码纠正初审对 28 个对照构成的表述。
