## 已确认的问题

`Store.stage` 复制全部 records 并扫描 Session；`verifyRefs` 对每个引用读取并哈希正文。`saveContext` 同时保存逐消息内容与完整 raw_context；其引用用于 Host 恢复、Checkpoint、Settings 和记忆来源。Host 的反馈投递反复扫描所有 trigger.missed 和 Feedback；Scheduler tick/retire 扫描历史 Execution/TaskPlan。Python 助手每毫秒轮询请求文件，Node 提交以 Atomics.wait 轮询回执。

## 实施方案

1. **暂存覆盖查找，独立提交。** 以本事务 Map 覆盖 records，Session 数量从已安装类型索引加本事务新增计数取得。仅成功追加后安装索引；验证失败不污染内存。保留 revision、引用、唯一主 Session 和同事务 Session 引用校验。
2. **引用元数据校验，独立提交。** stage 仍完整读取并校验 mutation snapshot；嵌套 ObjectRef 校验路径/sha 对应、普通文件、长度，正文哈希保留于 put/bytes。覆盖缺失、长度变化、符号链接、同长度内容损坏在读取时拒绝。
3. **Context 选择目标一：去掉重复正文，独立提交。** 新 raw_context 保存带明确编码标识的消息引用清单，逐消息内容继续 CAS 去重；统一读取入口识别旧消息数组与新清单并重建。Context.messages 保留现有语义；Host、Scheduler 恢复、Settings/记忆提取及引用读取都迁到统一入口。raw_context 仍是持久来源引用，避免破坏 Checkpoint/Consciousness 的来源关系。验证空上下文、多模态消息、重复消息、工具调用顺序、旧新混合与重启。请求和供应商 payload 保留完整证据，引用列表与请求字节仍可能平方增长，按分类报告。
4. **pump 索引，独立提交。** Store 在 install/replay 维护类型+状态集合，提供克隆查询入口。pump 上的 Feedback、Input、Execution、TaskPlan、Operation、WakeTimer 等只读取待处理集合；对 CLOSED TaskPlan 残留队列保留清理路径。Execution occurrence 去重保留历史索引，不能因过滤终态而重复执行。新 trigger.missed 与主会话 Input 原子提交；旧历史通过一次性恢复处理保留幂等性。覆盖全部实际 pump 调用链，不仅改最外层循环。
5. **追加传输，独立提交。** 基准后首选 FIFO；Python 继续独占 flock、恢复、追加和 fsync，Node 不直接写 journal。每次 open 使用私有通道，请求与 ACK 有明确分帧、request id 与 digest 校验；处理短读/短写、超过管道容量、EOF、助手死亡与超时，未获 ACK 永不安装或重试。助手空闲通过阻塞等待请求/父进程 EOF，不每毫秒唤醒。同步提交仍阻塞事件循环，验收同时记录 HTTP 延迟。

### R1 修订：读取语义与有界等待

采纳 B1/B2：编码读取应覆盖所有来源引用，不限于 Context 字段；同步 FIFO 不能在主线程可靠超时。

- 编码采用专用 media_type `application/vnd.secretary.message-list+json`，CAS 清单为 `{encoding:"message-refs-v1", messages:ObjectRef[]}`。`Store.read` 是统一解码入口，旧 JSON 数组行为不变；`Store.bytes` 始终返回并验证真实存储字节。清单只允许普通 JSON 消息引用，不允许清单嵌套，避免循环/递归攻击。读取逐项验证哈希。Context.messages 与清单顺序一致。
- 消费清单：`host.ts` history/run/summary 来源（原303/313/512/561/1402/1539/1573/1770）、`scheduler.ts` checkpoint 恢复和任务来源（原274/359/373/527/1370）、`settings.ts` 来源转发、`settings-memory.ts` source/rebuild、`memory.ts` quoteIn/CompactionJob 来源校验（原146/150/251）、`memory-extraction.ts` source_ref（原267/497）、`input-projection.ts` source_refs（原178/215）、`context-projection.ts` crop 来源统一经 Store.read。裸 bytes 路径中 Scheduler 的提示词装配需显式展开消息；API 对象读取继续返回实际 CAS 内容及实际 sha/bytes，公开字段语义不变，数值随编码变化。
- 前缀和承诺验证比较展开消息的内容哈希，来源身份仍使用原 ObjectRef。对旧/新编码均验证有效承诺通过、无效承诺拒绝、任务提示词正文一致。`pending_source_bytes` 改为展开消息 JSON 字节数，保证规模口径一致。
- 不采用“禁止所有 read<unknown>”的 grep：统一入口本身就是 Store.read，通用读取不构成绕过。用行为测试与裸 bytes 消费检查验证恢复、记忆、任务来源；保留原失败断言。
- FIFO 在专用 worker 内完成 open/write/read，主线程只 `Atomics.wait(timeout)` 一次等待 ACK。超时杀助手、毒化 owner；没有 ACK 不安装、不重试。worker/助手不持有多余 ACK 写端；fd CLOEXEC，按匹配读写端握手，启动等待有界。助手继续是唯一 journal 写者。worker 负责的大帧读写处理部分完成及 EOF。
- 对 reviewer 的一处异议：同步 Atomics.wait 仍阻塞主线程，期间 HTTP 无法响应。保留同步 Store 的前提下，验收为正常提交 HTTP 延迟改善、SIGSTOP 时在 30 秒期限后恢复并报错，不承诺等待期间响应。测试覆盖 SIGSTOP、半帧 SIGKILL、超过 1 MB 请求以及空闲 CPU。
- pump 内层补充：历史 occurrence 按 task_id+occurrence_key 索引；Feedback/logs 按 execution_id 索引；trigger.missed 旧记录沿用 receipt 幂等恢复；维护检查和 Settings 未完成查询也使用索引。WakeTimer source event 验证复用 event id 查询，避免扫全部日志。
- 提供显式 CAS 完整校验维护脚本，逐文件哈希并报告损坏；不在启动时自动执行。
- 性能门禁：第一部分每项验收前补充数值门槛并复核；追加路径实施前必须取得第一部分基准，确定提交与 HTTP 门槛并复核。大规模性能数据不放 CI；CI 使用缩小规模回归。
- 回归首次 fixture 失败为 Session 使用非法 PAUSED，改用合同已有 STOPPED 后 2/2 通过；原日志保留在 `.demo-data/issue24/`。
