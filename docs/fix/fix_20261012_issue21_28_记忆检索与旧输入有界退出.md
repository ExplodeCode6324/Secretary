## 3. #21：可重建检索索引

### 3.1 存储、生命周期与恢复

在现有 PostgreSQL 内建立独立 `mem` schema，新增迁移文件，由 owner 的 `POST /api/v1/admin/world/migrate` 入口在现有迁移锁下管理。World 的权威事实仍在 `wm`，索引是 journal/CAS 的派生数据。

采用事件文档、正文分块及投影水位三类表。文档含来源身份、event_id、日志 sequence、时间、kind、session_id、scope_id、task_id、正文摘要指纹与读取引用；分块含 chunk_index、原文偏移和正文；水位含已提交的 journal sequence/digest、投影版本及源身份。源身份绑定该 journal 的稳定起始身份和会话，避免同一 DSN 切换 Store 后串入另一份历史。

单个后台投影器读取 `Store.projectionFrames`，有界批次执行 SQL 事务；文档/分块和水位同事务提交。失败不推进水位，重放按来源及事件/分块键幂等写入。由 `App.open/pump/settle/close` 管理初始化、推进、测试等待和关闭，复用 World 的连接池，不另建存储组件。一次处理建议最多 100 个事务帧；单条大输入完整分块，仍与其帧水位原子提交。

首次迁移或无水位从起点重建。启动检查 source_id、水位版本、对应 journal digest，以及文档/分块与水位完整性；清空索引表但留下旧水位也要触发重建。身份、版本或 digest 不匹配统一走重建，不另外设计“分叉状态机”或多 Store 共用调度。重建期间正常业务恢复继续，搜索明确返回状态和已索引水位。迁移权限不足、扩展缺失或索引故障给出具体诊断，不把异常变成“没有命中”。

### 3.2 纳入的正文与事件身份

| kind | 来源 | 规则 |
| --- | --- | --- |
| input | Master 的 `input.accepted` 事件及 Input.payload | 接受后即可索引完整原文；每次输入以事件区分，相同文字不合并 |
| reply | `main.message` 的最终 assistant 文本 | 仅已持久完成的正常最终回复；不索引 thinking、toolCall 或失败输出 |
| task | `execution.finished` 中的 TaskResult.summary、`feedback.delivered` 中的 Feedback.summary | 使用现有事件冻结正文；后续 revision 不重复建文档 |
| notification | Notification 创建正文 | 只纳入一次；presented/read/发送状态更新不复制正文 |

优先使用上述既有事件，不为索引新增业务记录或虚构 event_id。TaskResult 的最终摘要和交给主会话的 Feedback 是两类独立来源；不得再把同一反馈包装的 SCHEDULER Input 重复索引。旧数据若缺失上述来源事件，先核验旧事件注册及其完整引用；仍无法溯源的记录给出具体诊断，在计划中记录缺口后再决定迁移处理。搜索返回的每个 event_id 都必须通过分片读取验证，不能提供只存在于 SQL、无法溯源的 ID。

scope_id 是 #16 的工作范围，不是日志中的会话归属结构。任务材料从冻结的 Feedback/TaskResult/Execution 绑定取值；普通 Master 输入和无任务归属的回复/通知保持 null，不从关键词推断范围。时间使用来源的 occurred_at 或创建时间，后续索引时间不改变历史时间。

正文按 Unicode 边界完整分块，建议每块约 2 KiB UTF-8、相邻重叠 256 个字符，与支持的最长 query 对齐；原文偏移统一为 Unicode code point。完整正文没有前缀截断，尾部及跨块关键词可命中。返回片段才限约 200 字；同一事件多块命中归并，按时间倒序和稳定事件键排序。

### 3.3 中文查询与性能

使用 `pg_trgm`、正文列 GIN `gin_trgm_ops` 和参数化 `ILIKE` 子串查询。query 作为字面关键词，转义 `%`、`_` 和转义字符；不让用户输入成为 SQL 模式或 SQL 语句。时间、kind、scope、task 先作联合过滤，保留相应 B-tree 索引；首期固定时间排序，暂不加入 similarity 排序参数。

PostgreSQL 官方说明没有可提取 trigram 的模式会退化为扫描整个索引，因此两字中文不能以“出现 GIN”替代性能验收。参见 [PostgreSQL 18 pg_trgm 文档](https://www.postgresql.org/docs/18/pgtrgm.html#PGTRGM-INDEX)。

实施第一步按第 8.2 节自建隔离 PostgreSQL 18。记录实际 `server_version`/`server_version_num`、编码、`datctype`、`datcollate`、`datlocprovider`（报告为 locale_provider）、`datlocale`、`datcollversion` 和 pg_trgm 版本；字段含义见 [PostgreSQL 18 pg_database 文档](https://www.postgresql.org/docs/18/catalog-pg-database.html)。保存 `show_trgm('杭州')`、`show_trgm('杭州见')` 及英文的结果，在该库实际默认 collation 下运行最终搜索 SQL，明确断言“杭州”“杭州见”命中预期合成事件，并与无索引的字面子串查询结果核对。S1 同时验证命中正确性和查询计划，不能用 `show_trgm` 非空代替实际搜索。

另建 `LC_CTYPE=C` 的隔离对照库，记录中文分类与索引退化行为；`C` 和 `C.UTF-8` 分别记录，不能混用。r2 所述“中文完全失效”不能仅由 CJK 不产生 trigram 推导：上述官方文档给出的行为是模式退化为全索引扫描；本计划使用 ILIKE 字面子串而非相似度阈值查询。正确性与性能分别实测，实际 SQL 漏掉预期事件即失败，正常场景超过 5 秒也失败。

用于部署验收时只读核对版本及 locale 元数据；与本地基线不同时，在匹配版本和 locale/provider 的隔离库重跑 S1 中文验证，结果分别标注。现有真实数据实例不作测试 DSN，所有测试数据、扩展安装和迁移只进入隔离库。

性能基线使用至少 10 万个合成事件，并按实际历史的匿名统计调整正文长度、分块量与命中比例；保存普通执行器选择的 `EXPLAIN (ANALYZE, BUFFERS)`，记录冷/热查询、两字/三字、无命中/高命中、带过滤的 p50/p95 和索引体积。**高命中两字查询单独列出**，使用最终的事件去重、时间倒序、稳定事件键及 limit 查询，记录原始匹配规模、实际返回数、排序与 buffer 开销。GIN 位图路径可能先收集大量匹配再排序，不能由返回 limit 很小推断其扫描量很小；还要核对 top-N 事件顺序，不以预先截断正文候选换取通过。关闭 seqscan 的诊断另列，不作自然计划证据。

温缓存常用查询 p95 ≤ 1 秒是优化目标，issue 要求记录查询计划与延迟，不把这个新增目标冒充原 issue 的硬门槛。单次搜索数据库 statement_timeout 固定为 5 秒：正常验收查询超时即失败，不能把超时改成空命中；另有专门故障用例验证 search_timeout 的状态。新消息正常负载下 ≤ 5 秒可检索仍为本计划的验收线。

两字查询不达优化目标时，固定处理顺序为：核对 locale/统计信息与自然计划，优化已有 GIN、时间/范围索引及去重/limit 查询，再复跑同规模场景。仍超时则明确返回 search_timeout，并提示调用方主动缩小时间或工作范围。不得自动限定最近 N 天、强制 kinds/from/to，或静默截掉老历史；这些做法会使未知道范围的旧事实无法找回，改变 #21 的全历史查询语义。若优化后正常场景仍越过 5 秒硬线，记录失败及具体修订方案后报 Master 复核。

### 3.4 工具形状与全文读取

`memory_search` 参数：非空 query（最多 256 字）、可选 from/to（带时区）、kinds（input/reply/task/notification）、scope_id、task_id、limit（默认 10，最大 20）。时间范围采用 `[from, to)`；所有过滤联合生效。返回状态、已索引水位及命中列表，列表含 event_id、时间、kind、session_id、scope_id、task_id、约 200 字片段和正文偏移。索引未追平时明确标记部分结果。

未配置 PostgreSQL 返回 `not_configured`；未迁移、重建、暂时故障分别给出可识别状态，不能伪装成空结果。主会话的其他工具和新输入路径继续工作。

`memory_read source=log` 保留 event_id，增加 offset/length；默认 2000、最多 4000 code point。返回事件元数据、正文片段、总长度、正文 hash 和 next_offset；按完整 CAS 来源读取，读取不依赖索引或 PostgreSQL。近期日志列表也有界，不把大 payload 塞回模型。对旧任意日志保留读取能力，对搜索文档使用同一正文提取规则；未知 ID、非法 offset 返回明确原因。测试逐片拼回全文、尾部命中和 emoji/转义字符边界。

搜索及读取返回还受本轮可用工具结果预算约束：必要时减少命中条数或实际片长，明确 truncated/next_offset，最小可读片也放不下时返回具体容量原因。只收缩本次返回，不删索引正文；避免最大 20 条中文片段或大正文分片把当前受保护轮次推到预算之外。

## 4. #21：World 读取与结构化提案

### 4.1 名称、别名与分页

`memory_read source=world` 增加 subject（实体 ID 或名称）、predicate 和 cursor/limit；保留现有 subject_id 参数供读取。同次调用只能提供一个非 null 选择器；二者同时提供时返回 SELECTOR_CONFLICT，即使指向同一实体也拒绝，subject_id=null 视为未指定。基于现有 `World.page` 做有界分页，默认 20、最大 100；能按 predicate 查询并继续读取第 100 条之后的事实。PR 复核处置见[修订记录](fix_20261013_pr38_39_复核修订.md)。

先精确解析有效实体 ID，否则按规范化名称或别名精确匹配。零命中返回 subject_not_found；多命中返回候选 ID/name/kind，调用方明确选择后再读或提案，不能自动选第一条。

当前 `wm.entity` 没有别名字段。本批增加 `aliases text[]`，通过原有 Settings ENTITY 编辑及 WorldCatalogChange 授权路径维护，同步内部 schema、公开 WorldEdit DTO 与生成文档；旧记录缺失时按空数组读取，旧编辑缺省不清空已有别名。别名去空、去重并限制数量及长度，同名/同别名仍允许但必须返回歧义。未找到实体由现有 Settings 创建，不根据一句名称猜 entity kind 或自动新建目录项。

### 4.2 提案意图与宿主责任

删除模型工具的 change_json 参数，改为 `intent`（ASSERT/CORRECT/RETRACT）、subject、predicate、value、可选 valid_from、target_fact_id、source_event_ids 和 source_note。ENTITY 类型 value 使用明确实体 ID/名称选择器；普通值按 predicate.value_schema 验证，关系引用按同一歧义规则解析。

宿主生成 request/change/assertion ID、时间、当前 slot revision、内容引用和内部 WorldChange。CORRECT 与 RETRACT 必须指向当前且与 subject/predicate 一致的目标事实；RETRACT 复用目标 assertion_id，value/object_entity_id 为 null，避免违反现有撤回合同。SINGLE 使用空 scope_key；MULTI 更正/撤回复用目标 slot，新断言根据规范化值或对象形成稳定 scope_key，重复值复用同一 slot，不能随机键逃避冲突。

事实来源、来源说明和授权分开处理：source_note 仅是说明。提供 source_event_ids 时从当前 Store 的真实事件/CAS 组装证据，检查会话、来源和内容；缺省仅在当前轮次存在唯一相关 Master 来源时使用该事件，否则返回 evidence_required。Master 来源必须由 MASTER_UI 的 input.accepted 原事件证明，且冻结 payload 是 producer=MASTER 的 Input；其他 MASTER_UI 事件返回 SOURCE_EVENT_NOT_STATEMENT，混合引用也拒绝。任务/观察/模型推断保留其来源类别及 epistemic，不把模型解释升级为 Master 事实。所需来源登记沿用现有 REGISTER_SOURCE 的授权路径，不偷偷登记或以 source_note 替代证据。

组装结果仍交给 `World.propose`：保留展示 hash、批准、拒绝、revision 冲突、幂等和 SQL 校验。工具执行重放依据现有 toolKey 复用持久提案，不能再次生成一份待批变更。模型不获得直接修改 World、批准或裁定能力。

仅补一条已注册工具说明：当前上下文缺失的过去对话/任务细节先搜索，必要时读取来源，并在回答中引用 event_id；查不到或检索不可用时如实表达。历史事实不能盖过当前说明设置、有效限制及最新修正。#26 后续再整理整体提示词。

## 5. #28：统一的退出资格与近期窗口

### 5.1 逐条输入的资格

一条 Master Input 只有同时满足以下条件，才可在压缩或 Settings 新请求构建时退出：

1. 原 Input、完整正文引用和对应原始消息事件能被唯一识别。
2. 其完整消息已包含在成功提交的 WORKING_MEMORY 摘要来源，或成功 APPLIED Settings 的完整摘要来源；覆盖证据关联 session、来源事件与已提交水位。
3. 不在当前轮次 `protected_from_index` 及完整工具协议的受保护区间内。
4. 不在本次选择的近期原文窗口内，且第 6 节检索前置已满足。

不能只用 payload hash 或“sequence 比较小”推断已摘要。相同文字的两个事件、迟到事件、未处理输入、FAILED/STALE 摘要、尚未 APPLIED 的 Settings 各自核验；身份不明确的旧数据继续保护，后续通过真实来源整理建立覆盖。承诺提取是否成功不增加退出条件。

覆盖沿现有成功提交事务核验：普通摘要用 job.source_event_ids、source_end_sequence 与完整来源；Settings 用冻结的 extraction_messages、来源 refs 和已 APPLIED 的 application。只做 CONTEXT_COMPACTION 的 job 不新增摘要覆盖。第 6 节的唯一输入选择凭证保存策略版本、所用覆盖提交和参数指纹，供重启与诊断复算；旧记录缺省按原规则读，不改写历史快照。现有 context_compaction 仍负责对话及工具消息的裁剪，不再承担另一份输入退出账本。

### 5.2 默认参数与预算算法

| 参数 | 建议默认 | 含义 |
| --- | --- | --- |
| `SECRETARY_RECENT_INPUT_MAX_COUNT` | 12 | 当前轮次之外近期完整 Master Input 的最多条数；允许配置为 0 |
| `SECRETARY_RECENT_INPUT_BUDGET_RATIO` | 0.15 | 近期原文占可用输入预算 U 的最大比例，配置范围 `[0, 0.25]` |
| 原有整理阈值/目标 | 0.60 / 0.80 / 0.30 | 普通/强制阈值及整理目标沿用当前预算配置 |

先放入 system、工具声明、当前工作记忆/账本、未覆盖输入、当前轮次和不可拆的工具协议；再从新到旧按完整 Input 选取近期窗口。使用 `requestBudget` 的增量估计，不另创 tokenizer；窗口同时受条数、`0.15 × U` 和剩余整理目标预算约束。某一条过大放不下则不截断，跳过该条并继续选择更早可容纳的完整输入；具备退出资格的过大旧输入可退出，不具备资格的必须保留。

输出按原历史顺序放置，重复投影得到一致集合；当前轮次不计入 12 条且优先保护。若 mandatory 内容本身超过目标，记 target_reached=false；若超过实际发送预算，保留来源并报 CAPACITY_BLOCKED。200 轮验收使用固定有限约束和正常输入，验证历史原文驻留有界；不能靠截断未覆盖输入、删承诺或虚报预算达成。

参数纳入现有 runtimeHash/预算指纹，参数改变沿 Settings 流程生效。避免独立的隐式开关；检索是否可用由真实初始化状态和索引水位决定。

## 6. 统一投影、检索前置及恢复

普通压缩、Settings 重建和重启后的新请求共用一个选择器。完整 CHECKPOINT、ModelCall 的 MODEL_REQUEST/成功响应和历史 CAS 继续不可变；同一中断请求按原 MainPromptSnapshot 和已保存请求恢复，不能在恢复中换工具声明或重选本轮来源。

SettingsSource 的完整摘要与补提证据继续冻结；用于新请求的 anchors 由共同选择器生成，不等同于全部摘要来源。已认证历史 wrapper 先验证完整来源，再拆为 Input 身份选取并重建有界 wrapper；旧 wrapper 读得懂，新请求不整批回填已退出原文。未认证的相似前缀不当作宿主 wrapper，损坏的认证证据继续明确阻止发送。

将输入退出状态收敛为一个 `Consciousness.input_projection_ref`（旧记录可缺省），指向唯一不可变 CAS 凭证：策略/参数指纹、本次已考虑来源的日志水位、冻结的成功摘要覆盖引用、近期窗口的 Input ID（最多配置条数，默认 12）。**覆盖引用必须是单个 ObjectRef**，指向本次选择时最近一次已提交的累计覆盖状态快照；合同 schema 及 CAS 凭证校验均不接受引用数组，也不追加历次摘要引用或串联旧凭证。

“累计覆盖”表示此前已验证的成功覆盖继续有效，不能只取最近一次摘要的增量 event_id 而遗忘旧覆盖；也不能仅凭最大 sequence 推断所有更早输入都已覆盖。具体 Input 仍按第 5.1 节，从原 journal/CAS 的成功 job、APPLIED 来源和会话证据复核，歧义或覆盖缺口继续保护。凭证自身只保留该单值引用和有界窗口，不复制完整来源清单。原 journal/CAS 的历史证据继续保存，增加压缩次数不增加当前凭证的引用数或列表长度。不存累计退出集合、替换消息副本或第二套状态机；未覆盖及当前轮次的保护集合从原记录推导，不存进窗口列表。

对上一凭证水位内、在其冻结覆盖证据中且不在其窗口中的 Input，视为已提交退出。新选择只在上次驻留、新来源及上次未覆盖来源中进行，不能把已退出输入因预算变大而重新入窗。冻结覆盖引用也防止数据库故障期间新摘要成功后，在水位不变时意外新增退出。近期窗口因超大输入跳过而可能不连续，因此不能只存一个标量 exit_boundary；反例与取舍见第 11 节 N1。

凭证与当前采用的新请求投影在同一 journal 事务提交。Settings APPLIED 后承接凭证，即使 context_compaction 被重置也不会遗忘退出；未提交的候选不改变退出事实。历史 CAS 和 wrapper 的完整来源仍可验证及读取，输入选择凭证不随请求发给模型。

只有 PostgreSQL 已配置、迁移完成、memory_search/分片读取已注册，且索引水位覆盖本次待退出的来源时才提交新增退出。落后时等待后台追平或保留本次相关原文，不能以“将来能重建”替代现在的检索能力。

PostgreSQL 未配置或索引未就绪时保留原文规则，search 返回状态，其他功能继续。已退出之后发生数据库故障，冻结最后已提交的输入选择凭证，暂停新增退出并报告检索不可用；全文读取仍可从 journal/CAS 工作。重新连接或重建追平后继续，不整批回填历史。该边界需覆盖数据库断连、重启和 Settings 操作的组合。

**R3 采用报告方案 a：有界历史原文请求依赖已配置且可用的 PostgreSQL 检索。** Master 本轮已确认达到实施条件，按此方案实施。PG 仍是 Core 的可选组件，但它是本批有界上下文功能的前置；无 PG 部署保留原文，长期对话仍可能因旧原文累积进入 CAPACITY_BLOCKED。本批不对这类部署承诺有界。部署手册明确写出前置，memory 状态返回未启用退出的具体原因，发生容量阻塞时说明历史退出为何未启用及如何配置检索，不静默裁掉来源。

不采用方案 b 作为默认降级：按时间分页能枚举日志，却不能在模型不知道 event_id/时间的情况下按内容找回，和 #21/#28 明确的“检索可用后才启用退出”条件不一致。无 PG 也有界的实现涉及新的可找回能力及 issue 范围，不纳入本批。

N1 的具体反例：已覆盖输入按旧到新为 A（小）、B（大）、C（小），近期预算能放 C 和 A、不能放 B。原规则会保留 A/C、退出 B。若 exit_boundary 越过 B，按“边界前已覆盖输入不得重新入窗”会错误移除 A；若边界留在 A 前，Settings 后预算变大又会让已退出的 B 入窗。只靠标量不能同时表达这三个选择。另一个反例是边界前尚未覆盖的旧输入：数据库故障后摘要新覆盖它，若只使用最新覆盖加冻结边界，会在未确认检索水位时新增退出。保留冻结覆盖引用和有界近期 ID 能分别解决这两个故障。

若改成“遇到大输入立即停止选更早输入、退出只推进连续的已覆盖且已索引前缀”，可另做纯边界方案，但它改变本计划的窗口利用方式，并会在早期未覆盖缺口前阻止后续合格输入退出。本次不为单标量目标改掉这些行为。

初审修订阶段只检查计划的本地链接、验收矩阵完整性和 diff，未执行功能验收、启动测试集群或修改业务代码。后续 r2 及 Master 确认记录见第 12 节。
