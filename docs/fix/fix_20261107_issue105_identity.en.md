## 3. Durable names and round allocation

### 3.1 Title rules

The final `TaskPlan.title` is unique in the whole Store data domain, including other sessions, historical tasks and archived scopes. UUIDs remain authoritative and continue naming workspaces; titles never change goal, paths, parent references or execution IDs. There is no rename feature in this issue.

Proposed normalization v1, to be implemented as one pure shared routine and documented with examples:

1. Main supplies a short `title_candidate` in its existing task_propose call. Omitted/null/normalization-empty candidates fall back to a bounded prefix of the original goal, then `Task` if that is empty. Examine at most 4,096 UTF-16 units of goal for fallback; no separate model request. Candidate input is capped at 1,024 UTF-8 bytes; reject oversized explicit candidates before acceptance.
2. Normalize NFC; convert Unicode White_Space and C0/C1 control characters to ASCII spaces. Remove Unicode format controls except U+200D ZWJ, retained for emoji sequences; collapse spaces and trim. Reject malformed surrogate sequences. Preserve Chinese, case, punctuation, underscores, quotes and backslashes. This is case-sensitive NFC equality, not case folding, NFKC, fuzzy matching or visual-confusable equivalence. Render through existing safeText as well.
3. A final title is at most 64 Unicode scalar values and 256 UTF-8 bytes, including suffix. Truncate at a grapheme boundary within both ceilings; if a pathological first grapheme exceeds the budget, use the fallback `Task`. Naming normalization is not applied to task goal/body.
4. Try the bounded base, then `_1`, `_2`, etc. For each candidate, shorten the base as necessary to leave room for the entire suffix and check the actual final string against all reserved titles. A naturally supplied title ending `_1` is a normal reserved title, not parsed as an allocator counter. Choose the lowest available suffix deterministically; never release an old name. Guard numeric overflow explicitly.

The candidate and final bounded base must contain at least one display base character (not whitespace, a mark, a format/control or a Unicode default-ignorable code point). A joiner/variation-selector/combining-mark-only candidate is empty for fallback purposes. ZWJ and variation selectors may accompany visible emoji/text; they cannot form an invisible title by themselves. Persisted title validation never re-runs normalization during replay.

Allocation-only precisions from R2: if the normalized candidate is exactly UUID-shaped, use goal fallback; if that normalized fallback is also UUID-shaped, use `Task`. Always perform the final UUID-shape check after bounding too, so truncation cannot produce a UUID-shaped title. This prevents newly allocated titles from colliding with full internal IDs. Truncate fallback sampling without splitting a surrogate pair. Unicode-table-dependent normalization, grapheme boundaries and display-base classification run only during allocation. Replay/stage uses only engine-independent well-formed UTF-16, scalar/UTF-8 byte ceilings, no C0/C1 controls, exact-string uniqueness and immutability; a Node/ICU update must not reclassify an old saved title into an invalid journal. Do not rename existing assigned titles to reapply allocation policy.

Persist the candidate in the new proposal and the allocated title in TaskPlan. `title_candidate` is creation-only: non-null input on ordinary reuse is rejected before admission with `TITLE_ON_REUSE_NOT_ALLOWED`; REDO keeps its current correctable `FAILURE_REQUIREMENTS_CHANGED:title_candidate` rejection. Omitted/null is ignored everywhere and must be omitted from Scheduler.propose's options object, not inserted as a null key: v2 drops nulls but the legacy v1 hash serializes that object. Reuse/REDO therefore keeps the original Task title without loosening its requirements guard. For new creation, a supplied non-null candidate participates in the request fingerprint; same request/same input returns the original Task/title, changed input conflicts. A normalization-equivalent but differently supplied request is still governed by the fingerprint, not treated as implicit rename. Describe the field as creation-only in the Main tool schema/help and test absent/null legacy receipts separately.

The synchronous title selection + TaskPlan creation + existing task receipt/admission commit forms one acceptance boundary. No await between selection and commit. Build a title index from committed TaskPlans and update it only on committed frames; validate uniqueness against both committed and staged changes. A failed append cannot leak a successfully accepted name; after an uncertain ACK reopen and replay before retry. Concurrent callers in one Core serialize through this boundary; a second Store owner is refused by the existing flock.

### 3.2 Permanent execution rounds

Add `Execution.execution_round` (safe positive integer) and `TaskPlan.execution_round_high_water` (safe nonnegative integer). On actual new Execution creation, use high_water + 1 and atomically commit the Execution, incremented high-water mark, pending-request/occurrence consumption and existing parent-link changes. `plan_revision` continues referencing the actual plan snapshot used for that execution; do not fabricate or rewrite historical snapshots merely to expose the new counter.

A queued request reserves no round. Rejecting/removing it before Execution creation consumes none. An existing `(task_id, occurrence_key)`/request retry returns the same Execution and round; restart, WAIT_AUTH, WAIT_DECISION, model retry, redispatch and recovery keep that round. A new continuation or periodic execution increments it, even after failure/cancellation/retirement. No wraparound, reuse or UI-based numbering. At `Number.MAX_SAFE_INTEGER`, reject creation with an explicit capacity error while preserving the queued request and counter.

Commit validation prevents changing an assigned title/round, decreasing the counter, duplicate `(task_id, execution_round)` or a round exceeding the effective TaskPlan counter. Validate staged TaskPlan+Execution together and require the normal new-Execution allocation path to advance exactly once; migration is a separate narrowly identified operation. Historical records without the new fields remain valid during replay. Do not globally impose new-field requirements on old journal frames. Completed identity assignments cannot be erased by an older in-memory TaskPlan/Execution revision.

**Replay-stable rules (R1 B1):** `Store.stage(txn)` validates both append and every historical replay. Every identity check therefore depends only on pre-frame committed state and that frame, never on an in-process migration flag or the running binary's date. Use the per-Task `identity_version` and one existing-journal event `task.identity.activated` (version 1), written once after all migration units complete, to distinguish historical legacy creation from new admission. This marker is a format boundary, not a second identity authority or a business notification.

- Before activation, a first-created TaskPlan with none of the identity fields and first-created unnumbered Executions under a wholly unmigrated Task are accepted as legacy shapes. A first-created v1 TaskPlan is always complete with title, version 1 and high_water=0. After activation, incomplete new Task/Execution creation is rejected. The activation frame is valid only if all effective Tasks/Executions are complete; no duplicate/unsupported activation version. An empty Store activates once before App becomes ready as well. The event has no Input/Feedback producer and must not pollute business history/notifications.
- A title is assigned absent→value once and never changes/disappears. Compare exact stored strings against the committed index plus other staged Tasks, without re-normalizing them.
- For a Task with identity_version=1 **before** the frame, at most one new Execution per frame is permitted: its round is old high_water+1, and the same frame revises that Task's counter by exactly 1. With no new Execution the counter is unchanged. Existing assigned rounds never change. New Task+first Execution in one frame is not an allowed producer path; existing code already creates them in separate commits.
- For an existing Task without version 1 **before** the frame, only migration may introduce identity fields: reserve its title/high_water once; number only already-existing unnumbered Executions within that reserved range and in deterministic creation order; do not add executions once reservation has begun. Marker completion requires exactly rounds 1..high_water and no missing/duplicate mapping. The final assignment batch may set version 1 in the same frame because classification uses the pre-frame state. Once marked, no existing Execution can acquire a previously missing round.
- Build committed creation-rank, title and round indexes during replay/install and validate whole staged sets, including a staged final batch when checking completion. Avoid a full historical reread for each batch. Full close/reopen tests must replay old frames, partial/final migration frames, activation and subsequent ordinary Execution creations; snapshot-only reopen mocks are insufficient.

TaskPlan itself is the durable reservation and counter. Current retention does not delete it or Execution, so a second authoritative identity ledger is unnecessary. Identity metadata must remain reserved if execution payload/history is later reclaimed. A future physical TaskPlan purge must explicitly preserve its reservation first; physical purge is not implemented here.

## 4. Legacy backfill and startup gate

Add optional fields in storage schema for historical replay, but require complete identities on new creation and on public post-upgrade DTOs. In `App.open`, run versioned `ensureTaskIdentities(store)` immediately after `await Store.open`, before constructing Authorization / calling auth.recover(), World, Scheduler / scheduler.recover(), Host or exposing API/model work. Those recovery functions commit, so migration must precede them. Store.open retains its generic replay responsibility; production's sole caller is App.open. The migration itself does not call models, create Inputs/Feedback, initialize workspaces or execute tasks.

Deterministic order is ascending first committed creation frame sequence, then mutation position within that frame, then UUID as a defensive tie breaker. Do not use updated_at, started_at, locale sorting, directory enumeration or process start order. For legacy Tasks, allocate from the original proposal's goal in that Task creation order; reserve already assigned titles first. Include archived/closed Tasks and RETIRED Executions. For each legacy Task, assign rounds 1..N to its genuinely retained committed Execution creation records in that order. Never create a synthetic Execution to fill a presumed missing past event, and never modify old immutable journal snapshots/proposal refs.

Migration is restartable and bounded: persist the Task's reserved title and planned high-water value, then update at most 128 Execution records per transaction, and mark `identity_version=1` on the Task only after its assignments are complete. Before this marker, reconstruct the same complete ordered mapping on restart and verify existing assigned values against it; do not start numbering after the temporarily reserved high-water value. No business operations are admitted until all Tasks complete and the store-wide activation event commits. The last Task transaction may combine the final batch, Task completion and global activation if every effective record is complete. Completed Tasks are never renumbered; a second clean startup performs no identity writes. New Tasks are born complete with identity_version=1 and high_water=0. A crash after all Task markers but before activation only appends the missing activation on reopen; it does not rerun allocations.

Before mutating each migration unit, validate its required retained references and planned mapping. Existing conflicting identities, missing required creation/proposal evidence or inconsistent partial migration fail with a diagnostic and leave Core unready; do not guess or silently reassign. Preserve prior completed migration units and resume deterministically after repair. Record count/duration for the upgrade; no all-history scan on each lookup/keystroke. Explicit fault tests cover after title reservation, inside execution batches, before/after completion marker and fsync/ACK uncertainty. Upgrade validation uses copied isolated roots; real user data is untouched in the plan phase.

This is a one-way data-format upgrade: the old schemas use additionalProperties=false and an older binary cannot replay new fields after the first write. Before the first upgraded start on the real data root, cleanly stop its writer, take a consistent full backup of journal/objects and associated root state, and verify an isolated copy can reopen. Preserve that backup; do not suggest downgrading the binary against an upgraded root or restoring a prior snapshot over newer work automatically. Tests must demonstrate old-format→migration→new-format reopen; backward old-binary readability is not promised.

## 6. Minimal mouse and Esc navigation

Render a distinct `[详情]` hotspot on each root Task card, separate from title/goal text, with metadata containing the stable Task UUID. Derive hotspot rectangles while rendering, using Pi terminal-cell width and mapped wrapped rows, never UTF-16 string length or reverse parsing the title. Only root cards have this navigation action. Keep Main DocumentView behavior unchanged.

On an unmodified left press inside a hotspot, retain `{task_id, entry_id, page/navigation generation, rendered layout generation, scrollTop, screen/cell geometry}` and consume that small hotspot press so Pi can route its release/click. Reset any previous gesture on every new press; do not consume ordinary text press. Activation requires an outstanding record proving this very component consumed this gesture's press, plus the same press point/hotspot/Task, unchanged layout generation/scrollTop/target row, left button, no modifiers and `clickCount === 1`. Without that record return the click unhandled, including Pi's selection-path clicks. Cancel on drag, wheel, modifier, page/input-ownership change, resize, programmatic scroll/reflow or target replacement. Wheel cancels the record and returns unhandled so scrolling still occurs. Recheck current layout and scroll position even if Pi supplies stale press-relative coordinates. A conservative cancelled click is acceptable; opening a replacement Task is not. Hold a valid pending identity through release until Pi's subsequent click, not clearing it on release too early; invalid release cancels it. Consume the record once on successful click and clear on cancellation/next press. Do not capture the whole document, synthesize alternate mouse protocols or patch Pi. Test ordinary unconsumed press followed by a fallback click after content moves under the pointer, not just captured hotspot clicks.

Use existing `open(id)` fetch/authorize-before-view-switch and navigation epoch guards, so a late response cannot replace another page. Save the current root anchor before leaving, stop Task follow, open exact UUID and preserve the shared Task draft. If the Task has become unavailable, keep current view/draft and show the reason. Navigation creates no Input, Guidance, answer, authorization or cancellation request.

Esc priority: existing matter/authorization handlers first; then the active editor's completion menu closes and consumes Esc; then ordinary Task detail returns to root even when reading focus is active; Task root Esc only leaves reading/focus state if needed and otherwise does nothing. Main's reading Esc remains unchanged. `/back` and click use the same navigation helper and anchor restoration. If the anchored root row has disappeared, retain the existing honest neighbor fallback with a notice. Do not clear draft/undo/paste provenance, exit the process, submit a command or cancel business work. Mouse navigation is disabled while a matter, completion overlay, page transition or shutdown owns input; those existing handlers keep priority.

Draft precision: mouse and Esc call navigation directly, bypassing the command-submission block that currently clears editor text. Explicitly submitted `/back` or another local command retains its existing consume-own-command behavior; it does not restore a per-Task hidden draft or erase subsequent edits.
