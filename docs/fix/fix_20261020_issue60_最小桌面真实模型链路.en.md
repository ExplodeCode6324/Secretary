## 1. Outcome and observed gap

A person must complete conversation → task/execution → approval → structured result → artifact in the actual Tauri window against an isolated live Core and real provider. Then close/reopen and interrupt/reconnect the client without losing admitted work or creating duplicate side effects. Master tries the actual application and gives GO/NO-GO before #61. Passing tests or reviewer approval cannot substitute for that decision.

Source inspection at the baseline:
- `src/secretary_desktop/src/Connected.svelte` currently prints raw cache JSON, supports durable input/send, and downloads an artifact by manually entered ID. It lacks a readable business workflow, task/execution detail, approval controls, artifact listing and transient rendering.
- `src/secretary_desktop/src/bridge.ts` and `src-tauri/src/{bridge,storage,sync,protocol,transport}.rs` already provide controlled queries, durable submissions, domain isolation, sync, receipts and verified native downloads. Reuse this sole bridge/outbox/network stack.
- Generated `src/contracts.ts` comes from Core API v1. TaskDetail/Execution contain the public `Result` (outcome, summary, limitations, artifact_ids, needs_action, verified_by). There is no invented TaskResult endpoint. IDs, revisions and byte counts retain string precision.
- Core `sync-stream.ts` emits complete transient snapshots `{previews,activities}`. Current Rust retains the latest snapshot. Preview identity and durable Message.call_id support reconciliation; transient is replaceable and cannot advance durable sync state. The stream omits thinking blocks, so do not promise hidden reasoning display.
- The desktop bridge already allows tasks, executions, decisions, authorizations, artifacts and their required writes. FE-01 snapshots/send serialize with sync and may wait a network timeout; snapshots contain full active projections. FE-02 must measure and address user-visible blocking if it prevents usable interaction.

## 2. Implementation units, after approval

### A. Typed presentation and bounded subscriptions

Split Connected into small conversation, task/detail, attention/approval and result/artifact components, with pure view-model/reconciliation helpers and the existing generated DTOs. Retain the FE-00 light/blue styling and minimal layout; full PhaseUI, project switching, full management and advanced long-text navigation remain later work.

Keep a fixed bounded base subscription set (assistant, timeline, attention, tasks) for the connection. Do not call subscribe() when opening/changing a task, execution, approval or artifact. At this baseline subscribe() calls clear_cache(), which resets cursor and re-verifies admitted outbox rows; reserve that behavior for explicit rebuild/recovery. Selected details are bounded bridge_query reads, refreshed when the snapshot's already-present persisted cursor changes, on explicit open/refresh, and after relevant local commands. Expose cursor in the TS Snapshot type. Coalesce refreshes, ignore empty transactions that do not change relevant data where a lightweight projection version permits, and retain the last visible data during loading/error. Use generation + expected domain/instance/selection guards; old reads never overwrite current selection. Test that repeated selection switches retain timeline/cache/cursor, scroll and outbox admission states without new receipt verification. Add an inexpensive native projection-version notice if cursor-only refresh frequency is excessive; no second sync protocol. Stay below 16 windows and paginate explicitly. On reopen restore drafts and a versioned message-ID/relative-offset anchor through timeline/around (accept legacy numeric anchors as fallback), then reconcile work finished while absent. Preserve explicit jump-to-latest, selection and focus.

Expose connecting, catching-up, disconnected, authentication/domain/capability conflict, retry/error and stale projection states. Keep draft and intent visible on errors. Unknown states display their original value and disable state-dependent actions. Capability unsupported/not-configured/allowed=false prevents the affected action with a reason.

### B. Conversation and live preview

Render bounded timeline messages and activities with readable role/time/status, safe text/Markdown, and content continuation when incomplete. Reuse safe Message rendering where its contract fits; no raw HTML or new remote navigation capability. Input preserves Chinese IME behavior: composition confirmation/cancellation/focus transitions do not submit; an intentional send submits once through durable draft→outbox. Show local queued/admitted/uncertain status separately from the model/task outcome.

Treat transient as a full replacement snapshot, validate/narrow/bound it, and group blocks by preview call identity. The timeline currently mixes in-flight preview rows into message:<call_id>, while public messageView drops their running/truncated fields. Consequently Message.call_id alone does NOT prove durability, and even an empty assistant timeline row can be in-flight. Make a small additive API v1 correction: expose optional Message.persistence = transient|durable derived directly from timeline row.source, plus optional preview_status (running|saved|incomplete) and truncated for transient rows. Add these source-derived fields to timeline projection/messageView, schema and generated contracts/examples as applicable. They are projection metadata, not a new business state machine. Older/unknown contracts lacking persistence remain finality-unknown; never infer finality from text or call_id alone. A durable row replaces the same-ID transient regardless of fetch order; retain latest preview text while an in-flight empty row exists. Clear/dismiss interrupted transient honestly. Late transient cannot resurrect a finalized bubble; reconnect/instance change clears transient. Test mid-call durable invalidation, saved/incomplete previews, empty legitimate final messages, message fragments, restart and late snapshots. Prove exactly one durable final via independent journal main.message events and display_call_id, in addition to one rendered bubble. Do not invent finals for provider calls that legitimately emit none.

**Required bridge correction before UI integration:** sync_channel(2)/try_send currently overflows before the real 1-second IPC consumer drains it. Core activity.observed_at also changes every ~100ms, so idle streams churn too. Put the latest complete transient snapshot into a separately byte-bounded mailbox; preserve durable frame validation and use a bounded durable-hint queue with overflow→reconnect/catch-up. No silent dropping of unknown/invalid durable frames and no cursor advancement from hints. Use one scoped native bridge_transient read with domain/instance/epoch and monotonic local version, sampled at 250ms, reading only the small mailbox without the network/sync lock or full cache snapshot. Keep full/durable snapshots separate and coalesced. It exposes no token or arbitrary capability. Preserve byte limits, cancellation and honest connection status. Real bridge at the actual tick cadence must run against fixture Core for >=10 seconds, idle and with >=10Hz transient plus durable traffic; assert evolving non-null previews, no avoidable reconnect churn, bounded memory, durable convergence and final deduplication. Deliberate durable overflow and SSE cut still exercise honest recovery. No Core activity timestamp semantics change is required.

### C. Tasks, decisions and authorization

From conversation-generated work, show task ID, goal, proposal/acceptance information, request/execution IDs and current authoritative state. Selected execution shows result, conditions, cancellation status and unresolved operations, with refresh and a deliberate cancel action when supported. The optional viewed retention command is deferred; never submit it from refresh loops. If a TaskRequest is only admitted or waiting, label it as such rather than claiming an execution/result exists.

General user decisions/AnswerCommand are deferred; FE-02 implements the issue-required authorization decisions only. For authorizations fetch current detail, display the complete actual display payload/parameters, scope/root, revision, expiry and decision consequence. No approval based only on a short summary; oversize display (RESPONSE_TOO_LARGE) disables approval with its reason. Authorization.display is optional JSON: when required consent details are absent or cannot be interpreted, disable approval and explain the missing information. Never infer an authorization root from current UI selection. APPROVE/REJECT uses the inspected `expected_revision` and `display_hash`, with a deliberate click and durable pending state derived from unresolved outbox rows matching authorization ID, surviving reopen. Expose minimal bounded operation/target metadata for unresolved approvals if the current 50-row display window would hide them; do not recover pending state by parsing truncated body previews. Request IDs are generated/persisted by the existing bridge. Remembered permissions and rule management are outside this minimum scope.

On stale revision, changed hash, expired/resolved authorization or other domain refusal, preserve the original intent and visibly refresh the authoritative authorization. Do not silently change parameters or auto-approve the new revision. A new approval requires reinspection and a new deliberate action. Domain/instance/selection changes invalidate an open decision panel; receipt ACCEPTED is admission, not proof of authorized execution or successful work.

Cancel, checksum/length failure, missing content and quota failure remain visible and leave no successful-download claim or residual partial destination.
