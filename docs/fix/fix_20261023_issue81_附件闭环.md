## 3. 具体公共契约

全部沿用本机 loopback、owner 认证和 data-domain 边界，前缀 `/api/v1`；不通过 shell 处理路径，不给 task-only 调用者新增受支持的 owner 凭据传递路径。

| 操作 | 方案 |
| --- | --- |
| POST `/attachments/import` | `{request_id,source_path,expected_sha256,expected_bytes,name}`。UUID；绝对路径≤4096 UTF-8字节、无NUL；小写64位hex；正十进制字节数字符串；展示名1–255字符、无分隔符/控制符。返回202既有 Receipt，资源 AttachmentImport。 |
| GET `/attachments/{id}` | attachment_id/import_request_id/name/media_type/bytes/sha256/width/height/created_at/availability；bytes为十进制字符串，尺寸整数。仅最小元数据，无路径/base64；未知404。 |
| GET `/attachments/{id}/content` | 先核验长度和SHA，再返回原始不可变字节；octet-stream、attachment filename*、Content-Length、强ETag、nosniff、no-store；不存在/损坏410 ATTACHMENT_UNAVAILABLE；首版无Range。 |
| POST `/inputs/{id}/withdraw` | owner显式撤回，仅附件Input，新request_id+expected_revision；静止且无未决外部效果时允许，规则见5a；不用于停止正在生成。 |
| 既有 GET `/requests/{id}` | 导入进度/结果；COMPLETED给稳定附件身份，FAILED给稳定错误码；仅COMPLETED允许删源；导入pending期间保持QUEUED，不经过通用RUNNING/UNKNOWN。 |
| 既有 POST `/messages` | 保留必需text；允许空字符串搭配1–4个有序attachment_ids；数组可省略，禁止重复ID。text必须是精确空字符串或非空白正文，即使有图也拒绝纯空白。无正文无附件报错。正文在前，图片按数组顺序；不伪造正文。 |

导入ID与发送ID必须不同，使用既有全域冲突检查。同ID改任一字段（路径/名称/hash/长度/顺序）冲突。公共指纹保留完整body，所以省略字段与显式空数组重试仍可能冲突，客户端固定载荷；只有内部纯文本哈希将空附件归一为无附件。不同导入ID即使相同字节，也产生独立附件身份，可复用CAS。一个ready附件可以绑定多条独立消息，关系在各Input中，不维护“只属于一条消息”的可变指针。

202仅说明接收导入工作；只有对账到COMPLETED并取得ready附件元数据，客户端才可删除自己管理的源暂存。Core不删除源文件。此后重试/发送/历史/重启不依赖源路径。此前客户端保留快照；复制前崩溃且源变化或消失，可明确失败，但不能读取其他字节冒充原请求。

错误包含INVALID_REQUEST/REQUEST_CONFLICT、SOURCE_UNREADABLE/CHANGED、TYPE_UNSUPPORTED、INVALID_IMAGE、TOO_LARGE、CAPACITY_FULL、NOT_READY/UNAVAILABLE、MODEL_UNSUPPORTED（附件错误用ATTACHMENT_前缀），以及CAPACITY_BLOCKED。schema/auth/ID错误在准入前失败，异步导入失败持久记FAILED；消息失败不得留下Input/已接收回执。HTTP映射和可重试性文档化、测试化；不确定IO保留pending身份（导入不进入通用UNKNOWN），不宣称无影响。

## 4. 存储、校验、容量及崩溃边界

首批仅静态PNG/JPEG，以实际字节识别并完整解码，不信扩展名/MIME。增加固定版本sharp及lockfile，限制像素、完整解码检查截断/损坏、单帧，不改写输出。APNG解析PNG chunks拒绝acTL/fcTL/fdAT；拒绝JPEG MPO/MPF及PNG IEND/JPEG EOI后的尾随字节；JPEG必须解析marker/entropy边界，不能把元数据内部字节当终结。GIF/WebP/AVIF/HEIC/SVG/PDF等明确拒绝。保留原始字节（含可能存在的EXIF GPS等元数据）并原样交给所选provider，文档明确，不静默剥除/转换/缩放；实施验证sharp在两系统的实际行为。

提议默认：每文件5MiB，单边≤4096、总像素≤4,194,304；每消息最多4附件、原始字节合计≤10MiB；每Core域逻辑导入预留预算1GiB、10,000导入身份；单个有界导入worker。相同内容不同身份仍独立计费，物理CAS可去重。使用具名、启动时校验的配置并在能力元数据公布。这是导入限额，不承诺全部可导入图片都适合当前模型上下文。

路径读取使用fd/O_NOFOLLOW及适用的非阻塞打开，fstat确认普通文件后有界读取；拒绝目录、最终symlink、device/FIFO/socket、无权限/空文件/超限。允许父目录symlink（macOS的/var、/tmp即如此），不复用scopes.noLinks；只对最后组件O_NOFOLLOW。fd身份和预期hash/长度作为替换竞争的最终判断。比较读取前后fstat身份/长度/时间；观察到修改就拒绝。对即将复制的同一Buffer哈希。中文、空格、shell元字符均按字面处理。路径只留在私有命令数据，不进普通元数据/错误/日志正文。

新记录（保留独立Import以明确预留账本与约束）：AttachmentImport（不可变请求身份、预期digest/长度、预留字节、PENDING/READY/FAILED、预分配稳定附件ID、脱敏错误）；不可变Attachment（Store所属域/owner、导入ID、名、核验格式/尺寸、ObjectRef）。Input增加可选有序不可变附件快照和带版本完整内容digest；快照含ID、真实ref及元数据，由服务端解析，客户端不能提交CAS路径。源schema union、状态处理、Store重放/引用/身份约束、生成types完整同步，不改写旧记录。

1. 先验证schema/全域ID/容量，分配稳定ID，同帧提交Import PENDING预留+ApiCommand QUEUED。预留先于附件字节落盘，不能跨await持有同步withAdmission。PENDING用普通expected_sha256/expected_bytes字段，不能伪装成指向未存在文件的ObjectRef；全域ID也验证API与内部Host双向复用冲突。
2. 专用worker读取/校验有界字节，或核验预期hash对应的已写CAS；受限完整解码后调用现有CAS/fsync。内存一份文件Buffer及有界decoder输出；不扫描整个CAS。
3. 同帧提交Attachment、Import READY、ApiCommand COMPLETED/result/resource IDs。这才是正式交接。CAS已落盘但同帧未提交的崩溃，从预留的预期CAS身份重新核验并完成；CAS不存在才重读匹配预期hash的源，否则失败。
4. constructor的通用RUNNING/QUEUED循环和command()的通用queued分支都按attachments/import路由排除。只交专用串行worker，pending始终QUEUED，最终同帧直接COMPLETED或明确FAILED；不进入RUNNING/UNKNOWN/INTERRUPTED_DISPATCH。启动异步恢复pending，不要求异步代码先于同步constructor完成。IO/CAS/journal不明时保留QUEUED及预留，给有界诊断/暂停重试，或按Store损坏fail-closed，不虚报成功、不删可能有引用的CAS。其他命令策略不变。
5. 在Store.put内仅清理该调用分配的未提交临时文件，不删hash命名共享对象；保留写入/fsync失败证据。明确发生在任何CAS写入之前的校验失败，同帧FAILED并释放字节预留（身份保留且占数量）；CAS可能存在后失败仍保留预留，首版不自动回收。磁盘满/fsync/journal失败不得给成功回执。注明临时峰值开销与全Store磁盘容量不是同一配额。

重启从记录重建配额，包括pending；ready/unbound无过期删除。容量满拒绝新导入；下调限额低于已用量也只禁新预留。发送仍检查逐消息和模型预算。

消息准入先解析并验证全部ready附件/字节、模型能力、单次输入预算，然后通过既有admission同帧提交Input、input.accepted、内部receipt、ApiCommand。已接收消息重试应返回原回执，即使源已删/模型配置已变；不重新绑定。同ID并发不能产生重复导入或消息。

## 5. 身份、上下文、provider与恢复

## 5a. 存储与失败退出设计

图像aggregate请求/context/payload证据用版本化dehydrated CAS envelope：仅将识别出的图像叶子替换为真实不可变二进制ObjectRef，保留结构/顺序/其他字段，记录原始序列化body SHA与encoding版本。hydrate必须逐字节复原原JSON/hash（含dataURL MIME/prefix），不支持的encoding/hook改写拒绝。旧raw JSON继续读，logical request-key保持原语义，不能拿envelope物理hash替换请求身份。共享显式编码/解码helper覆盖ModelCall.request、model.payload、model.capacity_blocked及settings/summary/extraction aggregate evidence，核对全部reader。putMessages单消息CAS本身已去重，历史记录无需全改。附件原始ObjectRef保持Store既有校验；hydrate再验证所有叶子hash。重复含5MiB图的请求，CAS增量应随新文字/元数据，而非调用次数×图片体积；两adapter复原hash等于实际HTTP捕获。属于本项必要存储约束，不启动通用历史优化。

Store损坏边界：运行时读取缺失/截断/hash损坏均不发送且返回不可用；重新打开时，缺失/截断的已引用对象按既有规则使Store.open失败，不能承诺此时还有410服务。等长损坏可通过结构重放，但使用时必须hash失败。PENDING预期不是ObjectRef。不放宽Store不变量、不做修复服务/通用删除/损坏纯文fallback。

撤回提案（协调审批）：Input增加终态WITHDRAWN，不能冒充HANDLED；不可变原因/时间/命令证据及input.withdrawn事件。owner通过POST inputs/{id}/withdraw，新request_id+expected_revision；只允许附件ACCEPTED/CLAIMED，过期revision失败，同命令重放。纯文本状态机保持。新调度中附件Input单独成loop（最多4图），纯文批次在附件顺序边界截断，不改变旧恢复batch；避免图像把无关待办文字一起带入阻塞。

v1撤回收窄为该loop没有产生任何助手输出。真实CallState为PREPARED/IN_FLIGHT/RESPONSE_SAVED/INTERRUPTED/FAILED，没有UNKNOWN。串行检查/提交时要求Host active、maintenance/extraction空闲、无settings重建；CLAIMED还须session为RECOVERY_BLOCKED/CAPACITY_BLOCKED、claimed_input_ids精确[target]、active_loop_id等于input.loop_id，无IN_FLIGHT/RESPONSE_SAVED、无任何durable助手输出（包括尚未装进checkpoint的response），最新loop checkpoint的input后无assistant/toolResult，且该loop无pending/executed tool或未决Operation效果。其他均WITHDRAWAL_UNSAFE。不抹除INTERRUPTED尝试，不声称provider从未被调用；只放弃后续处理。tool迭代后换模型仍须恢复部署/既有恢复，不建设结果重建协议。

使用该loop最新checkpoint；失败在首checkpoint前则使用现有last_context_id的先前已完成历史。精确替换目标input为单个notice；从未插入时只追加一次。notice只有Input ID、有序附件元数据、“owner已撤回、不得执行”，不含原typed text/像素。通过不可变owning event/Context message ref和Input描述验证来源，不读取损坏像素、不跳过任意消息认证。先前已完成历史不变。ACCEPTED撤回只写Input/event/receipt，不清其他loop或无谓建checkpoint。
