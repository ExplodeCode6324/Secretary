## 4. 预算定义与初始配置

### 4.1 单一计算口径

在现有 `context.ts` 集中提供纯预算计算，实际调用、快照、触发判断和前台复用结果；不另建 token 服务或通用插件系统。

```text
C = effective_context_window
O = effective_total_output_ceiling_after_adapter_resolution
T = tool_growth_reserve
S = safety_margin
U = C - O - T - S
N = tokens(full_request: system + tools + memory + history + tool_results + envelope)
occupancy = N / U
```

- `C` 取已声明模型容量与部署/服务较低上限；分别支持 main/task 的配置，不把输入窗口当作输出上限。存在独立 input/output 上限的服务还须分别检查。
- `O` 是适配器最终发给服务的本次总输出上限，按该 API 语义包含共享额度内的推理。普通回复、摘要和承诺提取各自确定，不能先按 4096 检查再发送 16384，也不能把 Secretary 传给 `streamSimple` 的值直接视为最终值。保留“请求额度 / 适配后额度 / 实际 usage”三个字段，不能混用。
- `T` 只为尚未产生的工具返回预留；已存在结果计入 `N`。无工具的摘要调用不扣工具增长预留；未知工具返回最终仍须重新检查，不能依赖预留保证大小。
- `S` 为估算及协议开销的安全余量；与计数回退/校准各自目的写清，避免对同一项隐式重复扣减。
- 每个实际请求都校验 `N <= U` 及服务的独立限制，60%/80% 只是维护策略，不替代硬门禁。`U <= 0` 属配置/容量错误，不发送。
- `N <= U` 是本地策略门禁，不是未知服务必然接受的保证。主会话使用它触发维护；摘要和提取仅执行门禁，禁止递归触发维护自身。独立 input 上限也必须参与 usable budget 的计算，不能只在最后额外拒绝、前台却显示仍有容量。

### 4.2 建议初值（全部需要验证）

| 配置 | 初值 / 策略 |
| --- | --- |
| 普通压缩阈值 | `occupancy >= 0.60` |
| 强制检查阈值 | `occupancy >= 0.80`，在本次发送前同步判定是否须先压缩 |
| 压缩目标 | 默认完整请求占用 0.30，允许配置在 0.25–0.35；不为达到下限填充内容 |
| 摘要输出 | 首轮 16384，最多一次重试，目标上限 32768；同时受模型/服务输出上限、输入剩余容量和安全余量约束 |
| 普通回复 / 承诺提取输出 | 保留现有各自配置/4096 初值，纳入同一预算，不能全部升为 16384 |
| 工具增长预留 | 初始 4096 tokens，可配置；无工具请求为 0 |
| 安全余量 | 初始 `max(2048, ceil(C × 5%))`，可配置；此为保守起点，不能称已校准 |
| 工作记忆更新合并 | 确定性关键事件在安全边界合并处理；普通会话累计 8 个完成回合或首个未覆盖完成回合等待 60 秒即到期，但普通更新启动间隔至少 120 秒；关键事件可绕过间隔，仍合并已到达事件。均为待验证初值，详见第 5 节 |

明确校验 `0 < target < normal < forced < 1`，预算均为有限合法整数或比例。不接受 NaN、负数、0 容量或关系倒置，不静默改为 1M。新参数纳入运行配置指纹及文档，初版采用部署配置，不扩建设置 UI。

旧 `SECRETARY_COMPACTION_BYTES` 不再自动控制完整压缩；显式设置该旧变量时给出废弃说明。旧 `SECRETARY_COMPACTION_OUTPUT_TOKENS` 可保留作为首轮输出配置入口，默认值改为 16384，明确与重试上限的关系。不能同时暗中启用旧字节阈值与新比例阈值。

服务容量未声明时，显示“使用模型注册配置，服务上限未核验”；缺少有效模型容量则明确阻塞。若服务实际拒绝容量，记录与当前配置冲突，暂停相同请求自动重试并提示核对上限，不能悄悄假设更大的窗口。

### 4.3 计数与校准

1. 计数针对传给 provider 适配层的完整语义请求，包含有效 tools；同时考虑模板/角色/协议封装。当前 Pi 的 `TranscriptContext` 不含顶层 tools，声明在 system 的 `toolsAdded/toolsRemoved` 中，必须按真实接口重放有效工具集，不能再把同一声明作为顶层字段重复计费。声明前 CHECKPOINT 不冒充已归一化 MODEL_REQUEST。只有已验证匹配模型及模板的路径才标为准确计数，其余标估算。
2. 当前 Secretary 没有 tokenizer 实现。优先对实际配置模型寻找可信映射/官方 tokenizer；若必须引入依赖，应先说明包、覆盖范围、离线资源和维护成本，不按模型名字猜用另一家的 tokenizer。本次计划不预选尚未核实的第三方包。
3. 无匹配 tokenizer 时，对文本/JSON 使用保守 UTF-8 字节计数加封装开销回退，并标记方法；不再把 `/3` 粗估称为精确。不可识别的非文本负载没有可靠估价时阻塞或要求支持的计数路径，不默认为零。
4. 服务 usage 只作为对应已完成请求的观测。按 adapter 语义处理 input/cacheRead/cacheWrite，不盲目相加导致双计数；下一请求仍重算变化部分。
5. 校准按 provider/API/baseURL 配置身份、model、模板及工具 schema 区分；维护有界统计，模型切换清除不适用参数。观测只允许保守修正本地预测，不因一次低用量就降低安全边界。
6. 即使有 tokenizer，provider 封装仍可能不透明；不能承诺在缺少服务计数接口时得到供应商逐 token 完全相同的结果。验收分别记录方法、偏差及容量拒绝情况。

### 4.4 适配器最终请求核验

P0 检查实际安装的 `@earendil-works/pi-ai`，不要只看本地 `roleModel()`。已核实 `dist/api/simple-options.js` 有独立估算与输出钳制，`anthropic-messages.js` 的部分路径会增加 thinking 预算，`openai-responses.js` 有最小输出额度且可能因 compat 不发送输出字段。

初版只为实际使用且已验证的请求路径建立参数解析与最终校验。若保留 Pi，可用其公开 payload/fetch 钩子或显式参数 API，但必须验证执行顺序、抛错传播和重试行为；也可由 Secretary 主会话直接构建受支持服务的请求，使预算和发送共用同一解析结果。无需先尝试迁就 Pi 再获准使用自有流程。最终 payload 若与预算不同，发送前重新核验或阻塞，不得静默偏离。保存脱敏的参数事实及 schema/hash 引用，不保存鉴权 header。服务忽略输出字段或无法确定上限时，必须有经验证的服务配置上限，否则可见阻塞。用本地 HTTP 捕获端证明线上字段与预算一致，单纯 mock `StreamFn` 不足以覆盖此项；未改造的 task/Pi 路径仍独立验证。

## 5. 工作记忆与上下文压缩分离

### 5.1 复用数据模型，分开持久化边界

复用 `CompactionJob` 生命周期，增加向后兼容的可选维护类型，例如 `WORKING_MEMORY` / `CONTEXT_COMPACTION`，保留历史 job 缺字段时的旧语义；设置应用继续使用 `SettingsApplication`。不新增独立维护服务或平行队列。

`Consciousness` 分别记录“记忆已消费到的事件边界”和“历史已允许裁剪的来源/完整回合边界”。实现前在 canonical schema 固定字段：维护模式、记忆来源终点、压缩来源清单/终点、策略版本、基准 revision、候选阶段与结果引用。名称可随类型约定调整，但两种边界不可复用同一游标。`last_job_id` 的旧义必须有兼容读法，不能让一次增量更新覆盖原裁剪依据。旧 journal 不重写；原 CAS、Context 和完成证据不可变。

覆盖范围按 session、事件类型与完整回合确定，保存来源清单和终点；不是把全局 `source_end` 前所有事件自动视作已处理。同文消息也可能是不同事件，不能只按内容 hash 判定已消费。工作记忆只能推进实际完整处理的来源；压缩边界不能越过尚未进入成功记忆的来源。兼容读取旧 `last_job_id` / `covered_message_hashes` 后，新提交使用明确的新字段，设置重建也要同时初始化两类边界。类型及文档从 `src/contracts/contracts.schema.json` 生成。

### 5.2 工作记忆更新

- 主会话完成、新 task 结果/反馈、Master 决定、承诺状态变化等已有事件进入待处理增量；以固定事件终点和基准 revision 创建一次工作，已覆盖材料不重复摘要。
- 类型明确的关键事件优先，以现有任务反馈、显式决定/承诺状态事件为准。自然语言中的“重要决定”没有可靠的现成事件标签：初版由全部新增完成回合的批量更新兜底，允许按上述间隔延迟，不声称即时识别。暂不新增主回复标记协议或分类模型，也不靠关键词排除其他回合；若要保证自然语言决定立即整理，另列扩展范围。
- 普通回合按第 4.2 节合并；即使上下文不到 60%，也更新 Consciousness。接受输入本身不算已完成回合，任务重放不重复消耗额度。
- 只提交记忆增量与覆盖边界，不推进历史裁剪边界；下一请求替换唯一的工作记忆头，保留此前对话与完整工具协议对。避免把更新记忆变成隐式全量重建。
- 在现有 Host 中补齐主会话/维护/设置的互斥，不假设当前已具备。普通维护在完成回合边界执行；到期后在领取下一批输入前检查一次，不能只等 `drain()` 清空整个队列。维护期间可接收新输入但不启动新主回合；单纯新增 ACCEPTED 输入不使固定旧范围失效，后续增量再处理。基准记忆、所选来源、设置或已使用的任务/承诺事实发生冲突才 STALE。提交重新核验这些版本；等待和退出可取消。按到期状态调度，不每次 UI pump 创建 timer/job。
- 保留独立 `extractNewCommitments` 和宿主账本校验；原始引文是证据，不恢复字符串强制匹配保留机制。

### 5.3 上下文压缩

- 60% 到 80% 之间，在安全边界计划普通压缩；达到 80% 则在本次请求发送前执行容量评估，必要时压缩后重算；跳过阈值直接超限的单条输入同样受硬检查。
- 先检查计划移出的历史是否已进入成功工作记忆。已覆盖时直接构建更短请求，不再调用摘要/提取模型；未覆盖时只处理缺口。若已有摘要本身偏大，允许单独执行有界缩写并记录原因，不能默认重新摘要全部原始历史。普通更新和强制压缩同时到期时合并成一次来源处理，分别记录记忆提交与裁剪结果。
- 主会话每次请求前进入统一准备步骤，可使用 `prepareRequest`，也可由 Secretary 自有循环调用。不能直接调用当前只允许 IDLE 的 `maintain()`，也不能等待当前 loop 自身 `drain()`。抽取固定来源的维护步骤供安全边界调用，transport 保留最后门禁。主会话的新回合、工具返回后的继续请求都必须覆盖。
- 压缩固定范围的较老、完整回合；保留近期原文、未完成工具调用/结果配对、工作记忆、承诺账本、显式约束和证据引用。按 token 预算选择近期回合，而非固定若干条消息。
- 先用候选构造完整下一请求并计数，再原子提交压缩边界和关联上下文。记忆摘要本身不追求占用 30%；总请求不足目标则不补内容。
- **恢复检查点与请求投影分离。** CHECKPOINT 保存完整恢复材料，MODEL_REQUEST 保存实际发送材料/工具及所依赖的检查点、记忆和裁剪版本。新输出继续追加到恢复证据。重启先用原检查点对账工具，再按已提交裁剪边界恢复请求投影，不能误把短请求快照当作未完成 loop 的恢复基线。若继续使用 Pi，活跃 loop 的 `agent.state.messages` 保持顺序及旧工具键语义，`prepareRequest` 返回独立投影；只在结束旧 loop、开启新 loop 时实体化短历史。若采用自有循环，可用持久化调用身份替代位置键，但必须提供旧未完成 loop 的兼容对账并测试迁移，不能简单更换 key 导致重新执行。选择哪条路径，都先用多轮工具/崩溃测试证明安全。
- **初版继续保留原始 Master 输入约束兜底。** 如果这些内容加 system/tools/未完成协议本身已超过目标，显示“保留内容使压缩目标无法达到”，记录实际占用；仍在安全预算内可继续。若超出硬预算则 `CAPACITY_BLOCKED`，保留输入和证据，不能静默丢原文或伪报达标。将来若要减少此类保留内容，另行评审约束提取的可信度。
- 对同一来源/策略/基准的无效压缩或失败去重；只在新增可压缩材料、政策/容量改变或显式重试时再次尝试，防止残留摘要偏大导致每轮重跑。
- task 模型同样经过完整请求硬检查，但本 issue 不顺带引入新的 task 自动记忆压缩策略。task 超限必须形成可恢复的明确状态/失败原因，不重放不确定外部效果。
- 初版 task 沿用现有 Execution 终态机制，保存最新检查点及结构化 `CAPACITY_BLOCKED` 原因，不把它变成新的自动重试状态；后续由已有显式恢复/续作入口处理，并保持 `RESULT_UNKNOWN` 的阻断规则。主会话恢复也必须重算原 CLAIMED 批次，不能通过重新 accept 输入或更换 loopID 重放已执行工具。

## 6. 摘要预算、分段与失败

- 普通记忆更新、容量压缩、设置整理复用同一套摘要预算/长度校验，保持各自业务提交方式。小的共同函数即可，不抽象成新框架。
- 除单字段上限，增加整份候选摘要的 token/字节总目标和宿主校验。初始正文目标不超过本次可用输出的约 50%，再按材料量、系统/账本空间缩小；剩余用于推理和完整 JSON。该比例是待校准上限，不能保证任意服务的推理开销。
- 每次摘要输入也算完整请求：已有记忆、承诺、system、当前材料、错误说明均计入。按可用输入预算拆分材料，复用设置摘要的候选分段/检查点机制，保存覆盖引用；不能沿用单纯固定字符宽度判断输入一定能装下。
- 分段前固定来源清单、输出首轮/重试额度及上界，并按较大输出额度预留输入空间和有界错误说明。冻结本 job 的候选记忆/账本输入上界，各段提交后仍重算下一段；若连“已有记忆 + 必须账本 + 最小片段”都放不下，明确停止，不能丢 OPEN 承诺来挤空间。重试输出不能提高到会挤出同段来源的数值，低容量模型可使用较低上限并记录原因。
- 长单条材料分成带来源/偏移的可追溯片段，避免 UTF-8/代理对切断和空片循环；摘要逻辑不把 tool 输出变成命令。巨大工具结果先持久化完整证据，再决定分段/引用或阻塞。
- 一份固定材料的每个摘要分段最多首轮加一次重试；分段数在启动时按固定来源及预算确定，不能在失败后无限拆分重试。每个 job 另设总分段数/调用数/耗时上限，由 P0 在配置中冻结；超出时停止该维护工作并报告，不自动新建 job 绕过限制。失败去重不能只看最新全上下文 hash：保存失败范围和策略身份，新消息不能使同一失败前缀无限自动重跑。
- 截断、JSON 无效、空摘要、总目标超长分别记录原因。第二轮带上有界原因，缩短输出目标/重复提示并在允许范围内提高输出；不能删除未处理的来源却仍推进整段覆盖边界。预算被输出上限钳住时不能仅原样再请求。非正常 stopReason、errorMessage、意外 toolCall 均不得作为完整摘要接受。
- 两轮失败、容量不足、来源过期均不覆盖上一份成功 Consciousness，不推进覆盖边界、不删除材料。承诺提取仍遵循现有单次调用规则，不借此给它另加重试。
- 摘要候选通过后才进入独立承诺提取阶段；按 job/来源分段/策略身份持久化提取尝试和结果，再做宿主来源校验。已完成的提取在恢复时复用；失败或无法确定是否已完成的提取不由外层摘要重试再次发起。跨分段引文必须能映射回完整原消息，不能把缺少条件的半句作为承诺。摘要候选、提取结果和当前 revision 全部通过后才整体提交；阶段检查点不是成功记忆。
- `durableStream` 当前存在 120 秒上限：较大输入/输出可能增加超时，需要在真实验证中测量。初版保留有界超时；若必须调整，应按用途显式配置并测试取消/退出，不直接改为无限等待。

## 7. 保存、恢复与设置兼容

1. **持久化检查点不等于获准发送。** 完整输入、工具结果和恢复证据须先持久化，即使超预算；只在 MODEL_REQUEST/发送处阻止超限请求。更新 Context 契约说明、调用点和测试，避免工具已经执行却因保存 Context 抛错而丢失结果线索。
2. 新 Context 可选记录计数方法、有效容量、可用预算、各类 reserve、适用模型/策略身份、完整工具 schema 引用；兼容保留旧 budget/estimated/reserve 字段，旧快照显示“历史粗估”，不伪装为新计数。
3. 设置变更与模型切换仍先摘要、校验、提交、重建；低于 60% 不允许跳过。`prepareSettingsContext()` 当前依赖 `saveContext()` 做容量检查，解耦后必须补显式候选预检，计入新 system、完整 tools、输出额度和保留原文，并在 World Model 外部提交前完成。缩窗重建按目标模型验收，不能依赖旧模型可装下。提交前失败可保留旧记忆并由操作员恢复原配置；已有 World receipt 后失败只能 BLOCKED 并完成对账，不能宣称自动回滚外部事实。
4. 处理 `runtimeHash` 迁移：采用版本化策略指纹；升级前检查未完成设置应用，优先用原版本/原配置完成或显式处理后再升级，不实现通用旧策略解释器。新进程遇到旧未完成应用应给出可执行恢复说明，不能仅建议把环境变量设回旧值（代码改变 hash 结构后可能仍不相等）。首次新策略激活沿用设置协调器完整重建；不能自动丢弃旧应用或误标为 APPLIED。
5. 新普通维护采用固定 source_end、revision、模式和策略身份去重；中断后沿用可解释的 FAILED/中断状态，只有完整候选且校验通过才能提交。测试 kill/restart 不重复发送工具、不覆盖更晚的记忆。
6. 旧代码对新可选字段也可能因 `additionalProperties:false` 拒绝读取。因此上线回滚不能只换旧 JS：先保留完整部署前快照；新写入后回退需兼容读取版本，或明确使用隔离旧快照验证，不能覆盖运行中产生的新历史。

## 8. 活动、容量显示与性能控制

- 活动分别显示“更新工作记忆”“压缩上下文”“重建设置上下文”；重试展示真实原因及次数，例如“重试 2/2：上次输出超长，正在缩短摘要”。从 job/设置事件恢复模式，不仅依赖进程内标签；旧任务标为旧式整理。
- Web/TUI 展示最近快照/下一请求估算的明确范围、计数方法、使用量/可用输入预算、reserve 和服务上限状态；服务实测附对应请求，不把旧 usage 当当前精确值。详细口径放展开说明，避免增加常驻无用文案。
- 后端只在请求构建、内容变化或维护决策时计数；前台轮询只取已有摘要状态，不能每 700ms 重新读取和 tokenize 全历史。
- 普通更新的 due 时间、最后一次尝试、失败来源均从持久化事件/job 派生；重启不重置节流、不自动重试失败前缀。无新增来源时计时到期也不调用模型。新增记忆头使占用越过阈值时，在同一安全边界安排一次压缩，避免两个维护工作交替重复触发。
- 利用现有 source refs、序号、CAS hash，增量选择未覆盖事件。计数结果按模型/工具/材料身份复用且有界；不新增一套全正文缓存、合并索引或数据库服务。校准只维护少量按配置分组的统计。
- 对分词不具可加性的拼接和模板，发送前最终检查完整请求，不能简单累加消息缓存声称精确。测量最终扫描成本，而非承诺其对历史长度恒定。
- 压缩延迟后请求正文和日志会更大：同时测量计数/序列化、CAS 写入、事件循环阻塞、峰值堆和总维护成本。原有 Web 200 项/1MiB 单页、2000 项缓存/150 DOM 边界不变。
