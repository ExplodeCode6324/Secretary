## 1. 已确认需求与默认边界

Master 已确认：

1. WebUI 提供 World Model 增删改查。
2. 支持保存待应用修改，再一键统一生效。
3. 生效前强制摘要当前 context 与 consciousness 中全部未摘要内容，然后初始化 context。
4. 删除采用撤回：原记录和证据保留在原 PostgreSQL 库中，事实状态改为 `RETRACTED`，退出当前有效查询；不物理删除。更正保留旧版本，旧陈述标为 `SUPERSEDED`。
5. 后续所有需要新设置生效的场景遵循同一规则，并在开发测试后核对全部项目文档与代码。

本计划采用以下实施默认值，供 Master 审阅：

- 管理对象以事实为核心，提供实体创建、查询、修改和停用；实体类型保持不可变。停用前列出有效事实与关系引用，有引用时阻止停用并提示处理，不静默级联撤回。
- 提供当前事实、历史版本、来源、证据、冲突和操作结果查询；历史查询必须包含已过有效期的记录，不能只打开状态过滤却继续排除历史时间范围。
- 事实属性使用已有 predicate 目录和约束，页面按类型编辑。暂不提供任意 SQL、动态修改 predicate 定义或物理清除历史功能。
- 页面操作由后端记录 Master 来源与证据。点击应用即明确提交该批变更，不要求到另一张授权卡重复确认；模型提案仍走原授权规则，不能伪造 Master UI 身份。
- 本次将已有 Secretary 说明设置迁移到统一生效流程；界面主题、布局等仅显示设置不触发摘要。运行中任务继续使用原执行快照；主会话重建不自动重启或重新执行任务。
- 授权撤销、安全阻断继续立即检查，不能等待摘要。未来新增影响模型行为或认知的设置必须声明作用范围、是否需要重启以及如何接入统一生效流程，不能只约定下一轮读取新值。

## 2. 实施前事实与差距（基线记录）

- `world.ts` 已提供事实 ASSERT / CORRECT / RETRACT、实体登记和来源登记，以及 CAS、证据、回执和 outbox；没有完整管理页或草稿批次机制。
- `World.read()` 当前最多返回 100 条，未向调用者提供完整分页和历史管理能力。
- `host.ts` 的整理入口主要从 `pending_raw_refs[0]` 获取材料；整理期间新增输入会使候选过期。
- `history()` 在摘要后保留原始用户输入；该机制不等同于新设置应用后的上下文初始化。
- `/api/instructions` 直接保存说明并在下一轮使用；需要替换为待应用版本与有效版本分离。
- PostgreSQL 和 Store journal 是两个持久化域。现有 outbox 提供可恢复桥接，不提供跨域原子提交。
- `docs:check` 主要检查链接、迁移目标和部分测试隔离规则，不能证明文档行为与代码一致。
- 工作区已有 README 修改及未跟踪测试材料；本任务保留它们，不覆盖或清理其他工作的内容。

## 3. 统一生效协议

### 3.1 草稿与生效版本

- 草稿持久化，和当前有效设置分开。多个页面使用 revision 检查，禁止后保存者覆盖前者。
- 同一批可以包含多项 World 修改及 Secretary 说明修改；应用时固定批次内容与哈希，之后的编辑进入新草稿。
- 幂等键相同且内容相同返回原操作；相同键不同内容报冲突。
- 页面区分草稿、待应用、正在应用、已生效和失败状态，显示有效版本及失败原因。
- 无变化的应用返回明确的无变化结果；没有未摘要内容时不强行制造模型调用，仍校验覆盖边界并完成必要重建。

### 3.2 会话边界与摘要覆盖

1. 持久化应用请求，停止主会话领取后续输入，等待当前轮次在安全边界结束。不直接丢弃正在进行的模型调用或未配对工具结果。
2. 如当前轮次存在未解决恢复问题，应用请求进入可见的等待或阻塞状态；不绕过原恢复守卫。
3. 固定本次上下文、记忆版本、事件截止序号及设置基线，构造 context 与 consciousness 全部未覆盖材料的去重清单。
4. 新消息、任务反馈继续可靠接收，归入边界后的待处理队列；它们不无限使本次摘要过期，也不能被误标为已摘要或已处理。
5. 强制摘要绕过大小阈值。超出单次模型容量时分批整理，保存覆盖清单与中间结果；不得静默截掉尾部后标记全部完成。
6. 原文和工具输出保留可追溯对象。既有承诺、未解决冲突和必要的 Master 约束有明确承接记录；模型遗漏不能删除宿主持有的义务。
7. 验证候选结构、引用、来源覆盖与版本，区分材料覆盖完整和模型语义质量，不把结构校验当作语义无损证明。

### 3.3 提交、重建与知识更新

1. 摘要候选成功后，再提交有效变更。World 批次内的有效数据写入采用同一 PostgreSQL 事务；任何条目冲突时不部分应用该批事实。
2. 事务保存批次标识、请求哈希、回执与 outbox。Store 保存相应阶段和候选引用，恢复时先查回执再决定下一步。
3. 数据库已提交而 Store 未完成时，阻止主会话恢复并继续完成桥接与重建，不报告为全部未应用，也不盲目重做写入。
4. 同一批 Secretary 说明和 World 修改在运行时使用同一个生效边界，避免主会话看到混合版本。数据库直接读到已提交记录不代表整批已完成；UI 同时显示应用阶段。
5. 重建包含当前系统说明、有效设置版本、整理后的工作记忆、稳定承诺与必要约束，以及本次 World 更正和撤回信息。
6. World 修改与旧摘要中的相关陈述对齐：明确替代关系和撤回含义，防止旧摘要或保留的历史输入继续被解释为当前有效事实。撤回不生成相反事实。
7. World 仍按需读取，不能为了初始化把整个数据库装入 context；提供本次变化及必要引用，并记录实际使用的版本。
8. 新 context 持久化且生效版本可核验后，标记应用成功，恢复处理边界后的输入。历史 Context、聊天记录、任务和证据不清空。

### 3.4 失败、恢复与其他入口

- 摘要失败或写入前的版本冲突：保留原有效设置与 context，草稿和失败记录可重试；不显示成功。
- 写入开始后的中断或结果未知：先核对持久回执，必要时保持会话阻塞，完成确定性恢复后才允许继续。
- 取消仅在尚未提交有效变更的安全阶段开放；提交后不能将取消伪装成回滚。
- 自动摘要、手动 `/compact`、设置应用共用协调机制，不能并发覆盖记忆或互相吞掉工作。
- 检查 TUI、Web API、模型提案、World drain 等入口；有效设置写入不能从旧路径绕过新协议。后台事实提交与人工应用之间建立确定顺序，防止摘要和重建期间穿插未纳入版本边界的变更。
- 纯粹的例行工作记忆整理无需修改设置，但必须遵循同样的覆盖和恢复要求。设置回退本身是一次新的设置变更，也走统一生效流程。
