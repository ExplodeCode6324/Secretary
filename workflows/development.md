# 常规开发

1. 从 issue 的验收条件出发，检查已有实现、相关计划、调用方和测试。区分要交付的功能、明确排除的范围与仍需 Master 决定的事项。复用已有实现和可核实的历史证据，写明其版本和覆盖缺口。
2. 核对远端 main、当前工作树和未保存修改。从最新 main 建立本轮 `codex/` 分支，PR 指向 main。已有 PR 按其原目标继续。涉及独立 benchmark 工具时，通用 runner、原生目标适配和可复现实验入口放在 secretary-benchmark，Core 计划与结果放在本仓库。
3. 按 [docs/fix 命名约定](../docs/fix/README.md) 写中英文计划，列出正常入口、受影响合同、测试范围和数据恢复方式。将工作拆成可分别验收的工作包，为每包写明交付物和验收条件。标出哪些包可并行、哪些包互斥并说明原因；有前置依赖的包写明执行顺序。按[复核流程](review.md)取得计划结论。Master 要求只交方案时在此交付。常规实施须有 Master 的实施授权；已明确“通过后直接实施”时沿用该授权。
4. 按批准范围实施，记录关键取舍、涉及文件、实际命令和偏差。低成本、可逆且影响可控的细节由执行者判断，简记理由。新范围、数据迁移或不可逆处置交 Master 决定。

   Master 在任务开始前明确指定采用“调度 agent + 编码 agent”时，按以下分工执行。例如，可由 Codex 调度，其他 CLI agent 编码。

   - 调度 agent 按计划分派工作包，可并行的包同时开展，互斥的包错开执行，有依赖的包在前置交付就绪后开始。
   - 编码 agent 在一个独立 session 中完成一个工作包，提交该包的实现和测试证据。下一个工作包使用新 session。
   - 调度 agent 检查各包的实际改动和测试证据，按计划逐包验收，并验证各包合在一起后能从正常入口工作。

5. 从正常入口验证。功能逻辑运行 correctness，记忆机制运行 memory benchmark 和相关 correctness 回归。跨范围两者都运行；文档变更检查链接、命令、配置入口与项目文档检查。必需 CI 照常运行，范围外记 NOT_APPLICABLE，应测缺证记 NOT_TESTED。
6. 推送任务分支、创建或更新 PR，按[复核与验收](review.md)交付。合并后核对目标分支 CI。释放专用 checkout 前核实本地修改、子模块、忽略文件和证据归属。

## 隔离 benchmark

只从非部署检出通过 `npm run benchmark -- ...` 管理其自建的 `.local/benchmark/`、PG 和证据。先按本轮计划核对数据归属、实际 provider/model ID、冻结版本、请求及重试边界，分别配置工作负载和独立评分器。真实派发按当轮授权执行。程序 fixture 和真实模型测量分别报告。

测试凭据保存在私有、Git 忽略的测试凭据目录，目录 0700、文件 0600。测试结束后确认设施已停止、归属清楚及 NAS 已挂载。本地打包为 tar.gz，复制到指定备份位置，逐成员读回核对大小与哈希后释放源数据。保存清单、回执及恢复方法。保留活动设施、未知或混合数据和单独管理的凭据。

#122 的原始测试矩阵以 DeepSeek V4 Flash 或官方可用的 Flash 后继为必测主组，GPT 6 Luna、GPT 6.2 Sol 为对照。对照额度耗尽时登记实际运行、用量和未测原因。冻结请求 ID、日期、公布及返回的服务身份，跨版本分列。阶段 B 已批准的凭据和费用口径限于当时冻结；原生系统对照依当轮批准的模型与条件分组。连接故障先做有界端点检查，记录错误类别，保持全局路由与敏捷配置稳定。探针和真实 workload 分别记录。

测试凭据目录为非部署开发检出的 `.local/test-credentials/`。凭据、DSN、原始对话及本地路径不得进入提交或模型上下文。归档使用 Master 指定且已验证挂载的私有 NAS 目录；机器上的实际路径由本地归档配置提供。
