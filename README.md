# Secretary

Secretary 是面向 Master 的持续个人助理。当前已完成基本架构搭建，基于固定版本 Pi 实现唯一主会话、任务调度、执行 Agent、授权、工作记忆、可选 PostgreSQL World Model，以及 UI 无关的 Core API v1。SwiftUI 仍在后续实施阶段，旧 TUI/WebUI 不兼容新版服务。当前仍处于原型完善阶段。

## QuickStart

需要 Node.js ≥ 22.19、npm、Python 3；可选 World Model 使用 PostgreSQL（本仓库验证环境为 18）。从仓库根目录执行：

```sh
git submodule update --init --recursive
npm ci --ignore-scripts
npm start
```

默认使用离线 fixture 模型。`npm start` 启动独立 Core，不打开 UI；`npm run core -- status` 查询，`npm run core -- attach` 附着，`npm run stop` 显式停止。客户端退出不停止 Core。结构化请求、认证、数据目录、迁移与回退见 [API v1](docs/api/v1/README.md)。

真实模型入口 `npm run start:live` 沿用本地独立 main/task 密钥和运行配置，启动 Core，会调用真实 API。本分支已使用隔离合成数据进行有界真实模型验证；初轮为部分覆盖，已补齐同任务真实工具执行、API 产物下载与独立验算，并通过整理后 OS 进程重启真实回忆场景，具体覆盖边界与保留失败见 [API v1 验证记录](docs/api/v1/verification.md)。live wrapper 默认使用 `.demo-data/interactive-live`，停止时使用 `SECRETARY_MODE=live SECRETARY_DATA=.demo-data/interactive-live npm run stop`。未部署现有实例。旧 Web/TUI 启动方式及 macOS 双击 UI 入口不适用于新版服务，源码清理由 #10 完成。

```sh
npm run verify
npm run test:issue5
# 当前 SECRETARY_DATA 对应的数据目录，默认 .demo-data
npm run stop
```

Core 保留任务、审批、工作决定、Settings/World、记忆恢复和活动/时间线能力，均通过新版结构化协议访问。本分支已实现 [#9 持久 ChangeFeed 与通知回执](docs/api/v1/sync.md)，需显式初始化；原生客户端属于 #10，不提供新的 TUI。

## 开发路线

### 当前基础：原型架构已搭建

Secretary 的原型基础已搭建，当前仍处于架构、可靠性与日常使用体验的完善阶段，不能将基本流程跑通等同于最终产品完成。

任务系统已支持已结束任务的同任务接续：查询原任务后提交新的执行要求，保留工作目录、执行记录与产物证据；独立任务仍有独立工作区。验收方式见[任务复用验收](docs/testing.md#任务复用验收)。

### 后续软件完善

以下是继续完善的方向，不表示所列能力均已实现。

#### 架构与交互

1. **完善 task（任务）系统**：继续验证日常使用中的任务归并、长任务接续与失败恢复边界。
2. **改进 system prompt（系统提示词）**：进一步突出 Secretary 的架构特性、主会话职责和模型需要重点关注的内容；结合实际模型能力与可用上下文预算，提升需求理解、工作组织和授权范围内的主动推进能力。
3. **主会话工具与原生客户端**：继续补充工具能力；以 SwiftUI 原生薄客户端为主要交互方向，按[总路线 #7](https://github.com/ExplodeCode6324/Secretary/issues/7)先完成 Core 公共 API 与可靠同步，再完成原生迁移。所有客户端的数据、命令、事件、游标与回执统一按新版协议设计；迁移完成后不兼容旧 TUI/WebUI 的路由、文本输出或缓存，不建设长期兼容层。迁移中的旧客户端也不要求适配新版 Core；切换前保留旧版本作为回退基线，历史数据转换、证据保留与回退单独验收。新版 Core 已停止提供旧 WebUI 协议；旧运行版本可以作为独立回退基线保留，旧界面源码清理由 #10 完成，不将规划或客户端迁移等同于后端能力已经完成。
4. **优化 agent loop（智能体执行循环）**：使执行循环更适配 Secretary 的工作模式。
5. **完善 online（真实模型接入）回归用例**：覆盖更接近日常使用的场景，持续衡量行为稳定性。
6. **可选新版 TUI（后续，暂不实现）**：未来如保留终端交互入口，必须使用新版 Core 公共数据协议、身份、命令回执和同步机制；不解析旧 Web/TUI 输出，不直接访问内部 Store，也不建立另一套业务状态。新版 TUI 不属于本轮迁移的交付或验收前提。旧 TUI 启动入口随迁移退役；Core 启停、状态和必要排障由独立管理入口提供。

本轮实施按 [#8 公共 API](https://github.com/ExplodeCode6324/Secretary/issues/8)、[#9 可靠同步](https://github.com/ExplodeCode6324/Secretary/issues/9)、[#10 SwiftUI 基础迁移](https://github.com/ExplodeCode6324/Secretary/issues/10)、[#11 Portable](https://github.com/ExplodeCode6324/Secretary/issues/11)、[#12 EVENT](https://github.com/ExplodeCode6324/Secretary/issues/12)、[#13 远程工具](https://github.com/ExplodeCode6324/Secretary/issues/13)推进；设备展示与模拟验收由 [#14 配套工作包](https://github.com/ExplodeCode6324/Secretary/issues/14)承接。每阶段先提交 `docs/fix/` 计划，经 Master 授权后实施。

客户端遵循[页面、组件与行为规范 v0.3](docs/native-client-design-v0.3.md)：顶部纯文字名称与栏目、连续对话阅读区、较小默认字号（正文 13 pt）及可收起的窄右栏（默认 200 pt）。取消固定三比一分栏，把剩余宽高优先留给对话；补齐待处理入口、记忆/产物完整页、关联查询及能力/错误状态。尺寸与字号是待实际 macOS 验收的设计起点，不表示客户端已经实现。

#### 日常使用能力

- **World Model 内容导入**：支持从社交软件内容中导入人际关系信息，以及从 GitHub 等仓库状态中补充相关认知。
- **移动应用与语音输入**：扩展日常交互入口，并与下述便携设备规划衔接。
- **生命体征监测**：作为长期设备能力探索，设备关系与紧急告警边界见下文。

### 长期规划：设备与产品形态

设备按 Core、touch agent 与 Secretary Portable（便携设备）的关系规划。Portable 包含以下三类设备，共同服务于主助手，不是三个平行主助手。以下均为尚未实现的产品设计，验收目标须经原型与实测验证。

| 分类与从属关系 | 部署与职责 |
| --- | --- |
| Core（核心主机） | 运行核心服务，保存权威状态。 |
| touch agent（受管设备协助端） | 部署在其他机器，按授权监测设备活动并协助 Master 工作，作为主助手委派的设备执行端。 |
| Secretary Portable：internet portable（互联网便携终端） | 日常互联网连接与远程交互入口。 |
| Secretary Portable：internet portable 下属生命体征监测设备 | 向所属互联网便携终端提供监测数据；不默认拥有 root（系统最高权限）或任务执行权限。 |
| Secretary Portable：LoRa（低功耗远距离无线通信）应急终端 | 独立的短指令与状态通信终端，与日常互联网便携终端分工。 |

#### 客户端、状态与本地模型

- **薄客户端**：客户端主要承担交互，由一个主客户端和若干 touch agent 组成。主客户端位于 Core 部署机器，Portable 用于远程交互。计划提供更丰富的用户界面、代码 diff（差异展示）和可重建的会话缓存；缓存可从 Core 权威状态重建。
- **通信方案**：主客户端计划采用 SwiftUI；touch agent 的完整能力及跨终端协议仍需明确。HTTPS（加密超文本传输协议）配合 SSE（服务器推送事件）、WSS（加密双向连接）等仅为可选研究方向，尚未决定具体协议。
- **本地模型与断网降级**：最终设计必须包含本地模型，平时可以不用，但须支持断网时的降级运行。离线可用能力与资源要求仍需验证；断网本身不自动需要 root。

#### NX1 专用便携端

考虑为专用 NX1 定制 AOSP（Android 开源系统），以不依赖 GMS（Google 移动服务）的实时通信为目标。用户界面与系统级通信服务分离，规划可靠重连、消息去重、过期处理与回执。

连续在线 **48 小时**是待实测的验收目标，尚非现有能力。

#### Smartband：HK13 生命体征手环接入

**阶段与目标**：以 HK13 作为 internet Portable 下属的生命体征传感器；DS500 原方案不再作为当前实施主线，其 SDK、研究和历史证据保留作对照；更换设备建立独立身份，不改写旧记录的设备来源。现阶段已有 SDK 静态研究，尚不能宣称设备接入、持续采集、测量准确性或告警已经验收。SDK 能力列表不等于 HK13 实机能力。

**数据链路与职责**：HK13 → BLE（低功耗蓝牙）→ NX1 本地采集与持久队列 → Core 设备接口 → 规范化观测、状态与事件 → SwiftUI / Portable 展示。

| 层次 | 规划职责与边界 |
| --- | --- |
| HK13 与 SDK 适配层 | 先用随附 SDK 建立基线，记录设备、固件、SDK 版本和经验证能力；处理扫描、连接就绪、串行请求、取消/停止、超时与重连。不混装不同版本的 SDK，不把其他型号的采样间隔与能力直接套用到 HK13。 |
| NX1 采集端 | 将 BLE 采集与界面生命周期分离；先在本地可靠保存，再批次上传。熄屏、客户端关闭或网络中断不应导致无声丢失；队列容量、保留期、丢弃策略与重启恢复必须明确，存满或采集停止须可观察。 |
| Core 设备入口 | 使用独立、受限、可撤销的设备身份；服务端验证 NX1 与手环的绑定及可上报类型。设备数据不能冒充 Master 输入，NX1 不持有 Core 全权管理凭据；World 中登记从属关系不等于获得代报权限。现有本机管理接口不直接开放为公网设备入口，设备鉴权与安全传输须单独设计。 |
| Core 存储与事件 | 分开保存原始证据、规范化观测、质量状态与派生事件。World 记录稳定设备关系与能力引用，不堆放高频样本；高频数据不逐条进入主会话或触发模型。 |
| SwiftUI 主客户端与其他终端 | 通过统一后端查询与事件接口显示设备状态、趋势和异常，缓存可重建。客户端不直接依赖 QRing 厂商类型，也不负责维持 NX1 的 BLE 连接；客户端退出不停止已授权的采集任务。 |

**首批数据与真实性**：

- 优先验证心率、血氧、历史补采，再逐项扩展 HRV（心率变异性）、厂商压力分数、睡眠和步数。原始 PPG（光电容积脉搏波）与 RRI（搏动间期）只在能力与数据含义得到确认后进入限时研究；不因通用 SDK 存在接口就启用体温、血压、血糖等未确认功能。
- 每条观测须可追溯到设备、固件、SDK、采集模式与转换版本；区分测量时间、接收时间、时区及时间可信度。真实采样间隔、设备存储间隔和展示网格不得混为一谈。
- 保留有效、缺测、陈旧、未佩戴、超时、未知及占位等不同状态。SDK 调用成功不代表数值有效；默认/演示填充值不得进入真实健康指标，不能用正常值掩盖失败，也不能仅凭某个数值猜测是否为占位。
- 未确认单位与算法的 HRV、压力先按厂商原始指标保存，不直接解释为已验证医学指标；换设备、固件或算法后不得无条件沿用旧基线。

**可靠上传与统一接口**：

- 先完成通用设备身份与事件接入，再扩展“NX1 代报已绑定手环”的授权和健康数据合同；只允许网关上报自身的接口不能直接接受子设备数据。
- 本地持久化事件标识，Core 按来源与内容去重，并返回可核验的持久接收回执；确认丢失、断网重传、双端重启不应重复记账或重复通知。同一标识携带不同内容须拒绝或隔离。
- 原始数据已接收、已解析、已形成事件、已展示、Master 已确认和异常已恢复是不同状态，不能用一次 HTTP 成功代替整条链路完成。历史补采须保留历史属性，不能当作新发生的实时异常。
- 为 SwiftUI、Portable 和 touch agent 统一定义版本化的查询、命令与事件语义，但各设备按角色授权。查询支持分页与时间范围；事件支持游标恢复，超出保留窗口时重新获取快照。缓存不得覆盖 Core 权威状态；健康数据的查询、导出、保留期限及本地缓存保护须明确，不能随诊断日志或模型上下文默认外发。
- 采集配置、开始/停止、重新绑定及撤销等操作须走受控命令与执行回执。界面提交成功不等于设备执行成功；离线命令必须有有效期与状态，用户停止或撤权后不得偷偷恢复采集。需要审批的操作完整展示范围，内容或版本变化须重新确认，聊天回复不能替代正式批准动作。

**SwiftUI 展示与交互规划**：

- 提供设备列表/详情，展示 HK13—NX1—Core 从属链路、已验证能力、电量与最近同步时间；分别呈现 BLE 断连、NX1 采集停止、网关断网、Core 不可用及数据陈旧，避免一个“在线”图标掩盖不同故障。
- 提供最新观测、历史趋势、缺测区间和质量说明，可查看数据来源与时间。模拟数据必须明确标识，未知能力不得显示为已支持，缺测不得补成正常读数。
- 提供采集模式与间隔配置、开始/停止、同步进度、失败原因和受控重试入口；仅开放后端及固件确实支持的操作，不在前端自行决定权限或绕过失败状态。
- 提供事件列表与详情，分清待处理、已确认、已恢复；确认提醒不改变原始测量事实。异常提醒和紧急流程按下述告警边界单独设计，不由 UI 单方面推出医学结论。

**实施与测试验收顺序**：

| 阶段 | 必须覆盖的验证 | 完成边界 |
| --- | --- | --- |
| 1. 数据合同与离线模拟 | 使用 fixture（可重复的模拟数据）验证接口版本、分页、事件恢复、缺测/占位、时区与跨日、乱序和历史补采；覆盖不同 SDK 的数组转换与有效长度差异。 | 可先于硬件开展；不代表 SDK 或设备兼容性通过。 |

#### LoRa 应急终端

待产品稳定后探索 LoRa 独立终端，承担短指令与状态链路。两端均需额外无线电模块，必要时配置中继。

理想形态为小型开发板加 4G、LoRa，并进一步缩小体积，当前规划与 NX1 分工。Cardputer 类形态仅为候选，不承诺具体型号可购、频段或覆盖；**3 km** 是特定场景目标，须经过法规核查和实地验证。

#### 独立恢复服务与逃生终端

规划独立恢复控制服务及主会话逃生终端，应对系统、基础环境或必要组件故障。主会话及恢复入口不得依赖已故障的调度器。

- Master 可主动授权，并限定设备权限和有效期；凭据留在受控服务，不进入模型上下文。
- 故障只触发诊断或预授权范围内的恢复，不自动扩大 root 权限。
- 接管机制须防止旧调度器恢复后重复执行。
- 恢复策略、接管机制与权限细节仍需设计验证。

#### 生命体征监测与紧急告警

生命体征监测与紧急告警是待验证的辅助能力；采集、展示和验收规划见上文 Smartband 小节。普通采样先经过确定性质量检查与规则筛选，仅重要状态变化形成有界事件交给主会话。告警优先走预先设计的正常应急流程，执行链路故障时才使用恢复通道；生命体征异常本身不构成绕过权限或自动开启 root 终端的依据。

传感器异常不等于医学诊断，也不构成无限提权依据；该能力不能成为唯一的生命安全保障。
